# ngx_mruby v2.7.15

## 更新前に確認する挙動の変更

### proxyのレスポンスの最後の空のバッファで、mrubyのボディフィルタが2回目に走らなくなった

- 変更前：upstream(`proxy_pass`、`fastcgi_pass`、`uwsgi_pass`、`scgi_pass`、`memcached_pass`)からのレスポンスで、前段のフェーズのハンドラが`Nginx.rputs`か`Nginx.echo`の出力をmodule contextに残してDECLINEDしたあと、`mruby_output_body_filter(_code)`が、upstreamがボディのあとに送る空のlast bufferに対して2回目に走っていました。空のボディへの出力が非空になるボディフィルタ、たとえば`f.body`に前置きや後置きをするものは、この2回目でバイトを作り、そのバイトがレスポンスの`Content-Length`を超えて送られていました。
- 変更後：ボディフィルタは、この空のlast bufferをコードを走らせずに次へ渡します。枠付けされたレスポンスの後ろには何も送られません。
- 変更の理由：
  - 不具合：空のボディへの出力が非空になるボディフィルタが2回目に作り、レスポンスの`Content-Length`を超えて送られていたバイトです。keepaliveの接続では、クライアントがこのバイトを、その接続の次のレスポンスの先頭として読みます。詳細は[GHSA-5qjv-293c-64f8](https://github.com/matsumotory/ngx_mruby/security/advisories/GHSA-5qjv-293c-64f8)にあります。
  - 前の挙動を残せなかった理由：2回目には変換するボディが無いので、作られたバイトは、すでに枠付けして送ったレスポンスの後ろに続くしかありませんでした。
  - ドキュメントが示していた挙動：`docs/class_and_method/`は、ボディフィルタが2回目に走ることを書いていません。`docs/directives/`も、レスポンスの後ろに出力が出ることを書いていません。
- 影響の範囲：`mruby_output_body_filter(_code)`で空のボディへの出力が非空になるものがあり、`Content-Length`の分かるupstreamから配信され、前段のハンドラが`Nginx.rputs`か`Nginx.echo`の出力を残して、リクエストがdeclineして通り過ぎる負のコード(実際には`Nginx::DECLINED`)を返す場合です。空のボディを空のまま返すボディフィルタ(たとえば`f.body = f.body.upcase`)、静的ファイル、chunkedで送るレスポンスは変わりません。
- 必要な対応：ありません。このリリースでモジュールをビルドし直してください。空のボディをガードしていたボディフィルタ(たとえば`unless f.body.empty?`)は、ガードを残しても外してもかまいません。

## 不具合の修正

- macOSが`/usr/bin/make`として備えるGNU make 3.81でも、ビルドがリンクまで通ります。mrubyの`libmruby.flags.mak`は`MRUBY_PACKAGE_DIR`を`!=`で設定します。`!=`はGNU make 4.0で加わった書き方なので、make 3.81ではこの変数が空になり、nginxのリンクが`/lib/libmruby.a`を探して失敗していました。`Makefile.in`は、この変数が空のときに値を設定します。GNU make 4.0以降のビルドは変わりません(#872)。
