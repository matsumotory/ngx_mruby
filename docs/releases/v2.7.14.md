# ngx_mruby v2.7.14

## Behavior changes: read before upgrading

### A Content-Length set through Nginx::Headers_out is no longer sent as a response header line

- Before: `Nginx::Headers_out#[]=` with the name `Content-Length` added a `Content-Length` response header line next to the one that nginx writes from the length of the response body, so a response could carry two `Content-Length` lines with different values.
- Now: a `Content-Length` that a script sets through `Nginx::Headers_out` is not sent; nginx sends its own `Content-Length` for the response, as it does when the script sets none.
- Why it changed:
  - The defect: the second `Content-Length` line that a script's value added next to the one nginx writes. A response with two differing `Content-Length` lines has no single body length. On a response that nginx sends with `Transfer-Encoding: chunked`, the script's line was added next to the `Transfer-Encoding`, which leaves no single body length either; [GHSA-2cf7-qh69-j29q](https://github.com/matsumotory/ngx_mruby/security/advisories/GHSA-2cf7-qh69-j29q) has the details.
  - Why the old behavior could not be kept: the line a script set could not be made to agree with the body in every case, so the fix sends only the length that nginx frames the body by.
  - What the documentation promised: `docs/class_and_method/` on the 2.x line did not describe setting `Content-Length` through `Nginx::Headers_out`.
- Affected: a configuration whose Ruby code sets `Content-Length` through `Nginx::Headers_out` in a content handler, a phase handler or an output header filter. Reading `Content-Length` with `Nginx::Headers_out#[]` and removing it with `#delete` are unchanged.
- What to do: remove the `Nginx::Headers_out#[]=` of `Content-Length`; nginx sends the length of the response. A response of a fixed length is sent by writing that many bytes with `Nginx.rputs`, whose total nginx sends as the `Content-Length`.

## Build and test changes

- CI: the required check `ci-ok` of `test.yml` needs the `perf` job, so a `FAIL` or `ERROR` row of the performance comparison fails it, and a `WARN` row does not. `test/perf/accepted.txt` lists the accepted differences of the comparison, with two conditions. A `mruby-version` line applies when the bundled mruby of the base and of the head match its versions; the file has no such line on `master`. A `pull-request` line names the base branch and the number of a pull request (for example `pull-request master 812 auth 7`) and applies only in the `perf` job of that pull request, which passes both to `perf.rb` in `PERF_BASE_REF` and `PERF_PULL_REQUEST`. A pull request adds such a line after the owner has accepted its `FAIL` in a comment, and the run passes. The comparison judges the Ir per request without the GC, as before ("Known differences" and "In CI" under "Performance comparison with callgrind" in [docs/test/README.md](../test/README.md)) (#865)

## Upgrading

- No directive was added, renamed or removed. Rebuild the module with this release the way you built 2.7.13, and replace the binary or the dynamic module as usual. `Nginx.module_version` returns `2.7.14`.
- If a script sets `Content-Length` through `Nginx::Headers_out`, remove that `[]=`: nginx sends the length of the response, and `Nginx.rputs` sends a response of a fixed length by writing that many bytes.

Read "Behavior changes: read before upgrading" above before you upgrade.
