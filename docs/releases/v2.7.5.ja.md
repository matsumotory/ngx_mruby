# ngx_mruby v2.7.5

## アップグレードの前に読む挙動の変更

### `Nginx::Async.sleep`の後に`Nginx::DECLINED`を返すrewriteハンドラで、後のハンドラが500で応答しなくなります(#739)

- 変更前：rewriteハンドラ、つまり`mruby_rewrite_handler`と`mruby_rewrite_handler_code`が`Nginx::Async.sleep`の後に`Nginx.return`で`Nginx::DECLINED`を返すと、リクエストはステータスを500にしたまま次のフェーズへ進みました。そのため、ステータスを設定しない後のmrubyのハンドラ、例えばaccessハンドラが500で応答し、そのlocationが返す静的なファイルも500になりました。
- 変更後：リクエストは、rewriteハンドラがsleepせずに`Nginx::DECLINED`を返したときと同じように次のフェーズへ進みます。ステータスを設定しない後のハンドラは500で応答しません。contentハンドラは自分の出力で応答し、nginxは静的なファイルを200で返します。
- 変更の理由：
  - 不具合：sleepの後にハンドラを再開するコードが、`Nginx::OK`以外のすべての結果でリクエストのステータスを500にしていました。リクエストが先へ進む`Nginx::DECLINED`でも同じでした。この不具合は、メールで報告を受けました。
  - 前の挙動を残せなかった理由：rewriteハンドラが`Nginx::DECLINED`を返すのは、後のフェーズに応答させるためです。残った500のせいで、どのハンドラも設定していないエラーを後のフェーズが返していました。
  - ドキュメントが示していた挙動：2.7.4の[Nginx::Async#sleep](https://github.com/matsumotory/ngx_mruby/blob/v2.7.4/docs/class_and_method/README.md#nginxasyncsleepmsec)は、rewriteハンドラでsleepを使えると説明し、その後のステータスについては何も書いていませんでした。
- 影響の範囲：`Nginx::Async.sleep`を呼んだ後に`Nginx::DECLINED`を返すrewriteハンドラと、後のmrubyのハンドラがステータスを設定しないlocation、nginxが静的なファイルを返すlocationです。
- 必要な対応：ありません。500に頼っていた設定では、そのステータスを`Nginx.return`でハンドラから返してください。
