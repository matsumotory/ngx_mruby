# ngx_mruby v3.0.0

## アップグレードの前に読む挙動の変更

### ローカルの導入例をループバックに限定し、mockのモデル振り分けを加える(#672)

- 変更前：`examples/start/compose.yaml`はホストの全インターフェースでポート8080を公開し、試用は`/hello`のRubyハンドラだけを扱っていました。
- 変更後：ホストの公開先を`127.0.0.1:8080:8080`にします。`/hello`を残し、公開のデモ用キーを検査してモデルに応じた2つのループバックmockへ転送する`/v1/responses`を加えます。英日の手順で、転送先、認証情報の差し替え、拒否するリクエスト、編集、復元、リロードを確認します。
- 変更した理由：
  - 理由：プロバイダのアカウントや本物のキーを用意せず、最初の試用でモデル振り分けの用途を確認できるようにするためです。
  - 以前の挙動を維持できない理由：ローカルだけの試用に全インターフェースへの公開は不要です。`/hello`は引き続き使えます。
  - 文書が約束していたこと：[従来の導入ページ](https://github.com/matsumotory/ngx_mruby/blob/9221ea4ed2b513eb083d55195b0004db5cacc968/examples/start/README.md)はHelloの応答を示し、ホストのポートが広く公開されることを説明していました。
- 影響の範囲：開発版の`examples/start/`を実行する利用者です。ランタイムAPIや安定版2.xの設定は変わりません。
- 必要な対応：更新した手順をローカルで実行してください。同梱のキーはデモ用で、mockの応答はLLMによる生成、プロバイダ互換性の試験、API形式の変換ではありません。この試用を公開サービスにしないでください。

### 同梱のmrubyが3.3.0から4.1.0-rc2になる(#561, #678)

- 変更前：ngx_mruby 2.xはmruby 3.3.0を同梱し、mruby 3.3.0の`full-core.gembox`が選ぶコアgemをビルドします。その中にmruby-printも入ります。
- 変更後：このリリースは、4.1.0のリリース候補であるmruby 4.1.0-rc2を同梱します。これはmrubyのタグ`4.1.0-rc2`で、コミットは`c17ffcc24190`、日付は2026-09-11です。その`MRUBY_VERSION`は`4.1.0`です。既定の`build_config.rb`は、`NGX_MRUBY_CORE_GEMS`が名前で挙げるコアgemを取り込みます。この一覧は、mruby 3.3.0の`full-core.gembox`が選んでいた集合からmruby-printを除いたものです。mruby-printは、mruby 3.4で削除されました。`Kernel#print`、`#puts`、`#p`は、mruby-ioが定義します。一覧は、4.1.0-rc2の`full-core.gembox`が取り込む次のコアgemを含みません。mruby-task、mruby-encoding、`Time#strftime`を定義するmruby-strftime、`Benchmark`を定義するmruby-benchmark、そして4.1で加わったmruby-env、mruby-process、mruby-regexp、mruby-signal、mruby-string-bitops、mruby-bin-mrbです。`ENV`、`Process`、`Regexp`は、これまでどおりサードパーティのgemのiij/mruby-env、iij/mruby-process、mattn/mruby-onig-regexpが定義します。一方、`full-core.gembox`が含まないmruby-sleepは含みます。mruby 4.1は、RubyのコードをPrismでコンパイルします。nginxが設定を読むときに`info`のレベルで出す行は、`(mruby/4.1.0) mechanism enabled`で終わります。以下の項目は、スクリプト、ログの監視、C拡張、ビルドから見える違いのうち、ngx_mrubyのために見つけて測ったものを挙げます。mruby 3.3.0から4.1.0-rc2までの変更をすべて挙げたものではありません。mrubyは、利用者から見える変更を[`doc/mruby3.4.md`](https://github.com/mruby/mruby/blob/4.1.0-rc2/doc/mruby3.4.md)と[`doc/mruby4.0.md`](https://github.com/mruby/mruby/blob/4.1.0-rc2/doc/mruby4.0.md)に、4.1については[`NEWS.md`](https://github.com/mruby/mruby/blob/4.1.0-rc2/NEWS.md)に挙げています。リクエストあたりのコストを、同梱していたmruby 4.0.0と比べてngx_mrubyで測りました。測ったのはcallgrindのレーンで、nginxのユーザー空間の命令数をリクエストごとに数えています(2026年10月31日、#678)。`auth`は、サーバーのrewriteハンドラでHashを2回引き、変数に3回代入してからプロキシするシナリオです。命令数は44228から52761に増え、GCを除くと42599から45621に増えました。`headers`では30040から34903で、GCを除くと28044から27612です。3GHzで1サイクルに1〜2命令を実行すると、1命令は0.17〜0.33nsです。そのため`auth`のCPU時間は、4.0.0では1リクエストあたり約7.4〜14.7µs、4.1.0-rc2では8.8〜17.6µsで、1.4〜2.8µs増えます。毎秒10,000リクエストでは、1コアの7.4〜14.7%の代わりに8.8〜17.6%を使います。GCは前より多く動き、1回の仕事も増えます。`auth`では、1000リクエストあたりのGCの呼び出しが12.2回から24.4回に、1回あたりの命令数が134,000から293,000に増えました。mruby 4.1は、前のマークで空きが残っていれば、ヒープのページを足す代わりに全体のGCを実行します。これは小さいターゲットのヒープを抑えるためのmrubyのコミットc009f1633によるものです。また、4.1のVMは同じバイトコードに多くの命令を使います。詳しくは[docs/test/README.md](../test/README.md)の「Performance comparison with callgrind」の「Known differences」にあります。
- 変更の理由：
  - 背景：v3の計画は、安定性、性能、依存するソフトウェアの更新を、新しい機能より先にします。また、mrubyは3.xの保守のリリースを出していません。根拠は`docs/proposals/v3-plan.md`の3.3節と6節です。計画の7節の決定1は、v3のmrubyを4.1.0とします。4.1は`mrb_gc_register()`の登録を数えるためです。あるオブジェクトに2回目の`mrb_gc_unregister()`を呼んでも、別の持ち主の登録は消えなくなりました(mruby/mruby#7277)。`Nginx::Async`は、ファイバをこの方法で登録します。オーナーは2026-10-29に、タグ`4.1.0`を待たずに4.1.0-rc2を同梱することを選びました。4.1.0のタグが付いたら、`next`は4.1.0に移ります。4.1.0-rc2は、mruby/mruby#7032の修正であるコミット`c6866eed4`を含みます。
  - 前の挙動を残せなかった理由：mruby 3.3.0には、もう修正が出ません。4.1の`NEWS.md`だけでも、「Security Fixes」の節に4.0からの修正を20項目挙げています。その中には、`String#lstrip!`、`#rstrip!`、`#strip!`のuse-after-freeと、インクリメンタルGCのuse-after-freeがあります。3.3.0を残すと、こうした不具合がすべてのワーカーに残ります。
  - ドキュメントが示していた挙動：2.xのドキュメントは、後のリリースが同梱するmrubyのバージョンについて何も書いていません。2.7.0の[docs/install/README.md](https://github.com/matsumotory/ngx_mruby/blob/v2.7.0/docs/install/README.md#2-configuring-mrbgems)は、既定のmrbgemを「mruby/mruby default mrbgems」と、バージョンなしで挙げています。
- 影響の範囲：このモジュールのすべてのビルドと、モジュールが実行するすべてのRubyスクリプトです。
- 必要な対応：同梱のmrubyと一緒にモジュールをビルドし直してください。そのうえで以下の項目を確かめ、項目が扱わない変更をmrubyの3つの一覧で確かめてください。手順は[Migrating from ngx_mruby 2.x to 3.0.0](../migration/README.md)にあります。ngx_mrubyは、mrubyのGCの既定値をそのまま使います。`GC.interval_ratio`を変えてもGCの割合は変わらず、ヒープを大きくするとGCの割合は下がりましたが、GCを除いた仕事が増えました。

### 自前の`build_config.rb`は、mruby 4.1のコアgemの変更に合わせる必要がある(#561, #678)

- 変更前：自前の`build_config.rb`は、mruby-printを名前で挙げることも、`full-core.gembox`を取り込んでmruby 3.3.0のコアgemを得ることもできました。その中にmruby-sleepも入ります。
- 変更後：mruby 4.1.0-rc2には、mruby-printもhal-*のgemもありません。`build_config.rb`の`ngx_mruby_core_gems`は、同梱のmrubyに無い名前があるとビルドを止めます。mruby 4.0.0向けに書いた一覧で、hal-posix-io、hal-posix-dir、hal-posix-socketを挙げるものも、そこで止まります。4.1では、POSIXのバックエンドはmruby-io、mruby-dir、mruby-socketの中にあるためです。4.1.0-rc2の`full-core.gembox`は、mruby-taskとmruby-encodingを取り込み、mruby-sleepを含みません。mruby-taskは`Kernel#sleep`を定義し直します。また、mrb_stateを開くすべてのプロセスでSIGALRMのインターバルタイマー(`setitimer`)を動かし、mrb_stateの数を最大8個(`MRB_TASK_MAX_VMS`)に制限します。mruby-encodingについては`String#valid_encoding?`の項目を参照してください。`full-core.gembox`は、mruby-env、mruby-process、mruby-regexpも取り込みます。この3つは`ENV`、`Process`、`Regexp`を定義します。これらは、iij/mruby-env、iij/mruby-process、mattn/mruby-onig-regexpが定義するクラスです。また、iijの2つのgemは、これらのコアgemと同じ名前です。`mruby/lib/mruby/gem.rb`の`for_windows?`は、ルートにある1文字のディレクトリをWindowsのドライブとみなします。コンテナの`/s`に作業ディレクトリをマウントした4.0.0のビルドは、Windowsのバックエンドを自分で選び、`windows.h: No such file or directory`で止まりました。4.1.0-rc2の`for_windows?`も同じ判定をします。これはソースを読んで確かめたもので、測ってはいません。
- 変更の理由：
  - 背景：これらは、同梱のmrubyに伴う、mruby 3.4、4.0、4.1の変更です。上の項目を参照してください。
  - 前の挙動を残せなかった理由：同梱のmrubyに無いコアgemは、ビルドできません。また、`ngx_mruby_core_gems`は、そうした名前があるとわざとビルドを止めます。mrubyを更新したときに、一覧からgemが気づかれずに抜けないようにするためです。
  - ドキュメントが示していた挙動：2.7.0の[docs/install/README.md](https://github.com/matsumotory/ngx_mruby/blob/v2.7.0/docs/install/README.md#2-configuring-mrbgems)は「mruby/mruby default mrbgems」と挙げるだけで、自前の`build_config.rb`のコアgemについては何も書いていません。
- 影響の範囲：このリリースのものとは別の`build_config.rb`を使い、mruby-printかhal-*のgemを名前で挙げるか、`full-core.gembox`を取り込むビルドです。
- 必要な対応：このリリースの`build_config.rb`から始めるか、`NGX_MRUBY_CORE_GEMS`と同じようにコアgemを名前で選んでください。mruby-print、hal-posix-io、hal-posix-dir、hal-posix-socketを除いてください。mruby-taskとmruby-encodingを使うかどうかは、[コアのgem](../ja/install/README.md#コアのgem)の説明に従って決めてください。`full-core.gembox`と一緒にiij/mruby-env、iij/mruby-process、mattn/mruby-onig-regexpのどれかを取り込むビルドは、それらとコアgemのmruby-env、mruby-process、mruby-regexpのどちらを使うかを選んでください。

### 同梱のmrubyのビルドにRuby 3.0以降が要る(#678)

- 変更前：2.xが同梱するmruby 3.3.0のrakeは、Ruby 2.xでビルドできます。その`mrbc`は、macOSのRubyの2.6.10でビルドできます。
- 変更後：mruby 4.1.0-rc2のrakeをRuby 2.6.10で動かすと、`mrbc`をリンクするところで止まります。メッセージは`ArgumentError: unknown keywords: flags, flags_before_libraries, flags_after_libraries, libs, outfile, objs`で、場所は`mruby/lib/mruby/build/command.rb`の47行目です。Ruby 3.0.2とRuby 4.0.5では、ビルドできます。Ruby 3.0.2は、Ubuntu 22.04のRubyで、CIとテストのコンテナが使います。`Command::Linker#run`は、リンクのパラメーターをHashで`_run(options, params={}, chdir: nil)`に渡します。3.0より前のRubyは、メソッドがキーワード引数を取ると、Symbolのキーを持つ最後のHashをキーワード引数として読みます。Ruby 2.7は測っていませんが、この規則によって同じく止まります。mruby自身の`doc/guides/compile.md`は、今も「Ruby 2.5 or later」と書いています。
- 変更の理由：
  - 背景：mruby 4.1でビルドの仕組みが変わりました。「同梱のmrubyが3.3.0から4.1.0-rc2になる」の項目を参照してください。このリリースは、mruby 4.1.0-rc2を同梱します。
  - 前の挙動を残せなかった理由：Ruby 2.xを使い続けるには、`mruby/`を変える必要がありました。ngx_mrubyは、`mruby/`をmruby自身のツリーからだけ更新します。
  - ドキュメントが示していた挙動：2.7.0の[docs/install/README.md](https://github.com/matsumotory/ngx_mruby/blob/v2.7.0/docs/install/README.md)は、Rubyとrakeを求めるだけで、バージョンを挙げていません。
- 影響の範囲：Ruby 2.xで動かすビルドです。例えば、Ubuntu 20.04の`ruby`パッケージの2.7や、macOSのRubyの2.6です。
- 必要な対応：Ruby 3.0以降でビルドしてください。バージョン管理ツールでRubyを選ぶ場合は、ビルドの前にそのRubyの`bin`ディレクトリを`PATH`に入れてください。

### サードパーティのmrbgemを`build_config.rb.lock`が記録するコミットでビルドする(#558)

- 変更前：`build_config.rb`は、サードパーティのmrbgemをコミットを指定せずに挙げます。`.gitignore`は、mrubyのrakeが書く`build_config.rb.lock`を挙げているので、ロックはリポジトリに入りません。新しいチェックアウトやソースのアーカイブからのビルドは、各gemのブランチの先頭を`git clone --depth 1`でクローンします。そのため、同じngx_mrubyのコミットを別の日にビルドすると、別のgemのコードが入ることがあります。
- 変更後：`build_config.rb.lock`はリポジトリに入っています。ロックは、既定のビルドに入るサードパーティのgemと、それらが依存するgemのコミットを記録します。依存するgemの例は、同梱のrack-based-apiが必要とするksss/mruby-stringioです。新しいチェックアウトやソースのアーカイブからのビルドは、これらのgemを履歴ごとクローンし、記録されたコミットをチェックアウトします。そのため、ngx_mrubyのあるコミットをビルドすると、いつも同じgemのコードが入ります。自前の`build_config.rb`が加えるgemは、ブランチの先頭でクローンされます。rakeはそのgemの項目を手元のツリーにあるロックに加えるので、`git status`はロックを変更ありと表示します。rakeは、既にあるクローンにはフェッチしません。そのため、ロックが変わった後に`mruby/build`を残したツリーでビルドすると、ビルドが`fatal: reference is not a tree`で止まることがあります。止まるのは、新しいコミットを持たないクローンがあるときです。matsumotory/mruby-vedisが自分でクローンするsymisc/vedisはロックでは固定されません。
- 変更の理由：
  - 背景：v3の計画は、すべてのサードパーティのgemをコミットで固定し、`build_config.rb.lock`をコミットします。同じタグから同じバイナリをビルドできるようにするためです。この方針の根拠は`docs/proposals/v3-plan.md`の4節のPillar Aです。
  - 前の挙動を残せなかった理由：固定が無いと、ビルドに入るgemのコードはビルドした日で決まります。gemのリポジトリのどれかが変わると、その変更は、リリースしたタグを後でビルドするたびに入ります。CIの実行にも毎回入ります。どちらも、ngx_mrubyに変更が無くても起きます。
  - ドキュメントが示していた挙動：2.xのドキュメントは、サードパーティのgemのコミットについて何も書いていません。[docs/install/README.md](https://github.com/matsumotory/ngx_mruby/blob/v2.7.0/docs/install/README.md#2-configuring-mrbgems)は、既定のmrbgemを名前だけで挙げています。
- 影響の範囲：サードパーティのgemを最新のコミットで取り込むことを前提にした、ソースからのビルドです。gemを加える自前の`build_config.rb`と、ロックが変わるときに`mruby/build`を残すソースツリーも影響を受けます。
- 必要な対応：新しいチェックアウトとソースのアーカイブでは、何もしなくてかまいません。gemを別のコミットでビルドするには、[gemのコミットとbuild_config.rb.lock](../ja/install/README.md#gemのコミットとbuild_configrblock)の説明に従ってロックの項目を変えてください。`git pull`で入る変更も含め、ロックが変わったら、次のビルドの前に`mruby/build`を削除してください。

### `Hash#inspect`と`Hash#to_s`の形式が変わる(#561)

- 変更前：返る文字列は`{"a"=>1}`と`{:a=>1}`の形式です。
- 変更後：`{"a" => 1}`と`{a: 1}`です。mruby 3.4からこの形式です。これらのメソッドでHashを文字列にするものは、すべて同じく変わります。式展開(`"#{h}"`)、`sprintf("%s", h)`、`Array#inspect`がこれに当たります。
- 影響の範囲：Hashの`inspect`や`to_s`を、レスポンスのボディやヘッダに入れるスクリプトと、固定の文字列と比べるスクリプトです。ngx_mrubyのテストスイートでもこの変化が出ました。変化が出たのは`test/t/ngx_mruby.rb`の`/async_http_sub_request`です。
- 必要な対応：Hashの`inspect`や`to_s`を、レスポンスのボディやヘッダでデータの形式として使わないでください。文字列を自分で組み立てるか、`JSON.generate`を使ってください。

### `Exception#inspect`の形式が変わり、`error.log`の`mrb_run failed`の行も変わる(#561)

- 変更前：`boom (RuntimeError)`です。ngx_mrubyは、スクリプトの例外を`Exception#inspect`で文字列にして、`error.log`の`mrb_run failed`の行に書きます。この行のレベルは`error`です。ただし、nginxが設定を読む間に`mruby_stream_server_context_code`の例外が出す行のレベルは`emerg`です。その行は`mrb_run failed: ngx_mruby stream module configuration failed: error: ...`です。`error`の行の例は`mrb_run failed: return 500 HTTP status code to client: error: boom (RuntimeError)`です。
- 変更後：`#<RuntimeError: boom>`です。そのため、行は`error: #<RuntimeError: boom>`で終わります。`Exception#message`と`#to_s`は変わりません。
- 影響の範囲：古い形式に合わせたログのパーサーとアラートと、`Exception#inspect`を使うスクリプトです。ngx_mrubyのテストスイートでも`error.log`にこの形式の変化が出ました。
- 必要な対応：古い形式に合わせたログのパーサーとアラートを直してください。

### nginxが設定を読む間のメッセージのレベルが`notice`から`info`になる(#565)

- 変更前：nginxが設定を読む間、ngx_mrubyは次のメッセージを`notice`のレベルで出します。`http {}`のブロックに対して1回出す`ngx_mruby/<version> (mruby/<version>) mechanism enabled`、Rubyのコードを持つディレクティブごとの`ngx_mruby NOTICE ...: compile info: ...`、`stream {}`の中のそうしたディレクティブごとの`ngx_mruby-stream-module NOTICE ...: compile info: ...`、`mruby_set`と`mruby_set_code`ごとの`ngx_mruby NOTICE ...: target variable=(...)`です。nginxは、設定を読む間に出すログを起動時のログに書きます。起動時のログのレベルは、`error_log`の設定にかかわらず`notice`です。そのため、nginxを起動するたびにこれらの行が書かれます。`error_log ... warn;`でも同じです。
- 変更後：同じメッセージを`info`のレベルで出します。本文の`NOTICE`は`INFO`になります。行は`ngx_mruby INFO ...`と`ngx_mruby-stream-module INFO ...`です。nginxを起動しても、これらの行は書かれません。`nginx -t`は、これらの行を起動時のログだけに`[info]`で書きます。nginxが起動時のログの行を端末にも出力するのは、`warn`以上のレベルの行だけです。そのため、`nginx -t`の出力にこれらの行は出ません。動いている設定で`error_log`のレベルが`info`か`debug`なら、reloadはその`error_log`にこれらの行を書きます。開けないスクリプトのファイルのような、設定を読む間のエラーは、これまでどおり`emerg`で出ます。
- 変更の理由：
  - 不具合：nginxを起動するたびにこれらの行が書かれ、`error_log`のレベルを`notice`より上にしても止まりませんでした(#320)。
  - 前の挙動を残せなかった理由：nginxは、設定を読む間のログを起動時のログに`notice`のレベルで書き、設定した`error_log`にはその後で切り替えます。そのため、`error_log`をどう設定しても、`notice`のメッセージは除けません。起動時にこれらの行をログに出さないためには、`notice`より下のレベルにするしかありません。
  - ドキュメントが示していた挙動：2.xのドキュメントは、これらのメッセージについて何も書いていません。
- 影響の範囲：nginxの起動時にこれらの行を探すログの監視とスクリプトです。例えば、モジュールが読み込まれたことを確かめるためにこれらの行を探すものです。
- 必要な対応：これらの行を見るには、`nginx -t -e stderr`を実行するか、`nginx -t`の後で起動時のログを読むか、`error_log`を`info`にしてreloadしてください。`nginx -t -e stderr`は、起動時のログを端末に書きます。起動時のログは、`-e`で与えたファイルです。`-e`が無いときは、nginxのビルドで決めたエラーログのパスです。既定はprefixの下の`logs/error.log`です。説明は[Messages logged while nginx reads the configuration](../directives/README.md#messages-logged-while-nginx-reads-the-configuration)にあります。

### `NoMethodError`のメッセージがレシーバのクラスを示す(#561)

- 変更前：`undefined method 'foo'`です。
- 変更後：`undefined method 'foo' for NilClass`です。
- 影響の範囲：`NoMethodError`のメッセージの文字列にマッチさせるスクリプトとログの監視です。
- 必要な対応：メッセージでなく、例外のクラスで判定してください。

### `private`と`protected`の制限が効く(#561, #678)

- 変更前：制限は効きません。`private`や`protected`の後で定義したメソッド、`initialize`、トップレベルで`def`で定義したメソッド、`Kernel`のメソッドを、明示したレシーバで呼べます。`Kernel`自身もレシーバにできます。例えば`Kernel.Integer("12")`は`12`です。`Module#instance_methods`とオブジェクトの`#methods`は、privateメソッドも挙げます。メソッド`pub`とprivateメソッド`priv`を持つクラスでは、`instance_methods(false)`は`[:priv, :pub]`です。
- 変更後：制限が効きます。mruby 3.4からです。これらのメソッドを`self`以外の明示したレシーバで呼ぶと、`NoMethodError`が出ます。メッセージは`private method '<name>' called for <class>`です。対象には、`raise`、`sprintf`、`puts`、`Integer`、`rand`のような`Kernel`のメソッドを別のオブジェクトをレシーバにして呼ぶ場合と、mruby 4がprivateとして定義する`initialize_copy`、`respond_to_missing?`、`method_missing`も入ります。`1.Integer("3")`は`private method 'Integer' called for Integer`を出し、`"a".initialize_copy("b")`も例外を出します。`Kernel`自身をレシーバにすると、`Kernel`のメソッドは2.xと同じく動きます。`Kernel.Integer("12")`は`12`です。mruby 4.0.0ではここで`NoMethodError`が出ましたが、4.1は再び呼べるようにしました(mruby/mruby#6976)。`protected`のメソッドは、CRubyと同じく、同じクラスのメソッドの中からなら明示したレシーバで呼べます。それ以外の場所から呼ぶと、`NoMethodError`が出ます。メッセージは`protected method '<name>' called for <class>`です。`respond_to?`は、どちらのバージョンでもprivateメソッドに`true`を返します。そのため、`respond_to?`では、そうした呼び出しが動くかどうかを判定できません。`Module#instance_methods`とオブジェクトの`#methods`は、privateメソッドを挙げません。上のクラスの`instance_methods(false)`は`[:pub]`です。privateメソッドは、`Module#private_instance_methods`と`#private_methods`が挙げます。ただし、ハンドラのコードのトップレベルで`def`で定義したメソッドはpublicのままで、明示したレシーバで呼べます。理由は[#502の提案](../proposals/archive/handler-code-frame.md#14-what-handler-code-shares-today)の1.4節にあります。
- 変更の理由：
  - 背景：mruby 3.4は、CRubyと同じくメソッドの可視性を守らせます。mruby 4.1は、`protected`のメソッドのレシーバを、呼び出し元の`self`のクラスと照らします(mruby/mruby#6975、mrubyの`NEWS.md`のコミット534efe0)。このリリースは、mruby 4.1.0-rc2を同梱します。「同梱のmrubyが3.3.0から4.1.0-rc2になる」の項目を参照してください。
  - 前の挙動を残せなかった理由：同梱のmrubyのVMが可視性を確かめます。ngx_mrubyには、この確かめを止めるオプションがありません。
  - ドキュメントが示していた挙動：2.xのドキュメントは、メソッドの可視性について何も書いていません。
- 影響の範囲：そうしたメソッドを、`self`と`Kernel`以外の明示したレシーバで呼ぶスクリプトです。`instance_methods`や`methods`の結果からprivateメソッドを探すスクリプトも当たります。
- 必要な対応：レシーバなしで呼ぶか、`send`で呼んでください。`obj.send(:name)`はどちらのバージョンでも動きます。privateメソッドを挙げるには、`private_instance_methods`か`private_methods`を使ってください。

### `Module#remove_const`、`#private`、`#public`、`#protected`、`#module_function`とフックがprivateになる(#561)

- 変更前：publicです。`Foo.remove_const(:X)`、`M.included(Foo)`、`M.prepended(Foo)`、`obj.singleton_method_added(:m)`が動きます。ここで言うフックは、`Module`と`Class`の`#included`、`#extended`、`#prepended`、`#inherited`、`#method_added`と、`BasicObject#singleton_method_added`です。
- 変更後：privateです。明示したレシーバで呼ぶと、`NoMethodError: private method ... called`が出ます。`send`では動きます。mrubyは今もフックを自分で呼びます。`prepend`は`prepended`を、`def obj.m`は`singleton_method_added`を呼びます。
- 影響の範囲：これらのメソッドのどれかを明示したレシーバで呼ぶスクリプトです。
- 必要な対応：クラスやモジュールの本体の中でレシーバなしで呼ぶか、`send`で呼んでください。例えば`Foo.send(:remove_const, :X)`と書きます。

### `append_features`、`prepend_features`、`extend_object`のオーバーライドが呼ばれなくなる(#561)

- 変更前：`include`、`prepend`、`extend`はこの3つのメソッドを呼ぶので、モジュールはこれらをオーバーライドできます。
- 変更後：3つのメソッドはありません。`Module.new.respond_to?(:append_features, true)`は`false`で、他の2つも同じです。`include`、`prepend`、`extend`は、これらを呼ばずにモジュールを加えます。そのため、オーバーライドしたメソッドは呼ばれず、エラーも出ません。フックの`included`、`prepended`、`extended`は今も呼ばれます。
- 影響の範囲：3つのメソッドのどれかをオーバーライドするモジュールです。
- 必要な対応：そのコードを、フックの`included`、`prepended`、`extended`に移してください。

### `allbits?`、`anybits?`、`nobits?`が`Integer`だけのメソッドになる(#561)

- 変更前：`Numeric`のメソッドなので、Floatでも動きます。`1.5.allbits?(1)`は`true`です。
- 変更後：`Integer`だけのメソッドです。Floatに呼ぶと`NoMethodError`が出ます。Integerではこれまでどおり動きます。例えば`6.allbits?(2)`は`true`です。
- 影響の範囲：Floatにこれらを呼ぶスクリプトです。
- 必要な対応：Floatを先に`to_i`で変換してください。

### `FileTest`がモジュールになる(#561)

- 変更前：`FileTest`はモジュールでなく、クラスです。
- 変更後：`FileTest`はモジュールです。`FileTest.exist?`などのメソッドは、これまでどおりの形で呼べます。
- 影響の範囲：`FileTest`を、そのメソッドを呼ぶ以外の形で、クラスとして使うスクリプトです。
- 必要な対応：メソッドを呼ぶだけなら、何もしなくてかまいません。

### メソッドの本体で定数に代入すると`SyntaxError`になる(#561)

- 変更前：許されます。例は`def m; X = 1; end`です。
- 変更後：スクリプトをコンパイルするときに`SyntaxError`が出ます。メッセージは`syntax error, dynamic constant assignment`です。
- 影響の範囲：メソッドの本体で定数に代入するスクリプトです。ngx_mrubyのRack風の`Kernel#run`は、`Kernel.const_set`で`Server`を設定します。
- 必要な対応：`Object.const_set(:X, 1)`か`Kernel.const_set`を代わりに使ってください。

### 文字列の中の`"#@ivar"`、`"#@@cvar"`、`"#$global"`が変数を展開する(#678)

- 変更前：ダブルクォートの文字列、ヒアドキュメント、バッククォートのコマンドの中で、`#`の後に`@`、`@@`、`$`と名前が続く部分は、ただの文字です。`@x = 5; "a#@x"`は`"a#@x"`です。
- 変更後：CRubyと同じく、これらは変数を展開します。`"a#@x"`は`"a5"`になり、`"#$gv"`は`$gv`の値になります。設定していないインスタンス変数は空の文字列になります。`"a#@nope"`は`"a"`です。`#{...}`はこれまでどおり動きます。これはmruby 4.1からの変更で、[d4aad5d](https://github.com/mruby/mruby/commit/d4aad5d)です。
- 変更の理由：
  - 背景：mruby 4.1は、CRubyにあるこの形の展開を加えました。「同梱のmrubyが3.3.0から4.1.0-rc2になる」の項目を参照してください。
  - 前の挙動を残せなかった理由：同梱のmrubyのコンパイラがこの形を読みます。ngx_mrubyには、これを止める設定がありません。
  - ドキュメントが示していた挙動：2.xのドキュメントは、これについて何も書いていません。
- 影響の範囲：ダブルクォートの文字列に、`#@`、`#@@`、`#$`の後に名前が続く部分を含むスクリプトです。例えば、`"Ticket #@id"`や`"price #$total"`のように、文字どおりの意味で書いた文字列です。レスポンスのボディやヘッダに入れる文字列も当たります。
- 必要な対応：そうした文字列を探し、`#`をエスケープするか(`"a\#@x"`)、シングルクォートの文字列(`'a#@x'`)にしてください。探し方は[スクリプト](../ja/migration/README.md#スクリプト)にあります。こうした文字列は、どちらのバージョンでも同じになります。

### 構文エラーのメッセージがPrismのものになる(#678)

- 変更前：mruby 3.3.0のパーサーは、`syntax error, unexpected end of file`や`dynamic constant assignment`のようなメッセージを出します。
- 変更後：mruby 4.1はPrismでコンパイルし、`SyntaxError`はPrismのメッセージを持ちます。`eval("1 +")`は`syntax error, unexpected end-of-input; expected an expression after the operator`の`SyntaxError`を出します。`eval("foo(")`は``syntax error, unexpected end-of-input; expected a `)` to close the arguments``を、`eval("x = ")`は``syntax error, expected an expression after `=` ``を出します。これはビルドの`mruby`コマンドで測ったものです。ngx_mrubyが、構文の正しくないスクリプトのファイルやインラインのコードをコンパイルするときにmrubyが出すメッセージも、同じコンパイラから来ます。
- 変更の理由：
  - 背景：mruby 4.1は、`parse.y`から生成していたパーサーをPrismに置き換えました。根拠は[`NEWS.md`](https://github.com/mruby/mruby/blob/4.1.0-rc2/NEWS.md)の「the compiler is Prism」です。
  - 前の挙動を残せなかった理由：同梱のmrubyには、他のコンパイラがありません。
  - ドキュメントが示していた挙動：2.xのドキュメントは、構文エラーのメッセージについて何も書いていません。
- 影響の範囲：構文エラーの文面に一致させるログの監視とスクリプトです。例えば、`eval`の構文エラーや、nginxが読み込めなかったスクリプトの構文エラーを見るものです。
- 必要な対応：`syntax error`の後の文面でなく、`SyntaxError`と、ファイルと行に一致させてください。

### 自分自身を持つ`Array`、`Hash`、`Struct`を比べられる(#678)

- 変更前：自分自身を要素に持つ2つの配列、ハッシュ、構造体を`==`や`eql?`で比べると、再帰が終わらず、`SystemStackError`が出ます。`a = []; a << a; b = []; b << b; a == b`は、`SystemStackError`(`stack level too deep`)を出します。
- 変更後：このような比較は、CRubyと同じく動きます。比べている最中の組は等しいとみなし、他の要素で結果が決まります。上の`a == b`は`true`です。`a = [1]; a << a; b = [2]; b << b`のときの`a == b`は`false`です。mruby 4.1からの挙動で、mruby/mruby#7425の変更です。mruby 3.3.0の`mruby`コマンドと、このリリースのhostのビルドが作る`mruby`コマンドで測りました。
- 変更の理由：
  - 背景：mruby 4.1は、自分自身を持つコンテナについて、`Array`、`Hash`、`Struct`の`#==`と`#eql?`を変えました。「同梱のmrubyが3.3.0から4.1.0-rc2になる」の項目を参照してください。
  - 前の挙動を残せなかった理由：同梱のmrubyには新しいメソッドしかなく、ngx_mrubyには前のメソッドに戻すオプションがありません。
  - ドキュメントが示していた挙動：2.xのドキュメントは、これについて何も書いていません。
- 影響の範囲：自分自身を持つコンテナを比べ、`SystemStackError`を`rescue`するスクリプトです。
- 必要な対応：ほとんどのスクリプトでは、何もしなくてかまいません。`SystemStackError`を前提にするスクリプトは、比べる前に、コンテナが自分自身を持つかを確かめてください。

### Floatの値にビット演算が無くなる(#561)

- 変更前：`~`、`&`、`|`、`^`は整数部に対して動きます。`1.5 & 1`は`1`、`~1.5`は`-2`です。シフトの回数をnとします。nが1以上のとき、`<<`はFloatに2のn乗を掛けて切り捨てます。`1.5 << 1`は`3`、`-1.5 << 1`は`-3`、`1.5 << 40`は`1649267441664`です。結果がIntegerの範囲を超えると、Floatを返します。例えば`1.5 << 70`は`1.77088743107612e+21`です。nが1から32のとき、`>>`は正のFloatを2のn乗で割って切り捨てます。`8.0 >> 1`は`4`、`1.5 >> 1`は`0`です。nが1から32のとき、`>>`は負のFloatには`-1`を返します。例えば`-8.0 >> 1`は`-1`です。nが32を超えると、`>>`は正のFloatに`0`を、負のFloatに`-1`を返します。`1e20 >> 32`は`23283064365`、`1e20 >> 33`は`0`です。nが0のときは、Floatをそのまま返します。例えば`-1.5 >> 0`は`-1.5`です。nが負なら、逆の向きにシフトします。例えば`1.5 >> -1`は`3`です。
- 変更後：`~`、`&`、`|`、`^`、`>>`、`<<`は、Floatに`NoMethodError`を出します。mruby 3.4が6つすべてを削除しました。
- 影響の範囲：6つの演算子のどれかをFloatに使うスクリプトです。
- 必要な対応：`~`、`&`、`|`、`^`では、先に`to_i`で変換してください。`<<`と`>>`では、先に`to_i`で変換すると別の数になることがあります。`1.5.to_i << 1`は`2`、`-8.0.to_i >> 1`は`-4`です。前の数が必要なら、シフトの回数をnとして次のようにしてください。`<<`でnが1以上なら、Floatに2のn乗を掛けて`to_i`を呼びます。`>>`でnが1から32なら、正のFloatを2のn乗で割って`to_i`を呼び、負のFloatには`-1`を使います。`>>`でnが32を超えるなら、正のFloatには`0`を、負のFloatには`-1`を使います。この場合に割ると、別の数になります。例えば`(1e20 / 2**40).to_i`は`90949470`ですが、`1e20 >> 40`は`0`でした。nが0なら、Floatをそのまま使います。

### `String#valid_encoding?`が既定のビルドに無くなる(#561)

- 変更前：mruby-string-extが定義します。ngx_mruby 2.xは、既定の`build_config.rb`ではmrubyを`MRB_UTF8_STRING`なしでビルドします。そのため、このメソッドはすべての文字列に`true`を返し、`"\xfe"`にも`true`を返します。`build_config.rb`で`MRB_UTF8_STRING`を定義した2.xのビルドでは、UTF-8として正しくない文字列に`false`を返します。
- 変更後：mruby 3.4からは、このメソッドを定義するのはmruby-encodingだけです。既定のビルドはそのgemを含まないので、呼ぶと`NoMethodError`が出ます。メッセージは`undefined method 'valid_encoding?' for String`です。このメソッドを呼ぶハンドラは、500を返します。
- 影響の範囲：`String#valid_encoding?`を呼ぶスクリプトです。
- 必要な対応：2.xの既定の`build_config.rb`で使っていたスクリプトでは、呼び出しを削除してください。そこでは、このメソッドが`false`を返したことはありません。あるいは、mruby-encodingを加えてビルドし、[コアのgem](../ja/install/README.md#コアのgem)の説明に従ってスクリプトを確かめてください。`MRB_UTF8_STRING`を定義していた2.xのビルドで判定を続けるには、mruby-encodingが必要です。既定のビルドがmruby-encodingを含まない理由は次のとおりです。このgemはビルド全体に`MRB_UTF8_STRING`を定義するので、`String#size`、`#[]`、`#index`が、バイトでなく文字を数えます。そのため、`String#size`から`Content-Length`を計算するスクリプトは、別の数を得ます。オーナーは2026-10-04に、このgemを既定のビルドから外し、必要なときに加える形にすると決めました。

### シードを与えた`Random`が別の数を返す(#561)

- 変更前：`Random.new(seed)`と`srand(seed)`は、1つのシードに対して1つの数列を返します。アルゴリズムはxoshiroです。
- 変更後：同じシードに対して2.xのときとは別の数列を返します。mruby 4.0は、xoshiroの代わりにPCGを使います。
- 影響の範囲：シードを与えた乱数生成器が返す数に依存するスクリプトです。
- 必要な対応：シードを与えた乱数生成器が返す数に、バージョンをまたいで依存しないでください。

### `Set#inspect`と`Set#to_s`の形式が変わり、`Set#flatten_merge`が無くなる(#561)

- 変更前：`#<Set: {1, 2}>`です。`Set#flatten_merge`はpublicメソッドです。例えば`Set.new([1]).flatten_merge(Set.new([2, Set.new([3])]))`は、1、2、3を要素とするSetです。
- 変更後：`Set[1, 2]`です。これらのメソッドでSetを文字列にするものは、すべて同じように変わります。文字列の式展開(`"#{set}"`)、`sprintf("%s", set)`、`Array#inspect`がこれに当たります。mruby 4.0.0は`Set#flatten_merge`を削除したので、呼ぶと`NoMethodError`が出ます。mrubyの利用者から見える変更の一覧は、この削除を挙げていません。
- 影響の範囲：Setの`inspect`や`to_s`をデータの形式に使うスクリプト、それを固定の文字列と比べるスクリプト、`Set#flatten_merge`を呼ぶスクリプトです。
- 必要な対応：`Hash#inspect`と同じく、文字列を自分で組み立ててください。`set.to_a.join(",")`は、どちらのバージョンでも同じ文字列を返します。`s.flatten_merge(t)`の代わりに`s.merge(Set.new(t).flatten)`を呼んでください。どちらのバージョンでも、この呼び出しは、2.xの`s.flatten_merge(t)`と同じSetを返します。`t`がSetでもArrayでも同じです。

### `Hash#default_proc=`がProcでないオブジェクトに`TypeError`を出す(#561)

- 変更前：受け付けます。
- 変更後：`TypeError`が出ます。
- 影響の範囲：`Hash#default_proc=`の引数に、Procでないオブジェクトを渡すスクリプトです。
- 必要な対応：代わりにProcか`nil`を渡してください。

### キーワード引数を受けるブロックに、キーワード引数を付けて`yield`すると動く(#561)

- 変更前：`ArgumentError: missing keyword`が出ます。
- 変更後：ブロックがキーワード引数を受け取ります。
- 影響の範囲：キーワード引数を受けるブロックに、キーワード引数を付けてyieldするスクリプトです。例えばこの`ArgumentError`をrescueしたスクリプトです。
- 必要な対応：何もしなくてかまいません。これはmrubyの不具合の修正です。

### ハンドラのコードで、ブロックや`for`の本体の中の`return`がコードを終える(#561)

- 変更前：ハンドラのコードのトップレベルで、`[0].each do ... end`や`3.times { ... }`のようなブロックの中や、`for`の本体の中に`return`を書くと、`LocalJumpError`が出ます。ハンドラは500を返します。`error.log`には`mrb_run failed: return 500 HTTP status code to client: error: unexpected return (LocalJumpError)`が出ます。`return`の前に出力を書いていたコンテンツハンドラも500を返します。その出力は送りません。2.7.0は、この出力を200の応答で送りました。例外はログに出すだけでした。2.7.1は、`Nginx.rputs`の後に出たすべての例外について、この挙動を変えました。詳しくは[2.7.1のリリースノートのエントリ3](v2.7.1.ja.md#3-nginxrputsの後で例外が発生するとレスポンスは500になります)にあります。`mruby_set_code`の変数には空の値が入ります。ブロックの外でコードのトップレベルに書いた`return`は、コードを終えます。
- 変更後：この`return`は、トップレベルの`return`と同じくコードを終えます。後のコードは動きません。応答は、それまでにコードが決めたものになります。つまり、`Nginx.return`で決めたステータスと、`Nginx.rputs`で書いた出力です。`mruby_set_code`では、ブロックの中の`return`の値が変数に入ります。`error.log`には、この`return`についての行は出ません。
- 変更の理由：
  - 不具合：[#502](https://github.com/matsumotory/ngx_mruby/issues/502)が報告した不具合です。ハンドラを途中で終える`return`をブロックや`for`の本体の中に書くと、`LocalJumpError`が出ました。ハンドラは、コードが決めた応答の代わりに500を返しました。
  - 前の挙動を残せなかった理由：このエラーはmruby 3.3.0から来ていました。ngx_mrubyは、ハンドラのコードをファイバーの最初のフレームで動かします。mruby 3.3.0は、こうした`return`が抜けるフレームとしてこのフレームを受け付けません。mruby 4.0.0と4.1.0-rc2は受け付けます。詳しくは[ハンドラのコードのフレームについての提案の1.3節](../proposals/archive/handler-code-frame.md#13-why-502-fails-on-master-and-not-on-next)にあります。エラーを残すには、同梱のmrubyを3.3.0の規則に戻す必要がありました。#502は、このエラーを不具合として報告しています。
  - ドキュメントが示していた挙動：2.xの[docs/class_and_method/README.md](https://github.com/matsumotory/ngx_mruby/blob/v2.7.0/docs/class_and_method/README.md#nginxreturnnginx_status_code)は、ngx_mrubyがハンドラのコードで`return`文を使えることと、`return`がハンドラから戻ることを書いています。ブロックの中を例外とする記述はありません。
- 影響の範囲：トップレベルのブロックや`for`の本体の中に`return`を持つハンドラのコードです。メソッドやlambdaの中の`return`は当たりません。500や`LocalJumpError`の行に頼っていたログのアラートとスクリプトも当たります。
- 必要な対応：何もしなくてかまいません。2.xでの回避の書き方は、どちらのバージョンでも動きます。この2つの回避の書き方は、コードのトップレベルに`return`を書くことと、コードをメソッドやlambdaの中に置くことです。
- このリリースで変わらない挙動：ハンドラのコードを動かすフレームは変わりません。`self`は`main`です。ローカル変数は、コードを1回実行する間だけ使えます。定数、グローバル変数、`main`のインスタンス変数、`def`で定義したメソッドは、ワーカーの中に残ります。詳しくは[提案の1.4節](../proposals/archive/handler-code-frame.md#14-what-handler-code-shares-today)にあります。

### 出力なしで終わるcontentハンドラが、500でなく、空のボディの200で応答する(#574)

- 変更前：2.7.1と2.7.2では、メインリクエストのcontentハンドラが出力なしで終わると、次の場合に500が返りました。ステータスを設定していない場合、`Nginx::HTTP_OK`を設定した場合、201と204以外の300未満のステータスを設定した場合です。出力なしとは、何も書かない場合、`Nginx.rputs`で`""`か`nil`だけを書く場合、レスポンスヘッダだけを設定する場合です。`Nginx::HTTP_OK`は、`Nginx.return`、`Nginx.send_header`、`Nginx.status_code=`のどれで設定しても同じです。300未満のステータスの例は`Nginx::HTTP_ACCEPTED`です。`Nginx::Async::HTTP.sub_request`が再開した後にこのように終わった場合も、同じでした。500のボディはnginxのエラーページか、500に設定した`error_page`で、ヘッダには`Connection: close`が付きました。詳しくは[2.7.1のリリースノートの項目13](v2.7.1.ja.md#13-contentハンドラが出力なしで終わるとレスポンスは500になります)にあります。error.logには`error`レベルの行が出ました。その行は、`status code is 200, but response body is empty. return NGX_HTTP_INTERNAL_SERVER_ERROR`、`status code is not set, and response body is empty. return NGX_HTTP_INTERNAL_SERVER_ERROR`、`status code is <N>, but response body is empty. return NGX_HTTP_INTERNAL_SERVER_ERROR`のどれかです。2.7.0までは、出力なしの`Nginx::HTTP_OK`に同じ500が返りました。ほかの場合には、レスポンスがまったく返りませんでした。nginxは、HTTP/1.0の接続を1バイトも送らずに閉じ、keep-aliveの接続を`keepalive_timeout`までレスポンスなしで開いたままにしました。
- 変更後：そのようなハンドラは、nginx自身の`return 200;`と同じに応答します。ステータスはハンドラが設定したもので、設定していなければ200です。ヘッダには`Content-Length: 0`が付き、ボディは空です。`Content-Type`は付きません。ngx_mrubyの出力のある応答にも付きません。nginxの`return 200;`は、`default_type`の`Content-Type`を付けます。HEADリクエストにも同じヘッダが返ります。locationのヘッダフィルタとボディフィルタは、この空のレスポンスにも動きます。対象は`mruby_output_header_filter`、`mruby_output_body_filter`と、それぞれの`_code`の形です。ngx_mrubyは、空の応答を送る前に、読まれていないリクエストボディを破棄します。出力のある応答を送る前にも、2.7.1から同じように破棄します。詳しくは[2.7.1のリリースノートの項目12](v2.7.1.ja.md#12-応答の前に読まれていないリクエストボディを破棄します)にあります。そのため、開いたままの接続の次のリクエストは、クライアントがボディの後に送ったリクエストになります。nginxは、keep-aliveの接続を次のリクエストのために開いておきます。例外は、mrubyの出力のボディフィルタがあるlocationへのHEADリクエストです。この場合、nginxはヘッダを送ってから接続を閉じます。出力のあるハンドラでも、2.7.1とこのリリースで同じです。error.logには、上の行は出ません。
- 変更の理由：
  - 不具合：[#200](https://github.com/matsumotory/ngx_mruby/issues/200)が報告した不具合です。`Nginx.return Nginx::HTTP_OK`を呼んでボディなしで終わるcontentハンドラには、500が返りました。nginx自身の`return 200;`は、空のボディの200で応答します。HTTPは、この応答を認めています。[RFC 9110の15.3.1節](https://www.rfc-editor.org/rfc/rfc9110#section-15.3.1)によると、200のレスポンスはメッセージのコンテントを含むと想定されますが、メッセージのフレーミングが長さ0を明示する場合は除きます。`Content-Length: 0`は、長さ0を明示します。2.7.1は、ステータスを設定していない場合と、nginxが自分では応答しない300未満のほかのステータスにも、同じ500を返すようにしました。それまで、これらのリクエストにはレスポンスがまったく返らなかったためです([#566](https://github.com/matsumotory/ngx_mruby/pull/566))。
  - 前の挙動を残せなかった理由：500のままでは、contentハンドラは空のボディの200で応答できません。ハンドラが選べる空の応答は204だけです。204は、クライアントとキャッシュにとって別のステータスです。v3の計画は、空の200をv3の挙動の変更として受け入れています。計画は[docs/proposals/v3-plan.md](../proposals/v3-plan.md)の7節の項目8です。2.x系列は互換性を優先するので、この500を残します。
  - ドキュメントが示していた挙動：2.7.1のドキュメントは、前の挙動を説明していました。出力なしで終わるcontentハンドラは500で応答し、空のボディには`Nginx::HTTP_NO_CONTENT`を使う、という説明です。この説明は[2.7.1のNginx.return](https://github.com/matsumotory/ngx_mruby/blob/v2.7.1/docs/class_and_method/README.md#nginxreturnnginx_status_code)にあります。2.7.1より前のドキュメントは`Nginx.return`について「Returns nginx status code to send back HTTP status to the client」と書いているだけでした。この記述は[2.7.0のNginx.return](https://github.com/matsumotory/ngx_mruby/blob/v2.7.0/docs/class_and_method/README.md#nginxreturnnginx_status_code)にあります。
- 影響の範囲：出力なしで終わることのある`mruby_content_handler`と`mruby_content_handler_code`のハンドラと、上の行を見るログの監視です。ハンドラの例は、条件が成り立つときだけ書くハンドラ、空か`nil`になりうる値を`Nginx.rputs`に渡すハンドラ、レスポンスヘッダだけを設定するハンドラ、`Nginx.return Nginx::HTTP_OK`を呼んでボディなしで終わるハンドラです。変わらない挙動：出力なしの200未満のステータスは、2.7.1と2.7.2のときと同じく500になり、`status code is <N>, but response body is empty`の行が出ます。201、204、300以上のステータスには、nginx自身が応答します。出力のあるハンドラと`Nginx.redirect`も変わりません。ほかのハンドラも変わりません。rewriteハンドラやaccessハンドラで、出力なしで`Nginx.return Nginx::HTTP_OK`を呼ぶと、これまでどおり500が返り、`status code is 200, but response body is empty`の行が出ます。サブリクエストも変わりません。対象は`Nginx::Async::HTTP.sub_request`、SSIのinclude、`auth_request`です。サブリクエストのcontentハンドラが、出力なしで`Nginx::HTTP_OK`を返すと、サブリクエストのステータスはこれまでどおり500になります。何も書かずステータスも設定しないハンドラは、これまでどおりレスポンスボディもステータスも無いままサブリクエストを終えます。
- 必要な対応：ほとんどの設定では、何もしなくてかまいません。空のボディで応答すべきハンドラは、`Nginx::HTTP_OK`を返せるようになりました。返すものが無いことを500で知らせていたスクリプトは、そのステータスを自分で設定してください。例は`Nginx.return Nginx::HTTP_INTERNAL_SERVER_ERROR`と`Nginx.return Nginx::HTTP_NOT_FOUND`で、nginxはこれまでどおり応答します。`response body is empty. return NGX_HTTP_INTERNAL_SERVER_ERROR`に一致させるログの監視に見える行は、次の場合だけになります。contentハンドラが200未満のステータスを返した場合と、ほかのハンドラやサブリクエストで`Nginx::HTTP_OK`を返した場合です。
- テスト：`test/conf/conf.d/54-content-empty-body.conf`と`test/t/cases/content_empty_body.rb`の、ポート18136のテストです。1つの接続で、ハンドラが読まないボディを持つ`POST`を2つ送るテストも含みます。`test/t/ngx_mruby.rb`の「Nginx.return 200 dont have body」と、`test/t/cases/request_api.rb`の「send_header 200 without a body answers 200 with an empty body」も、この挙動を試します。

### 空のボディで終わる出力のボディフィルタが、接続を閉じずにレスポンスを送る(#574)

- 変更前：出力のボディフィルタが空のボディで終わると、nginxは`alert`レベルで`zero size buf in writer`をログに出し、ステータス行を書く前に接続を閉じました。クライアントは1バイトも受け取りませんでした。対象のボディフィルタは`mruby_output_body_filter`と`mruby_output_body_filter_code`です。空のボディで終わるのは、フィルタが`Nginx::Filter#body=`か`Nginx::Filter#output`で`""`を設定した場合と、ボディの無いレスポンスでフィルタがボディを空のままにした場合です。2.7.2と2.7.1でも、それより前のリリースでも同じです。
- 変更後：レスポンスは、そのステータスと`Content-Length: 0`と空のボディで送られます。error.logには、このレスポンスについての`alert`の行は出ません。
- 変更の理由：
  - 不具合：ボディフィルタは、空のボディを、`memory`のフラグを立てた0バイトのバッファとして次へ渡していました。nginxのwriterは、このバッファを拒否します(`zero size buf in writer`)。そのため、レスポンスは送られませんでした。nginx自身の`return 200;`は、このフラグを立てない空の最後のバッファを渡します(`ngx_http_send_response`)。2.x系列にも、2.7.2までは同じ不具合があります。2.7.1の`test/t/cases/filter_connection.rb`は、これを2.xの挙動として記録しています。テストの名前は「an empty String closes the connection without a response」です。2.7.3は、2.x系列でも同じ方法でこの不具合を直します([2.7.3のリリースノートの項目8](v2.7.3.ja.md#8-output-body-filterで空の本文を送れるようになります664))。
  - 前の挙動を残せなかった理由：送られないレスポンスは、クライアントを応答の無いままにします。上の項目の空の200も、そのlocationのボディフィルタを通ります。この変更が無いと、ボディフィルタのあるlocationは、空の200の代わりに何も送りません。
  - ドキュメントが示していた挙動：[2.7.1のNginx::Filter#body=](https://github.com/matsumotory/ngx_mruby/blob/v2.7.1/docs/class_and_method/README.md#nginxfilterbodystring)は、フィルタが設定したボディそのままでレスポンスを送り、`Content-Length`をその長さにすると書いています。空の文字列を例外とする記述はありません。
- 影響の範囲：空のボディで終わることのある出力のボディフィルタを持つlocationです。上の項目の、出力なしで終わるcontentハンドラのlocationも当たります。`zero size buf in writer`の行を見るログの監視も当たります。これらのレスポンスでは、この行が出なくなるからです。
- 必要な対応：ありません。
- テスト：`test/t/cases/filter_connection.rb`のポート18112のテスト「an empty String sends the status with Content-Length: 0」と、ポート18136のボディフィルタのあるlocationのテストです。後者は`test/t/cases/content_empty_body.rb`にあります。

### `Nginx::Var`のアクセサが、ワーカーで最初に使われたときに`Nginx::Var`のメソッドになる(#610)

- 変更前：`Nginx::Var`への`v.NAME`と`v.NAME = value`は、毎回`Nginx::Var#method_missing`を通りました。`Nginx::Var`が自分で持つメソッドは、`method_missing`、`exist?`、`set`の3つでした。`v.respond_to?(:request_method)`は`false`を返し、`Nginx::Var.instance_methods(false)`はこの3つだけを挙げました。スクリプトが変数と同じ名前のメソッドを`Object`か`Kernel`に定義すると、`v.NAME`は変数を読まずにそのメソッドを呼びました。例は、ハンドラのコードのトップレベルの`def`です。
- 変更後：ワーカープロセスで、ある名前の最初の`v.NAME`か`v.NAME = value`は、`NAME`か`NAME=`を`Nginx::Var`のメソッドとして定義します。そのワーカーでその名前を後で使うと、このメソッドが呼ばれます。このメソッドは、`method_missing`と同じに変数を読み書きします。値、変数でない名前への`nil`、例外、`error.log`の行は変わりません。ワーカーは、スクリプトが使う宣言済みの変数ごとに、getterとsetterを定義します。宣言済みの変数とは、nginxとそのモジュールの変数と、`set`が宣言する変数です。接頭辞の変数には、スクリプトが使う最初の16の名前にgetterを定義します。接頭辞の変数の名前の例は、`arg_q`と`http_x_request_id`です。メソッドを定義するのは、名前が`a`から`z`、`0`から`9`、`_`だけでできているときです。setterの名前は、その後に`=`が付きます。`v.Request_Method`は、これまでどおり`method_missing`を通って`$request_method`を読みます。次の場合には、メソッドを定義しません。変数でない名前、接頭辞の変数のsetter、`Nginx::Var`のサブクラスのインスタンス、凍結した`Nginx::Var`、`Nginx::Var`かその祖先が同じ名前のメソッドを既に持つ名前です。最初に使った後は、`v.respond_to?(:NAME)`、`v.methods`、`Nginx::Var.instance_methods(false)`、`Nginx::Var.method_defined?(:NAME)`がそのメソッドを示します。何を示すかはワーカーがそれまでに処理したリクエストで決まるので、2つのワーカーが違う答えを返すことがあります。メソッドができた後は、スクリプトが同じ名前のメソッドを後から`Object`か`Kernel`に定義しても、`v.NAME`は引き続き変数を読みます。
- 変更の理由：
  - 背景：mruby 4.0.0では、どのクラスも定義していないメソッド名を探すと、その名前を`Nginx::Var`、`Object`、`Kernel`、`BasicObject`の全部のメソッドと比べます。比べる項目は110を超えます。mrubyは、見つからなかった名前をキャッシュしません。そのため、`v.NAME`は毎回、`method_missing`が動く前にこの探索をしていました。#561のcallgrindの比較で、mruby 3.3.0との差のうち、`var`のシナリオの74%と、`auth`のシナリオの59%が、この探索の分でした。説明は[構想の1.1節](../proposals/archive/nginx-var-method-lookup.md#11-what-the-comparison-of-561-counts)にあります。名前のメソッドがあれば、mrubyのメソッドのキャッシュがそれを見つけます。
  - 前の挙動を残せなかった理由：mrubyのメソッドのキャッシュは、探索で見つけたメソッドにしか答えません。`v.NAME`が探索を飛ばすには、メソッドを定義するしかなく、定義したメソッドはイントロスペクションに見えます。構想のほかの案は、いま書かれているスクリプトを遅い経路に残すか、mrubyのリリースを待つ案です。説明は[構想の2節](../proposals/archive/nginx-var-method-lookup.md#2-candidates)にあります。オーナーは、2026-10-15に、イントロスペクションの変化を3.0.0の挙動の変更として受け入れ、2026-10-19にその受け入れを確かめました。記録は[構想の状態](../proposals/archive/nginx-var-method-lookup.md)にあります。
  - ドキュメントが示していた挙動：[2.7.1のNginx::Varのクラス](https://github.com/matsumotory/ngx_mruby/blob/v2.7.1/docs/class_and_method/README.md#nginxvar-class)は、`Nginx::Var#VARNAME`か`Nginx::Var#VARNAME=`を評価すると`Nginx::Var#method_missing`が呼ばれると書いています。`respond_to?`と`Nginx::Var`のメソッドについては、何も書いていません。
- 影響の範囲：`Nginx::Var`かそのインスタンスに`respond_to?`、`methods`、`instance_methods`、`method_defined?`を呼ぶスクリプトです。例は、名前が変数かどうかをこれで判断するスクリプトです。変数と同じ名前のメソッドを`Object`か`Kernel`に定義し、その変数を`v.NAME`でも読むスクリプトも当たります。`Nginx::Var#method_missing`を包むスクリプトも当たります。例は、`super`を呼ぶ`method_missing`を持つモジュールを`Nginx::Var`にprependするスクリプトです。包んだ処理は、メソッドを定義する名前については最初のアクセスのときだけ動きます。
- 必要な対応：変数があるかどうかは、`v.exist?(name)`で判断してください。スクリプトのメソッドには、nginxの変数の名前でない名前を付けてください。
- テスト：`test/conf/conf.d/68-var-accessor.conf`と`test/t/cases/var_method_lookup.rb`のポート18159のテストです。

### `Nginx::Connection`、`Nginx::Server`、`Nginx::Request`が、`Nginx::Var`を呼ばずに変数を読む(#610)

- 変更前：次のメソッドは、自分の変数のアクセサを`Nginx::Var`に呼んでいました。`Nginx::Connection#remote_ip`、`#remote_port`、`#local_ip`、`#local_port`、`Nginx::Server#document_root`、`#realpath_root`、`#path`、`Nginx::Request#hostname`、`#authority`、`#filename`、`#user`、`#get_body`です。変数は、`remote_addr`、`remote_port`、`server_addr`、`server_port`、`document_root`、`realpath_root`、`host`、`http_host`、`request_filename`、`remote_user`、`request_body`です。その`Nginx::Var`は、オブジェクトが作ってインスタンス変数`@iv_var`に持っていました。スクリプトがそのようなメソッドか独自の`method_missing`を`Nginx::Var`に定義するか、`@iv_var`に別のオブジェクトを入れると、これらのメソッドが返す値が変わりました。
- 変更後：これらのメソッドは、nginxから変数をCで読みます。スクリプトが`Nginx::Var`にどんなメソッドを定義しても、nginxがその変数に持つ値を返します。`Nginx::Var`を作らず、`@iv_var`も設定しません。`Nginx::Request#var`は、これまでどおりオブジェクトの`Nginx::Var`を作って`@iv_var`に持ちます。リクエストの外では、これまでと同じ`RuntimeError`を出します。
- 変更の理由：
  - 背景：これらの変数の名前は決まっています。`AGENTS.md`の「Design principles」は、初期化のときに一度だけ用意できる決まったものを、リクエストごとに探したり確保したりしないように求めています。Rubyの呼び出しは、呼ぶたびに`Nginx::Var`でメソッドを探しました。この探索は、上の項目の探索と同じです。また、オブジェクトごとに`Nginx::Var`を作り、そのクラスを探しました。いまは、名前とそのハッシュのキーを一度だけ用意します。説明は[構想の案(d)](../proposals/archive/nginx-var-method-lookup.md#d-ngx_mrubys-own-methods-read-the-variable-in-c)にあります。
  - 前の挙動を残せなかった理由：スクリプトが値を変えられたのは、`@iv_var`のオブジェクトへのRubyの呼び出しがあったからです。この呼び出しをせずに変数を読むと、その費用とその効果の両方が無くなります。
  - ドキュメントが示していた挙動：[2.7.1のNginx::Connectionのクラス](https://github.com/matsumotory/ngx_mruby/blob/v2.7.1/docs/class_and_method/README.md#nginxconnection-class)は、`remote_ip`、`remote_port`、`local_ip`、`local_port`がnginxの変数`$remote_addr`、`$remote_port`、`$server_addr`、`$server_port`と同じだと書いています。[Nginx::Server#realpath_root](https://github.com/matsumotory/ngx_mruby/blob/v2.7.1/docs/class_and_method/README.md#nginxserverrealpath_root)も、`$realpath_root`について同じことを書いています。いまは、どの場合にもその値を返します。
- 影響の範囲：`Nginx::Var`へのメソッドの定義、独自の`method_missing`、`@iv_var`の別のオブジェクトで、これらのメソッドが返す値を変えるスクリプトです。`Nginx::Request#var`を先に呼ばずに、これらのオブジェクトの`@iv_var`を読むスクリプトも影響を受けます。
- 必要な対応：別の値を返すには、`Nginx::Connection`、`Nginx::Server`、`Nginx::Request`そのものにメソッドを定義するか、自分のメソッドを呼んでください。変数は、`@iv_var`でなく`Nginx::Var`で読んでください。`Nginx::Var`は、`Nginx::Request#var`、`Nginx.var`、`Nginx::Var.new`のどれかで得られます。
- テスト：`test/t/cases/var_method_lookup.rb`の、ポート18159のテストです。

### `Dir`をmrubyのコアgemが定義するようになり、閉じた`Dir`が`RuntimeError`でなく`IOError`を出す(#559)

- 変更前：`Dir`はiij/mruby-dirが定義します。閉じた`Dir`を読んだり、その項目を繰り返し処理したり、もう一度閉じたりすると、`RuntimeError`が出ます。メッセージは`closed directory`です。ブロックの中で`Dir`を閉じたときの`Dir.open`も、`RuntimeError`を出します。ブロックなしで呼んだ`Dir#each`と`Dir.foreach`は、`NoMethodError`を出します。
- 変更後：`Dir`は、mruby 4のコアgemであるmruby-dirが定義します。このgemはiij/mruby-dirをもとにしていて、iij/mruby-dirのメソッドをすべて持ちます。閉じた`Dir`を読んだり、その項目を繰り返し処理したり、もう一度閉じたりすると、`IOError`が出ます。メッセージは`closed directory`です。ブロック付きの`Dir.open`は、ブロックの中で`Dir`を閉じたときも、ブロックの値を返します。ブロックなしの`Dir#each`と`Dir.foreach`は、`Enumerator`を返します。ブロック付きの`Dir.foreach`は、開いた`Dir`を閉じます。これは「不具合の修正」に挙げます。また、`Dir`には、iij/mruby-dirに無いメソッドがあります。それは「新機能」に挙げます。
- 変更の理由：
  - 背景：v3の計画は、サードパーティのgemのiij/mruby-env、iij/mruby-process、iij/mruby-dirを、mrubyのコアgemに置き換えます。根拠は`docs/proposals/v3-plan.md`の4節のPillar Aです。mruby 4.0.0がコアgemを持っていたのは`Dir`だけです。4.1にはmruby-envとmruby-processもあります。iijの2つのgemをそれらに置き換えるのは、後の変更です。
  - 前の挙動を残せなかった理由：`RuntimeError`は、iij/mruby-dirが出します。iij/mruby-dirは、`ENABLE_IO`なしでコンパイルすると、閉じたディレクトリに`RuntimeError`を出します。既定のビルドは`ENABLE_IO`を定義しません。`RuntimeError`を残すには、iij/mruby-dirを残すしかありませんでした。iij/mruby-dirには、2018-09-14からコミットがありません。また、iij/mruby-dirの`Dir.foreach`は、開いた`Dir`をGCが解放するまで閉じません。
  - ドキュメントが示していた挙動：2.xの[docs/class_and_method/README.md](https://github.com/matsumotory/ngx_mruby/blob/v2.7.0/docs/class_and_method/README.md#built-in-mrbgems)は、既定のビルドで使えるクラスに`Dir`のクラスを挙げ、iij/mruby-dirへリンクしています。iij/mruby-dirのREADMEはメソッドを挙げていますが、閉じた`Dir`に対して出る例外については何も書いていません。
- 影響の範囲：閉じることのある`Dir`のメソッドや、ブロックの中で`Dir`を閉じる`Dir.open`の周りで、`RuntimeError`をrescueするスクリプトです。`rescue RuntimeError`が例外を捕まえなくなると、ハンドラは500を返します。このときのログの行は`mrb_run failed: ... error: #<IOError: closed directory>`です。
- 必要な対応：`IOError`をrescueしてください。2.xと3.0.0の両方のバージョンで動かすスクリプトは、`IOError`と`RuntimeError`の両方か、`StandardError`をrescueしてください。

### C拡張：`MRB_TT_DATA`と宣言していないクラスのオブジェクトでは、Cのデータをラップできない(#561)

- 変更前：mruby 3.xは、インスタンスの型を設定しないクラスを検査しませんでした。`Data_Wrap_Struct`や`mrb_data_object_alloc`で、Cの構造体を自分のクラスのオブジェクトでラップするgemは、オブジェクトを得られました。
- 変更後：mruby 4.0は、クラスを`MRB_SET_INSTANCE_TT(klass, MRB_TT_DATA)`で宣言していないと、割り当てのときに`TypeError: allocation failure of <class>`を出します。
- 影響の範囲：その宣言をしていないクラスのオブジェクトでCのデータをラップするmrbgemとC拡張です。matsumotory/mruby-unameの、matsumotory/mruby-uname#1より前のコミットがその1つです。このとき、`Uname`のどのメソッドも`TypeError: allocation failure of Uname`を出します。それを呼ぶハンドラは、500を返します。ngx_mrubyのテストスイートでもこの変化が出ました。変化が出たのは`test/t/cases/gem_uname.rb`です。
- 必要な対応：クラスを`MRB_SET_INSTANCE_TT(klass, MRB_TT_DATA)`で宣言してください。既定のビルドは、matsumotory/mruby-unameを、この宣言をするコミットに固定します。詳しくは「ビルドとテストの変更」を参照してください。mruby-unameを取り込む自前の`build_config.rb`には、固定したそのコミットか、それより後のコミットが必要です。

### C拡張：mrubyが、Cのメソッドに渡す引数の数を引数仕様で検査する(#561)

- 変更前：mruby 3.3は、Cのメソッドに渡す引数の数を、定義したときの引数仕様で検査しました。仕様は`MRB_ARGS_REQ(2)`などです。ただし、検査したのは仕様が`MRB_ARGS_NONE()`のときだけです。他の仕様では、`mrb_get_args`だけが、自分が読むものに対して引数を検査しました。
- 変更後：mruby 4.0は、すべてのCのメソッドで、呼ぶ前に引数の数を検査します。仕様が求めるより少ない引数で呼ぶと、`ArgumentError`が出ます。仕様に可変長引数(`MRB_ARGS_REST()`、`MRB_ARGS_ANY()`)が無ければ、仕様が許すより多い引数で呼んでも`ArgumentError`が出ます。`mrb_get_args`が受け付けるかどうかは関係ありません。仕様がキーワードを受けないとき、空でないキーワードのハッシュは1つの引数と数えます。`MRB_ARGS_REQ(1)`で定義して`"o|o"`を読むメソッドは、2つの引数で呼ぶと`ArgumentError: wrong number of arguments (given 2, expected 1)`を出します。`MRB_ARGS_REQ(2)`で定義して`"S"`を読むメソッドは、1つの引数で呼ぶと`(given 1, expected 2)`を出します。mruby 3.3では、どちらの呼び出しも動きました。
- 影響の範囲：仕様と`mrb_get_args`が読むものが、どちらかの向きで食い違う、mrbgemとC拡張のCのメソッドです。ngx_mruby自身のCのメソッドは影響を受けません。`src/`にある110の定義のそれぞれで、仕様は、その`mrb_get_args`が受け付ける引数の数をすべて受け付けます。
- 必要な対応：`mrb_get_args`が読むものに合う仕様で、メソッドを定義してください。`"o|o"`なら`MRB_ARGS_ARG(1, 1)`です。

### C拡張：ヘッダと関数の名前が変わり、失敗したときの`mrb_open()`の戻り値が変わる(#561)

- 変更前：`mruby/ext/io.h`、`mrb_alloca()`、`mrb_open_allocf(f, ud)`、`mrb_open_core(f, ud)`があります。後の2つは、`mrb_allocf`の型のアロケータを受け取ります。既定のアロケータは`mrb_default_allocf()`です。プログラムは、この関数を定義し直せました。gemの初期化が失敗すると`mrb_open()`は`NULL`を返します。
- 変更後：IOのヘッダは`mruby/io.h`になりました。`mruby/ext/io.h`はありません。`mrb_alloca()`は`mrb_temp_alloc()`になりました。`mruby.h`は`mrb_alloca()`をそのマクロとして残し、コメントに「for compatibility」と書いています。`mrb_open_allocf()`、`mrb_allocf`、`mrb_default_allocf()`はありません。`mrb_open_core()`は引数を取りません。mrubyは、`mrb_basic_alloc_func(void *ptr, size_t size)`でメモリを割り当てます。プログラムはこの関数を定義して、mrubyのアロケータを置き換えられます。説明は、mrubyの[`doc/guides/memory.md`](https://github.com/mruby/mruby/blob/4.1.0-rc2/doc/guides/memory.md)にあります。gemの初期化が失敗すると、`mrb_open()`は`NULL`でなく、`mrb->exc`を設定したmrb_stateを返します。
- 影響の範囲：mrbgemと、mrubyを組み込むプログラムのうち、Cのソースが次のどれかに当たるものです。`mruby/ext/io.h`をインクルードするもの、`mrb_open_allocf()`を呼ぶもの、`mrb_open_core()`を引数付きで呼ぶものは、ビルドが止まります。自分の`mrb_default_allocf()`を定義するものでは、mrubyがそれを呼ばなくなります。`mrb_open()`の結果を`NULL`かどうかだけで判定するものも当たります。`mrb_alloca()`の呼び出しは、今もコンパイルできます。
- 必要な対応：`mruby/io.h`をインクルードし、`mrb_temp_alloc()`を呼んでください。`mrb_open_allocf(f, ud)`の代わりに`mrb_open()`を呼び、`mrb_open_core()`は引数なしで呼んでください。プログラムがアロケータを置き換えるところでは、`mrb_default_allocf()`の代わりに`mrb_basic_alloc_func()`を定義してください。`mrb_open()`の結果は、`mruby.h`の`MRB_OPEN_FAILURE()`で判定してください。このマクロは、`NULL`のときと、`exc`を設定したmrb_stateのときに真になります。

### C拡張：`mruby.h`をインクルードするソースに、生成されたヘッダが必要になる(#561)

- 変更前：`mruby.h`は`mruby/presym.h`をインクルードしませんでした。そのため、`MRB_SYM()`を使わないソースは、`mruby/include`だけでコンパイルできました。`MRB_NO_PRESYM`でpresymを無効にすることもできました。ngx_mruby 2.xは、自分のソースをこの形でコンパイルしていました。2.xの`config.in`は、インクルードパスに`mruby/src`と`mruby/include`だけを置きます。
- 変更後：`mruby.h`は`mruby/presym.h`をインクルードし、`mruby/presym.h`は生成された`mruby/presym/id.h`をインクルードします(mruby/mruby#6733)。`MRB_NO_PRESYM`も無くなりました。そのため、`mruby.h`をインクルードするすべてのソースに`build/host/include`が必要です。`mruby/include`だけでコンパイルしたソースは`fatal error: mruby/presym/id.h: No such file or directory`で止まります。
- 影響の範囲：mrubyのビルドとは別にコンパイルする、`mruby.h`をインクルードするCのソースです。`./configure --with-mruby-incdir`で、そのディレクトリを含まないディレクトリの一覧を与えたビルドでの、ngx_mrubyのソースもこれに入ります。
- 必要な対応：mrubyのビルドが作る`include`ディレクトリ、`mruby/build/host/include`をインクルードパスに加えてください。ngx_mrubyのビルドは、自分のソースにはこれを加えます。`--with-mruby-incdir`の既定の一覧は`<mruby_root>/src <mruby_root>/include <mruby_root>/build/host/include`です(#559)。`--with-mruby-incdir`で自分で一覧を与えるときも、このディレクトリが必要です。ngx_mrubyのソースが`mruby.h`と`mruby/presym.h`をインクルードするためです(#572)。詳しくは[3-B. Makefileを使う](../ja/install/README.md#3-b-makefileを使う)を参照してください。

### 既定のビルドからauto-sslのmrbgemと、それに伴うクラスが無くなる(#556)

- 変更前：2.xの既定の`build_config.rb`は、同梱のauto-sslのmrbgemと、それが依存するgemをビルドします。auto-sslは`mrbgems/auto-ssl`にあり、`Nginx::SSL::ACME`のクラスを定義します。依存するgemは、pyama86/mruby-acme-client、pyama86/mruby-polarssl、matsumotory/mruby-httprequest、matsumotory/mruby-simplehttp、mattn/mruby-http、mattn/mruby-base64、takahashim/mruby-forwardable、iij/mruby-tempfileです。スクリプトは、これらのgemが定義するものを使えます。`Nginx::SSL::ACME::Client`と`Nginx::SSL::ACME::Dehydrated`、クラスとモジュールの`Acme`、`CustomHttpRequest`、`OpenSSL`、`PolarSSL`、`HttpRequest`、`SimpleHttp`、`HTTP`、`Base64`、`Forwardable`、`FORWARDABLE`、`Tempfile`、`TempfilePath`、そして`Dir.tmpdir`と`Dir.mktmpdir`です。
- 変更後：既定のビルドには、これらがどれもありません。これらの定数は無く、`Dir.tmpdir`と`Dir.mktmpdir`は`NoMethodError`を出します。これらのどれかを使うハンドラは、500を返します。そのときログに出る行は、`mrb_run failed: ... error: #<NameError: uninitialized constant Base64>`のような形です。`Dir`のクラス自体は残ります。このリリースには、auto-sslのmrbgem自体がありません。詳しくは次の項目を参照してください。
- 変更の理由：
  - 背景：v3の計画の決定6は、v3の既定のビルドからauto-sslを外し、nginx-acmeと、ストアから証明書を引く例に置き換えます。根拠は`docs/proposals/v3-plan.md`の7節です。auto-sslのACMEのクライアントである`Nginx::SSL::ACME::Client`は、ACMEv1を使います。Let's Encryptは、ACMEv1をもう提供していません。こちらの根拠は計画の2.2節と3.4節です。
  - 前の挙動を残せなかった理由：このgemは、Let's Encryptから証明書を取得できません。また、既定のビルドに入る他のgemが必要としないサードパーティのgemを8つ、すべての既定のビルドに持ち込んでいました。その中には、GPLのpyama86/mruby-polarsslもあります。さらに、auto-sslを既定のビルドに残すと、mruby 4では既定のビルドも止まります。pyama86/mruby-polarsslが`mruby/ext/io.h`をインクルードするためです。次の項目を参照してください。
  - ドキュメントが示していた挙動：2.xの[docs/class_and_method/README.md](https://github.com/matsumotory/ngx_mruby/blob/v2.7.0/docs/class_and_method/README.md#auto-ssl-mrbgem)は、auto-sslを、開発の初期段階にある任意で使う同梱のmrbgemと呼んでいます。既定のビルドに入るかどうかは書いていません。同じ文書の[Nginx::Var Class](https://github.com/matsumotory/ngx_mruby/blob/v2.7.0/docs/class_and_method/README.md#nginxvar-class)にある`mruby_set_code`の例は、`Base64.encode`を呼びます。既定のビルドで`Base64.encode`が使えたのは、auto-sslがあったからです。
- 影響の範囲：nginxの中で、上の定数のどれか、`Dir.tmpdir`、`Dir.mktmpdir`を使うスクリプトです。
- 必要な対応：`Base64.encode(s)`の代わりに`[s].pack('m0')`を、`Base64.decode(s)`の代わりに`s.unpack1('m')`を使ってください。どちらもコアgemのmruby-packにあります。`Dir.tmpdir`の代わりに`ENV['TMPDIR'] || '/tmp'`を使い、`Dir.mktmpdir`の代わりに、自分で決めた名前で`Dir.mkdir(path, 0700)`を使ってください。例は[auto-sslのmrbgemと、それと一緒に入っていたクラス](../ja/install/README.md#auto-sslのmrbgemとそれと一緒に入っていたクラス)にあります。他の定数には、それを定義するgemを、自前の`build_config.rb`に`conf.gem`の行で加えてください。pyama86/mruby-polarsslに依存するgemは、mruby 4ではビルドできません。`Nginx::SSL::ACME`が必要なサーバーは、2.xのビルドを使い続けてください。次の項目を参照してください。

### auto-sslのmrbgemと`NGX_MRUBY_AUTO_SSL`が無くなる(#640)

- 変更前：ngx_mruby 2.xは、auto-sslのmrbgemを同梱し、既定のビルドに入れます。このgemは`mrbgems/auto-ssl`にあります。このgemは、ACMEのプロトコルのクライアントである`Nginx::SSL::ACME::Client`と、ACMEのクライアントのdehydratedを使うための`Nginx::SSL::ACME::Dehydrated`を定義します。`test/conf/auto-ssl/`には、両方の設定の例が入っています。
- 変更後：このリリースには、`mrbgems/auto-ssl`も`test/conf/auto-ssl/`もありません。`build_config.rb`は`NGX_MRUBY_AUTO_SSL`をもう読みません。そのため、このリリースのどのビルドにも`Nginx::SSL::ACME`はありません。環境に`NGX_MRUBY_AUTO_SSL=1`を与えたビルドは、与えないときと同じく既定のgemをビルドします。`Nginx::SSL::ACME`を使うスクリプトは`NameError`を出し、そのハンドラは500を返します。そのとき`error.log`には`mrb_run failed`を含む`error`の行が出ます。
- 変更の理由：
  - 背景：v3の計画の決定6は、auto-sslを、nginx-acmeと、ストアから証明書を引く例に置き換えます。根拠は`docs/proposals/v3-plan.md`の7節です。また、このgemは同梱のmrubyでは動きません。このgemは、TLSのためにpyama86/mruby-polarsslを必要とします。pyama86/mruby-polarsslは、ngx_mrubyが保守していないgemで、2017-03-03からコミットがありません。このgemは`mruby/ext/io.h`をインクルードします。mruby 4.0はこのヘッダを`mruby/io.h`に改名したので、auto-sslを入れたmrubyのビルドは`fatal error: mruby/ext/io.h: No such file or directory`で止まります(#561)。auto-sslのACMEのクライアントであるpyama86/mruby-acme-clientはACMEv1を使います。Let's Encryptは、2021-06にACMEv1を止めました。こちらの根拠は計画の2.2節と3.4節です。
  - 前の挙動を残せなかった理由：pyama86/mruby-polarsslが変わらない限り、このgemはmruby 4でビルドできません。ビルドできたとしても、Let's Encryptから証明書を取得できません。`next`に残すと、v3のどのビルドも使えないgemと、ビルドが止まるだけの任意の変数を残すことになります。ngx_mruby 2.xには、このgemが残ります。
  - ドキュメントが示していた挙動：2.xの[docs/class_and_method/README.md](https://github.com/matsumotory/ngx_mruby/blob/v2.7.0/docs/class_and_method/README.md#auto-ssl-mrbgem)は、auto-sslを、開発の初期段階にある任意で使う同梱のmrbgemと呼び、APIについては`mrbgems/auto-ssl/mrblib`のスクリプトを参照するよう書いています。このgemをいつまで残すかは書いていません。
- 影響の範囲：`Nginx::SSL::ACME::Client`か`Nginx::SSL::ACME::Dehydrated`を使うスクリプト、`test/conf/auto-ssl/`の例をもとにした設定、`NGX_MRUBY_AUTO_SSL=1`を与えるビルドです。
- 必要な対応：ACMEのサーバーから証明書を取得するには、nginx自身のモジュールである[ngx_http_acme_module](https://nginx.org/en/docs/http/ngx_http_acme_module.html)、つまりnginx-acmeを使ってください。`Nginx::SSL::ACME`が必要なサーバーは、2.xのビルドを使い続けてください。このgemの説明は[2.xのドキュメント](https://github.com/matsumotory/ngx_mruby/blob/v2.7.2/docs/class_and_method/README.md#auto-ssl-mrbgem)にあります。ビルドの環境から`NGX_MRUBY_AUTO_SSL`を除いてください。この変数は何の効果もありません。

### `Nginx::Upstream#server=`と`Nginx::Stream::Connection#upstream_server=`が、serverにできない文字列に`ArgumentError`を出す(#680)

- 変更前：空の文字列と256バイト以上の文字列と、2.7.3からはNULバイトを含む文字列に、`Nginx::Upstream#server=`は`ArgumentError`を出し、`Nginx::Stream::Connection#upstream_server=`は`RuntimeError`を出しました。NULバイトの扱いは、[2.7.3のリリースノート](v2.7.3.ja.md)の項目9にあります。`192.0.2.1:notaport`のように、nginxがアドレスとして読めない文字列には、どちらも`RuntimeError`を出しました。`upstream_server=`は、ホスト名にも`RuntimeError`を出しました。
- 変更後：どちらも、これらのすべてに`ArgumentError`を出します。メッセージは変わりません（`invalid upstream server (empty or too long)`、`invalid upstream server (contains a NUL byte)`、`invalid port in upstream 192.0.2.1:notaport`）。ホスト名だけはメッセージが`upstream server NAME is not an IP address or a unix: path`になります。serverは、前と同じく元のまま残ります。`RuntimeError`は、nginxが文字列を読む間に失敗したときと、`zone`のあるupstreamのときに残ります。
- 変更の理由：
  - 背景：同じ引数に、2つのsetterが別のクラスの例外を出していました。スクリプトは、直せる引数の誤りとnginxの失敗を区別できませんでした。この変更は、オーナーがv3について決めました（[提案の問い3](../proposals/archive/upstream-server-setters.md#4-questions-for-the-owner-with-recommendations)）。
  - 前の挙動を残せなかった理由：残すと、1つの種類の誤りに2つの規則が残ります。互換性を優先する2.xの系列は、この規則を保ちます。v3は、これを変えられるリリースです。
  - ドキュメントが示していた挙動：2.7.3向けの[#648](https://github.com/matsumotory/ngx_mruby/pull/648)が、前のクラスを`docs/class_and_method/README.md`に書きました。2.7.2のドキュメントは、例外について何も書いていません（[`Nginx::Upstream#server=`](https://github.com/matsumotory/ngx_mruby/blob/v2.7.2/docs/class_and_method/README.md#nginxupstreamserverstring)、[`Nginx::Stream::Connection#upstream_server=`](https://github.com/matsumotory/ngx_mruby/blob/v2.7.2/docs/class_and_method/README.md#nginxstreamconnectionupstream_server-1)）。
- 影響の範囲：`Nginx::Stream::Connection#upstream_server=`の周りで`RuntimeError`をrescueするスクリプトと、nginxが読めない文字列について`Nginx::Upstream#server=`の周りで`RuntimeError`をrescueするスクリプトです。この`rescue`は例外を捕まえなくなり、ハンドラは例外で終わります。リクエストのフェーズのハンドラは500を返し、`mruby_set`は変数を空にします。`Nginx::Upstream#server=`の周りで`ArgumentError`をrescueするスクリプトは、これらの場合も捕まえるようになります。
- 必要な対応：`ArgumentError`をrescueしてください。両方のバージョン向けのスクリプトは、`ArgumentError`と`RuntimeError`の両方か、`StandardError`をrescueしてください。
- このリリースで変わらない挙動：Stringでない引数への`TypeError`と、`zone`のあるupstreamへの`RuntimeError`は変わりません。後者は、引数でなくupstreamについての例外です。

### `Nginx::Upstream#server=`が、ホスト名を名前解決せずに`ArgumentError`を出す(#680)

- 変更前：`Nginx::Upstream#server=`は、呼ばれたときにホスト名をシステムのリゾルバで名前解決し、最初のアドレスを使いました。応答を待つ間、ワーカーは他のクライアントを処理しませんでした。解決できない名前には`RuntimeError`（`host not found in upstream NAME`）を出しました。
- 変更後：このメソッドは名前解決をしません。IPアドレスでも`unix:`のパスでもない文字列には`ArgumentError`（`upstream server NAME is not an IP address or a unix: path`）を出し、serverは元のまま残ります。ワーカーは待ちません。`Nginx::Stream::Connection#upstream_server=`は、前からホスト名を受け付けません。
- 変更の理由：
  - 背景：[AGENTS.md](../../AGENTS.md#design-principles)の設計の原則「No blocking」です。AGENTS.mdは、この変更まで、このsetterをブロックする箇所に挙げていました。この変更は、オーナーがv3について決めました（[提案の問い3](../proposals/archive/upstream-server-setters.md#4-questions-for-the-owner-with-recommendations)）。
  - 前の挙動を残せなかった理由：リゾルバが応答するまで、そのワーカーの他のリクエストはすべて待ちます。リゾルバが遅いと、その間ワーカーが止まります。待たずに名前解決するには、スクリプト向けのリゾルバが要りますが、ngx_mrubyにはありません。
  - ドキュメントが示していた挙動：2.7.3向けの[#648](https://github.com/matsumotory/ngx_mruby/pull/648)が、前の挙動を`docs/class_and_method/README.md`に書き、ワーカーが待つことと、IPアドレスを渡すことを書きました。[2.7.2のドキュメント](https://github.com/matsumotory/ngx_mruby/blob/v2.7.2/docs/class_and_method/README.md#nginxupstreamserverstring)は、ホスト名について何も書いていません。
- 影響の範囲：`Nginx::Upstream#server=`にホスト名を渡すスクリプトです。`localhost`も当たります。`127.1`、`2130706433`、`0x7f.0.0.1`のようにシステムのリゾルバだけが読めた形式のIPv4アドレスか、`255.255.255.255`を渡すスクリプトも当たります。これらの文字列では、ワーカーは待っていませんでした。スクリプトが例外をrescueしなければ、リクエストのフェーズのハンドラは500を返し、`mruby_set`は変数を空にします。
- 必要な対応：スクリプトが待たずに得られるIPアドレスを渡してください。例えば、スクリプトの設定から読みます。IPv4アドレスは、4つの10進数で書いてください。nginxの動作中に変わらない名前は、`upstream {}`ブロックの`server`の行に書き、setterを呼ばないでください。nginxは、設定を読むときにこの名前を解決します。nginxは、この名前のすべてのアドレスを使います。アドレスが2つ以上あると、`Nginx::Upstream.new`はそのupstreamに`RuntimeError`を出すので、その呼び出しも削除するか、`server`の行にIPアドレスを書いてください。解決できない名前があると、nginxは起動しません。
- このリリースで変わらない挙動：2.xの系列は、引き続きホスト名を名前解決します。`upstream {}`ブロックの`server`の行に書いたホスト名は、nginxが解決するので当たりません。

### `Nginx::Async.sleep`で待つaccessハンドラとpost_readハンドラが、待たないときと同じように終わる(#715)

- 変更前：`Nginx::Async.sleep`のタイマーが切れると、ngx_mrubyがコードを再開し、ハンドラを自分で終えていました。そのとき使っていたのは、ハンドラのフェーズの規則でなく、contentフェーズの規則です。`satisfy all`と`satisfy any`のどちらのaccessハンドラも、post_readハンドラも、sleepの後に結果なしで終わった場合と、`Nginx::OK`で終わった場合が問題でした。結果なしとは、`Nginx.return`、`Nginx.send_header`、`Nginx.status_code=`のどれも呼ばないことです。リクエストはcontentまで進みましたが、nginxはその後に接続を閉じ、同じ接続の次のリクエストに応答しませんでした。`satisfy any`では、sleepの後の401と403が、そのステータスでリクエストを終えていました。sleepが無ければ、nginxは次のaccessハンドラを試します。前のハンドラが`Nginx::DECLINED`を保存していたサーバーでは、この終わり方が隠れていました。この点は「結果を設定しないハンドラが、前のハンドラの結果を引き継がない」の項にあります。
- 変更後：sleepが終わると、nginxがハンドラをもう一度呼び、ハンドラはsleepの後のコードを続けます。ハンドラのフェーズのチェッカーは、待たなかったハンドラと同じようにその結果を扱います。結果が無ければ、accessハンドラは`satisfy all`で次のaccessハンドラへ進み、`satisfy any`でリクエストを許可します。post_readハンドラは次のフェーズへ進みます。キープアライブの接続では、次のリクエストにも応答します。`satisfy any`では、sleepの後の401と403でも、nginxは`allow`や`auth_request`のような次のaccessハンドラを試します。ハンドラが待っている間、nginxはそのコードをもう一度実行しません。
- 変更の理由：
  - 不具合：[docs/proposals/core-stabilization.md](../proposals/core-stabilization.md)の2.3節のgap 2です。同じコードが、`Nginx::Async.sleep`の後では待たないときと違う形で終わっていました。タイマーが、nginxのフェーズのチェッカーの代わりに、contentフェーズのチェッカーの写しを使っていたためです。8節のstep 3の設計は、2026-11-01に本人が決めました。
  - 前の挙動を残せなかった理由：待ったかどうかで終わり方が変わると、スクリプトはその終わり方に頼れません。また、応答の後に接続を閉じると、キープアライブのクライアントの次のリクエストが失われます。
  - ドキュメントが示していた挙動：2.7.3の[Nginx::Async#sleep](https://github.com/matsumotory/ngx_mruby/blob/v2.7.3/docs/class_and_method/README.md#nginxasyncsleepmsec)は、accessハンドラでsleepを使えることと、sleepの後のコードが動くことを説明していました。ハンドラがどう終わるかは書いていませんでした。
- 影響の範囲：`Nginx::Async.sleep`を呼ぶ`mruby_access_handler`、`mruby_access_handler_code`、`mruby_post_read_handler`、`mruby_post_read_handler_code`のハンドラです。特に`satisfy any`では、sleepの後に結果なしで終わるaccessハンドラが、リクエストを許可するようになります。
- 必要な対応：sleepの後にリクエストを拒むaccessハンドラは、sleepの後に`Nginx::HTTP_FORBIDDEN`か`Nginx::HTTP_UNAUTHORIZED`を返してください。`satisfy any`では、sleepが無いときと同じように、nginxがほかのaccessハンドラを試します。
- テスト：`test/conf/conf.d/82-async-resume-result.conf`と`test/t/cases/async_resume_result.rb`の、ポート18176と18178のテストです。`satisfy all`、`satisfy any`、`allow all`の前の`satisfy any`、`auth_request`の前のaccessハンドラと、post_readハンドラについて、すべての終わり方を、待たない場合とsleepの後で確かめます。

### 出力を書くaccessハンドラとpost_readハンドラが、レスポンスの後にリクエストを終える(#715)

- 変更前：accessハンドラとpost_readハンドラが`Nginx.rputs`か`Nginx.echo`で出力を書き、ほかのステータスを設定しないと、レスポンスを送った後もnginxはリクエストのフェーズを続けていました。contentフェーズがもう一度応答しようとし、nginxは`header already sent`をログに書き、同じ接続の次のリクエストに応答する前に接続を閉じていました。`Nginx::Async.sleep`の後では、同じハンドラがレスポンスの後にリクエストを終えていました。
- 変更後：待つかどうかに関わらず、レスポンスの後にリクエストが終わります。rewriteハンドラとcontentハンドラが出力を書いた後と同じです。キープアライブの接続では、nginxは次のリクエストにも応答します。
- 変更の理由：
  - 不具合：ハンドラは、レスポンスの後にnginxへ`NGX_OK`を返していました。accessフェーズとpost_readフェーズは、この値を「先へ進む」と読みます。[docs/proposals/core-stabilization.md](../proposals/core-stabilization.md)の8節のstep 3は、出力のある実行の終わり方を、待つ場合と待たない場合でそろえます。
  - 前の挙動を残せなかった理由：ハンドラのレスポンスは送り終えているので、後のフェーズはそこで失敗して接続を閉じるしかありませんでした。
  - ドキュメントが示していた挙動：2.7.3の[Nginx.rputs](https://github.com/matsumotory/ngx_mruby/blob/v2.7.3/docs/class_and_method/README.md#nginxrputsstring)は、どのハンドラでも「Puts response text」と説明し、その後のフェーズについては書いていませんでした。
- 影響の範囲：出力を書く`mruby_access_handler*`と`mruby_post_read_handler*`のハンドラと、それが出していた`header already sent`の行を見るログの監視です。
- 必要な対応：何もしなくてかまいません。リクエストに応答するために出力を書いていたハンドラは、1回だけ応答するようになります。
- テスト：`test/t/cases/async_resume_result.rb`と`test/t/cases/async_result_isolation.rb`の、ポート18176、18178、18179の「that ends with output」のテストです。

### 結果を設定しないハンドラが、前のハンドラの結果を引き継がない(#715)

- 変更前：`Nginx.return`、`Nginx.send_header`、`Nginx.status_code=`は、値をレスポンスのステータスに保存していました。`Nginx::DECLINED`のような0未満の戻り値も同じです。同じリクエストの後のハンドラが結果を設定しないと、そのハンドラはこの値を返していました。`mruby_server_rewrite_handler`がすべてのリクエストで`Nginx::DECLINED`を返すサーバーでは、出力もステータスも無く終わるcontentハンドラが、次のcontentハンドラかstaticモジュールへ進みました。staticモジュールは、合うファイルが無ければ404で応答します。`satisfy any`では、結果の無いaccessハンドラがDECLINEDを返したとみなされ、`deny`がリクエストを403で拒んでいました。`Nginx::Async.sleep`のタイマーかサブリクエストの終わりで再開したハンドラの後では、ngx_mruby自身が、`Nginx::OK`以外のすべての結果について500を保存していました。`Nginx::DECLINED`も同じです。そのため、後の出力もステータスも無いcontentハンドラは、500で応答していました。
- 変更後：ハンドラの結果は、そのハンドラ自身のものです。結果を設定しないハンドラには、前のハンドラが何を設定していても、結果がありません。出力の無いメインリクエストのcontentハンドラは、空のボディの200で応答します。詳しくは「出力なしで終わるcontentハンドラが、500でなく、空のボディの200で応答する」の項にあります。accessハンドラとpost_readハンドラは、`Nginx::OK`と同じように先へ進みます。結果の無いrewriteハンドラとserver rewriteハンドラは、次のフェーズのハンドラへ進みます。この点は「結果なしで終わるrewriteハンドラとserver rewriteハンドラが、次のフェーズのハンドラへ進む」の項にあります。
- 変更の理由：
  - 不具合：[docs/proposals/core-stabilization.md](../proposals/core-stabilization.md)の2.1節のgap 3です。ハンドラの動きが、そのハンドラに含まれないハンドラで決まり、同じスクリプトが2つのサーバーで違う動きをしていました。ハンドラの結果をそのハンドラ自身のものにすることは、2026-11-01に本人が9節のQ6で決めました。
  - 前の挙動を残せなかった理由：スクリプトは、同じリクエストの前のハンドラが何を返したかを見られません。そのため、結果なしで終わったときにどう終わるかを知ることができません。
  - ドキュメントが示していた挙動：2.7.3の[Nginx.return](https://github.com/matsumotory/ngx_mruby/blob/v2.7.3/docs/class_and_method/README.md#nginxreturnnginx_status_code)は、クライアントへステータスを返すか、nginxのリクエストの処理を制御すると説明していました。値が後のハンドラへ引き継がれることは書いていませんでした。
- 影響の範囲：すべてのリクエストで`Nginx::DECLINED`などの値を返す`mruby_server_rewrite_handler*`、`mruby_rewrite_handler*`、`mruby_post_read_handler*`、`mruby_access_handler*`と、次のどちらかのハンドラを組み合わせた設定です。1つは、出力もステータスも無く終わることのあるcontentハンドラです。もう1つは、`satisfy any`で結果なしで終わることのあるaccessハンドラです。
- 必要な対応：次のcontentハンドラへ進むべきcontentハンドラは、自分で`Nginx::DECLINED`を返してください。`satisfy any`でほかのaccessハンドラに判断を任せるaccessハンドラも、自分で`Nginx::DECLINED`を返してください。
- テスト：`test/conf/conf.d/82-async-result-isolation.conf`と`test/t/cases/async_result_isolation.rb`の、ポート18179のテストです。server rewriteハンドラが`Nginx::DECLINED`を返し、後のaccessハンドラとcontentハンドラが自分の結果で終わることを確かめます。

### `Nginx::Async.sleep`で待つ`mruby_set`のハンドラが変数を設定し、リクエストが先へ進む(#715)

- 変更前：sleepが終わると、ngx_mrubyは変数を設定した後、応答せずにリクエストを終えていました。ただし、同じリクエストの前のハンドラが`Nginx::DECLINED`を保存していた場合は終えませんでした。すべてのリクエストでこの値を返すserver rewriteハンドラが、その例です。sleepの後にコードが`Nginx.return`で設定したステータスは、そのステータスでリクエストを終えていました。sleepが無ければ、そのステータスはリクエストを終えません。
- 変更後：コードが戻ると変数が設定され、リクエストはsleepが無いときと同じように、そのフェーズの次のハンドラへ進みます。そのため、contentハンドラや`proxy_pass`のような後のフェーズが値を読めます。コードが設定したステータスは、リクエストを終えません。sleepの後の例外は、これまでと同じく500で応答します。
- 変更の理由：
  - 不具合：[docs/proposals/core-stabilization.md](../proposals/core-stabilization.md)の2.3節のgap 2です。sleepの後の`mruby_set`のハンドラの終わり方が、ほかのハンドラが保存したステータスで決まっていました。直し方は構想の4.4節と8節のstep 3にあり、2026-11-01に本人が決めました。
  - 前の挙動を残せなかった理由：応答せずに終わったリクエストでは、クライアントはタイムアウトまで待ちます。また、ハンドラの終わり方を、そのハンドラに含まれないハンドラで決めることはできません。
  - ドキュメントが示していた挙動：2.7.3の[Nginx::Async#sleep](https://github.com/matsumotory/ngx_mruby/blob/v2.7.3/docs/class_and_method/README.md#nginxasyncsleepmsec)は、setハンドラでsleepを使えると説明し、リクエストがどう先へ進むかは書いていませんでした。
- 影響の範囲：コードが`Nginx::Async.sleep`を呼ぶ`mruby_set`と`mruby_set_code`です。
- 必要な対応：ほとんどの設定では、何もしなくてかまいません。sleepの後にステータスでリクエストを終えていたコードは、そのステータスを後のハンドラから返してください。例えば、変数を読むrewriteハンドラから返します。同じrewriteのスクリプトの中で`mruby_set`より後にあるディレクティブは、今も値の無いまま、sleepが終わる前に動きます。
- テスト：`test/conf/conf.d/83-async-set-var.conf`と`test/t/cases/async_set_var.rb`の、ポート18182のテストです。

### 結果なしで終わるrewriteハンドラとserver rewriteハンドラが、次のフェーズのハンドラへ進む(#720)

- 変更前：`mruby_rewrite_handler*`か`mruby_server_rewrite_handler*`のハンドラが、出力も`Nginx.return`、`Nginx.send_header`、`Nginx.status_code=`も無く終わると、rewriteフェーズに`NGX_OK`を返していました。`Nginx.return Nginx::OK`で終わった場合も同じです。nginxは応答せずにリクエストを終えていました。`Connection: close`では1バイトも送らずに接続を閉じ、キープアライブの接続は`keepalive_timeout`まで開いたままでした。`error.log`には`error`レベルの行がありませんでした。前のハンドラがすべてのリクエストで`Nginx::DECLINED`を返すサーバーでは、このハンドラがその値を引き継いで先へ進みました。`Nginx::DECLINED`のような0未満の戻り値を`Nginx.return`に渡すと、その値はレスポンスのステータスにも保存されていました。

- 変更の理由：
  - 不具合：[docs/proposals/core-stabilization.md](../proposals/core-stabilization.md)の2.3節のgap 1です。応答の無い終わり方は、どのスクリプトの役にも立ちません。出力も`Nginx.return`も無く終わるrewriteハンドラを、`next`では`NGX_DECLINED`と同じに先へ進めることは、2026-10-04に本人が決めました。この決定(b)は[docs/HANDOFF.md](../HANDOFF.md)にあります。2026-11-01に本人が構想の9節のQ6で、server rewriteハンドラにも広げました。
  - 前の挙動を残せなかった理由：クライアントには応答がまったく届かず、`error.log`にも理由が残りませんでした。
  - ドキュメントが示していた挙動：2.7.3のドキュメントは、`Nginx.return`の無いrewriteハンドラがどうなるかを書いていませんでした。
- 影響の範囲：結果なしか`Nginx::OK`で終わることのある`mruby_rewrite_handler*`と`mruby_server_rewrite_handler*`のハンドラです。例えば、変数やヘッダだけを設定するハンドラです。これらのハンドラの後、リクエストはlocationのcontentへ進むようになります。2.xの挙動を確かめていた`test/t/cases/request_api.rb`のテスト「rewrite handler without output or DECLINED sends no response」は、contentハンドラの200を期待するようになりました。

- テスト：`test/t/cases/async_resume_result.rb`と`test/t/cases/async_result_isolation.rb`の、ポート18176、18177、18179のテストです。結果なしと`Nginx::OK`のrewriteハンドラとserver rewriteハンドラを、待たない場合、sleepの後、サブリクエストの後で確かめます。ポート18111の`test/t/cases/request_api.rb`のテストもあります。

### `Nginx::Async::HTTP.sub_request`がcontentハンドラで、`Nginx::Async.sleep`の後でも動く(#722)

### `Nginx::Async::HTTP.sub_request`で待つハンドラが、コードを1回だけ実行し、待たないときと同じように終わる(#722)

- 変更前：サブリクエストが終わると、ngx_mrubyはサブリクエストの終わりの中でコードを再開し、そこでハンドラを終えていました。そのとき使っていたのは、ハンドラのフェーズの規則でなく、contentフェーズの規則です。待っている間、ハンドラは`NGX_AGAIN`を返していました。accessハンドラとpost_readハンドラでは、サブリクエストの後にnginxがリクエストを先へ進めるとき、リクエストのフェーズをもう一度実行していました。そのため、ハンドラのコードが最初からもう一度動き、サブリクエストをもう一度送っていました。
- 変更後：ハンドラは待っている間`NGX_DONE`を返し、nginxはサブリクエストが終わるまで、そのリクエストのイベントを無視します。サブリクエストが終わると、nginxはリクエストを起こしてハンドラをもう一度呼び、ハンドラは呼び出しの後のコードを続けます。ハンドラのフェーズのチェッカーは、待たなかったハンドラと同じようにその結果を扱います。ハンドラのコードはリクエストにつき1回だけ動き、サブリクエストも1回だけ送られます。
- 変更の理由：
  - 不具合：[docs/proposals/core-stabilization.md](../proposals/core-stabilization.md)の2.3節のgap 5です。サブリクエストの終わりと親のハンドラの終わりが、nginxのフェーズのチェッカーの外で、1つの呼び出しとして動いていました。8節のstep 5は、再開を親のリクエスト自身のフェーズの実行の中へ移します。この設計は、2026-11-01に本人が決めました。
  - 前の挙動を残せなかった理由：コードがもう一度動くハンドラは、サブリクエストを含めて、コードがすることを繰り返します。また、その終わり方は別のフェーズの規則で決まっていました。
  - ドキュメントが示していた挙動：2.7.3の[Nginx::Async::HTTP#sub_request](https://github.com/matsumotory/ngx_mruby/blob/v2.7.3/docs/class_and_method/README.md#nginxasynchttpsub_requestlocation-string_or_hashnil)は、「Sends a sub request in non-blocking way」と説明し、accessハンドラで使えると書いていました。ハンドラがどう終わるかは書いていませんでした。
- 影響の範囲：`Nginx::Async::HTTP.sub_request`を呼ぶ`mruby_access_handler*`と`mruby_post_read_handler*`のハンドラです。このメソッドを呼ぶほかのハンドラも、結果をそれぞれのフェーズで扱われるようになります。
- 必要な対応：ほとんどのスクリプトでは、何もしなくてかまいません。サブリクエストの後にコードがもう一度動くことに頼っていたスクリプトは、その処理を呼び出しの後に書いてください。そこでは、サブリクエストのレスポンスを使えます。
- テスト：ポート18176から18179の`test/t/cases/async_resume_result.rb`と`test/t/cases/async_result_isolation.rb`のテストです。access、post_read、contentのハンドラについて、サブリクエストの後のすべての終わり方を確かめます。ポート18183と18184の`test/t/cases/async_subrequest_return.rb`のテストもあります。サブリクエストを待って結果なしで終わるか`Nginx::DECLINED`を返すaccessハンドラとpost_readハンドラが1回だけ動き、サブリクエストを1つだけ送り、リクエストが先へ進むことを確かめます。

### UDPのstreamのセッションがコードを1回だけ実行し、コードが待っている間に届いたデータグラムでは始め直さない(#727)

- 変更前：nginxは、UDPのセッション(`listen ... udp`)のクライアントからデータグラムが届くたびに、streamのハンドラを呼んでいました。セッションのコードが`Nginx::Stream::Async.sleep`で待っている間も、データグラムが届くたびに、同じセッションの別のファイバーでコードが最初から動きました。新しい実行のsleepが待っていたsleepを置き換えるので、sleepの後に先へ進むのは最後の実行だけでした。
- 変更後：セッションはコードを1回だけ実行します。コードが待っている間に届いたデータグラムでは、コードを始め直しません。nginxはデータグラムをそのハンドラの呼び出しの間だけ渡すので、コードはそのデータグラムを見ません。セッションは、待たないコードのセッションと同じように、sleepの後のコードの結果で先へ進むか終わります。
- 変更の理由：
  - 不具合：[docs/proposals/core-stabilization.md](../proposals/core-stabilization.md)の2.5節のgap 9です。セッションのコードが、1つのセッションのファイバーで同時に何回も動いていました。UDPのセッションがコードを1回だけ実行することは、2026-11-01に本人が9節のQ4で決めました。
  - 前の挙動を残せなかった理由：複数の実行がセッションとその結果を共有し、セッションがどう進むかを最後の実行だけが決めていました。
  - ドキュメントが示していた挙動：2.7.3の[Nginx::Stream::Async#sleep](https://github.com/matsumotory/ngx_mruby/blob/v2.7.3/docs/class_and_method/README.md#nginxstreamasyncsleep)は、sleepの後にセッションがコードの結果で先へ進むと説明し、sleepの間のデータグラムについては書いていませんでした。
- 影響の範囲：`listen ... udp`のサーバーの`mruby_stream`と`mruby_stream_code`のうち、コードが`Nginx::Stream::Async.sleep`を呼び、クライアントがsleepの間に2つ以上のデータグラムを送るものです。
- 必要な対応：ほとんどの設定では、何もしなくてかまいません。データグラムごとに1回動くことに頼っていたコードは、sleepしないか、1つのセッションで1つのデータグラムを扱ってください。
- テスト：ポート12392の`test/conf/conf.d/stream/47-async-sleep-udp-once.conf`と`test/t/cases/stream_async_sleep_udp_once.rb`のテストです。sleepの間の10個のデータグラムでも、コードが1回だけ始まることを確かめます。

### `worker_shutdown_timeout`が切れたときに待っているstreamのセッションが、そこで終わる(#727)

- 変更前：reloadかSIGQUITの後に終わりかけているワーカーで`worker_shutdown_timeout`が切れると、nginxは接続に閉じる印を付け、その読み込みのハンドラを呼んでいました。ところが、コードが`Nginx::Stream::Async.sleep`で待っているstreamのセッションは続いていました。コードは別のファイバーで最初からもう一度動き、ワーカーはコードが終わるまで動いていました。
- 変更後：そのようなセッションは、タイムアウトが切れたときに終わります。sleepの後のコードは動かず、`error.log`には`info`レベルの行`shutdown timeout`が出て、ワーカーは終わります。`proxy_pass`のセッションと同じです。
- 変更の理由：
  - 不具合：[docs/proposals/core-stabilization.md](../proposals/core-stabilization.md)の2.5節のgap 10です。ハンドラがnginxの求める接続の閉じを見ていなかったので、このようなセッションのある古いワーカーの寿命を`worker_shutdown_timeout`で区切れませんでした。この直しは8節のstep 6で、2026-11-01に本人が決めました。
  - 前の挙動を残せなかった理由：`worker_shutdown_timeout`は、reloadの後に古いワーカーが動く時間を区切る設定です。
  - ドキュメントが示していた挙動：2.7.3のドキュメントは、`worker_shutdown_timeout`とsleepするstreamのコードについて何も書いていませんでした。
- 影響の範囲：`worker_shutdown_timeout`のある設定で、コードが`Nginx::Stream::Async.sleep`を呼ぶstreamのサーバーです。
- 必要な対応：何もしなくてかまいません。終わらせる必要のあるコードは、sleepを`worker_shutdown_timeout`より短くしてください。`worker_shutdown_timeout`が無ければ、古いワーカーはこれまでどおり進行中のsleepを終えます。
- テスト：`test/t/cases/workers.rb`の`shutdown`の場面のテストです。設定は`test/conf/workers/shutdown.conf`で、ポートは18185と12393です。

### `Nginx::Stream::Connection.proxy_protocol_addr`と`proxy_protocol_ip`は、PROXYの送信元のアドレスが無い接続で`nil`を返します

- 変更前：nginx 1.17.6以降では、`Nginx::Stream::Connection.proxy_protocol_addr`と`Nginx::Stream::Connection.proxy_protocol_ip`は、クラスメソッドでもインスタンスメソッドでも、PROXYプロトコルのヘッダーから得た送信元のアドレスが無い接続で値を返しませんでした。そのような接続は、`proxy_protocol`の無いlistenの接続と、バージョン1のヘッダー`PROXY UNKNOWN`か、コマンドが`LOCAL`のバージョン2のヘッダーを受けた接続です。
- 変更後：これらのメソッドは、そのような接続で`nil`を返します。アドレスを持つヘッダーの後では、これまでどおり送信元のアドレスを返します。2.7.4も同じ変更をします。
- 変更の理由：
  - 不具合：「変更前」に書いたとおり、これらのメソッドは、そのような接続で値を返しませんでした。
  - 前の挙動を残せなかった理由：そのような接続には、返すアドレスがありません。`nil`を返すと、アドレスのある接続と区別できます。HTTPのコードでは、`Nginx::Var#proxy_protocol_addr`が同じ場合に`nil`を返します。
  - ドキュメントが示していた挙動：これらのメソッドには、ドキュメントがありませんでした。いまは[docs/class_and_method/README.md](../class_and_method/README.md#nginxstreamconnectionproxy_protocol_addrproxy_protocol_ip)が説明しています。
- 影響の範囲：PROXYの送信元のアドレスが無い接続で、これらのメソッドを呼ぶ`mruby_stream`と`mruby_stream_code`のコードです。
- 必要な対応：結果をStringと比べるコードでは、対応は要りません。結果にStringのメソッドを呼ぶコードでは、`to_s`などで`nil`を扱ってください。
- テスト：`test/t/cases/_second_instance.rb`のモード`stream_master`のポート12385と12386のテストです。このモードは、マスタープロセスと1つのワーカープロセスを持つ2つ目のnginxを起動します。

### `proxy_protocol`を付けたlistenで、コードがsleepしているstreamのセッションはクライアントから何も読まず、`worker_shutdown_timeout`で終わります

- 変更前：`proxy_protocol`を付けたlistenのセッションのコードが`Nginx::Stream::Async.sleep`で待っている間、接続の読み込みのイベントは、コードが動く前と同じに扱われていました。sleepの間にクライアントが送ったバイトでセッションが終わることがあり、アクセスログのステータスは400でした。sleepの間に`worker_shutdown_timeout`が過ぎても、セッションはそのときに終わりませんでした。
- 変更後：コードがsleepしている間、nginxはこのlistenでも、ほかのlistenと同じく、クライアントから何も読みません。その間にクライアントが送ったバイトは、コードの後のフェーズのために残ります。`proxy_pass`は、そのバイトをupstreamへ送ります。sleepの間にクライアントが接続を閉じると、ほかのlistenと同じく、コードの後のフェーズがそれを検出します。sleepの間に`worker_shutdown_timeout`が過ぎると、項目「`worker_shutdown_timeout`が切れたときに待っているstreamのセッションが、そこで終わる」のとおり、セッションは終わります。2.7.4も、TCPのセッションについて同じ変更をします。
- 変更の理由：
  - 不具合：「変更前」に書いたとおり、sleepの間の読み込みのイベントが、コードが動く前と同じに扱われていました。
  - 前の挙動を残せなかった理由：ヘッダーの後のバイトは、後のフェーズが運ぶプロトコルのものです。`worker_shutdown_timeout`で終わらないセッションは、ディレクティブが決めた時間を過ぎても古いワーカープロセスを残します。
  - ドキュメントが示していた挙動：[docs/class_and_method/README.md](../class_and_method/README.md#nginxstreamasync-class)は、sleepの間の読み込みについて何も書いていませんでした。nginxの[`worker_shutdown_timeout`](https://nginx.org/en/docs/ngx_core_module.html#worker_shutdown_timeout)のドキュメントは、タイムアウトが過ぎるとnginxが開いている接続を閉じようとすると書いています。
- 影響の範囲：`proxy_protocol`を付けたlistenで、`mruby_stream`か`mruby_stream_code`のコードが`Nginx::Stream::Async.sleep`を呼ぶstreamのサーバーです。sleepの間にバイトを送るか接続を閉じるクライアントと、コードがsleepしている間に`worker_shutdown_timeout`を付けて終わるワーカーが影響を受けます。ワーカーが終わるのは、リロード、アップグレード、停止のときです。
- 必要な対応：ありません。コードがsleepしないセッションと同じく、コードの後のフェーズがクライアントのバイトを受け取ります。
- テスト：ポート12384の`test/conf/conf.d/stream/48-proxy-protocol-wait.conf`と`test/t/cases/stream_proxy_protocol_wait.rb`のテストは、sleepの間にバイトを送った後の応答を確かめます。`test/t/cases/_second_instance.rb`のモード`stream_master`のポート12387と12388のテストは、`proxy_protocol`を付けたセッションと付けないセッションが、`worker_shutdown_timeout`が過ぎたときに終わることを確かめます。

### ローカルのURIへの`Nginx.redirect`が、ハンドラが終わったときに効く(#728)

- 変更前：ローカルのURIへの`Nginx.redirect`は、呼び出しの中で内部リダイレクトをしていました。nginxはそこでリダイレクト先のlocationのフェーズを実行し、そのmrubyのハンドラは呼び出したハンドラのファイバーの中で動きました。呼び出したハンドラは呼び出しの後も続き、自分の結果を返したので、2つのハンドラが1つのリクエストに応答することがありました。呼び出しの後に呼び出したハンドラが設定した出力やステータスが先に応答し、リダイレクト先の出力がその後に続く場合がありました。リダイレクト先のcontentハンドラは、`Nginx::Async.sleep`の時点で出力なしにリクエストを終えていました。contentハンドラでsleepの後に`Nginx.redirect`を呼ぶと、クライアントはリダイレクト先の200を受け取り、アクセスログには500が残りました。呼び出しの後の、呼び出したハンドラの例外は、リダイレクト先の応答を残していました。
- 変更後：post_read、server rewrite、rewrite、access、contentのハンドラでは、呼び出しはURIを記録し、コードは最後まで続きます。その後にnginxがリダイレクト先のフェーズを実行します。リダイレクト先のハンドラは呼び出し元のファイバーの外で動き、ほかのハンドラと同じように待てます。リクエストに応答するハンドラは1つだけです。呼び出したハンドラの出力とステータスは送られません。呼び出しの後にコードが出力を書くかステータスを設定すると、`error.log`には`warn`レベルの、`set after Nginx.redirect are not sent`で終わる行が出ます。呼び出したハンドラが設定したレスポンスのヘッダと、リクエストへの変更は残ります。例えば`Nginx::Request#args=`で変えた引数です。呼び出しの後に設定したものも同じで、リダイレクト先の応答はそのヘッダを持ち、リダイレクト先はその引数を受け取ります。呼び出したハンドラの例外は500で応答し、リダイレクトは効きません。URLへの`Nginx.redirect`と、`mruby_set*`のハンドラ、logハンドラ、フィルタからのローカルのリダイレクトは変わりません。
- 変更の理由：
  - 不具合：[docs/proposals/core-stabilization.md](../proposals/core-stabilization.md)の2.4節のgap 6で、上の3つの場合です。`Nginx.redirect`をハンドラが終わったときに効かせることは、2026-11-01に本人が9節のQ2で決めました。
  - 前の挙動を残せなかった理由：1つのリクエストに2つのハンドラが応答すると、レスポンスが2つ送られるか、1つも送られません。また、待つリダイレクト先は別のハンドラのファイバーの中で動いていました。
  - ドキュメントが示していた挙動：2.7.3の[Nginx.redirect](https://github.com/matsumotory/ngx_mruby/blob/v2.7.3/docs/class_and_method/README.md#nginxredirecturl_or_internal_location-http_statusnginxhttp_moved_temporarily)は、内部リダイレクトが呼び出しから戻る前にリダイレクト先のハンドラを実行し、呼び出したコードは呼び出しの後も続くと説明していました。
- 影響の範囲：ローカルのURIへの`Nginx.redirect`を呼んだ後に、出力を書くか、ステータスやレスポンスのヘッダを設定するか、リクエストの引数を変えるか、例外を出すハンドラです。呼び出しから戻ったときにリダイレクト先が動き終わっていることに頼るハンドラと、リダイレクトしたリクエストのアクセスログの500を見る監視も含みます。
- 必要な対応：`Nginx.redirect`の後に、クライアントへ送るつもりのものを書かないでください。呼び出しの後のコードを動かさないときは、呼び出しの後でハンドラから`return`してください。呼び出しの後にリダイレクト先が設定した変数やヘッダを読んでいたコードは、リダイレクト先へ移してください。
- テスト：ポート18186の`test/conf/conf.d/85-redirect-async.conf`と`test/t/cases/redirect_async.rb`のテストと、`test/t/cases/async_sleep_in_content.rb`と`test/t/cases/async_exception_state.rb`の`Nginx.redirect`のテストです。

### `mruby_set`のハンドラでは`Nginx::Async::HTTP.sub_request`が`RuntimeError`を出す(#NNN)

- 変更前：`mruby_set`と`mruby_set_code`のハンドラでは、`Nginx::Async::HTTP.sub_request`はサブリクエストを始めましたが、nginxはその終わりを待ちませんでした。`mruby_set`の後のディレクティブと後のフェーズは、コードが変数を設定する前に動きました。呼び出しの後のコードは、サブリクエストが終わったときに動きました。そのコードが例外を出すと、クライアントには応答が届きませんでした。
- 変更後：この呼び出しは、`Nginx::Async::HTTP.sub_request is not available in an mruby_set handler`というメッセージの`RuntimeError`を出します。ハンドラは、ほかの例外の後と同じように終わります。待つ前なら、`error.log`に例外が出て、変数は空になり、リクエストは続きます。`Nginx::Async.sleep`の後なら、リクエストは500になります。`mruby_set`のハンドラの`Nginx::Async.sleep`は、これまでどおり動きます。
- 変更の理由：
  - 不具合：[docs/proposals/core-stabilization.md](../proposals/core-stabilization.md)の2.3節のgap 7で、nginxは`mruby_set`のハンドラのサブリクエストを待ちません。この呼び出しで例外を出すことは、2026-11-01に本人が9節のQ5で決めました。
  - 前の挙動を残せなかった理由：rewriteモジュールは、`mruby_set`のハンドラを自分のスクリプトの中で動かし、ハンドラが戻ると先へ進みます。そのため、サブリクエストを待つハンドラの値は、それを読むフェーズの後に届きます。例外を出すと、スクリプトはすぐに気づけます。2.7.1からのlogハンドラと同じです。
  - ドキュメントが示していた挙動：2.7.3の[Nginx::Async::HTTP#sub_request](https://github.com/matsumotory/ngx_mruby/blob/v2.7.3/docs/class_and_method/README.md#nginxasynchttpsub_requestlocation-string_or_hashnil)は、このメソッドを`set`のハンドラで使えると説明していました。2.7.3の[Nginx.rputs](https://github.com/matsumotory/ngx_mruby/blob/v2.7.3/docs/class_and_method/README.md#nginxrputsstring)は、nginxは変数を待たずに進み、呼び出しの後の例外ではクライアントに応答が届かないと説明していました。
- 影響の範囲：コードが`Nginx::Async::HTTP.sub_request`を呼ぶ`mruby_set`と`mruby_set_code`です。
- 必要な対応：`Nginx::Async::HTTP.sub_request`は、サブリクエストを待てるrewriteかaccessのハンドラで呼び、そこで`Nginx::Var#set`で変数を設定してください。
- テスト：ポート18182の`test/conf/conf.d/83-async-set-var.conf`と`test/t/cases/async_set_var.rb`の、`sub_request`を呼ぶテストです。

## 新機能

- `Nginx::Async::HTTP.sub_request`は、サブリクエストのレスポンスを返します。これは`Nginx::Async::HTTP.last_response`と同じステータス、ヘッダ、ボディの`Nginx::Async::HTTP::Response`です。2.xでは`nil`を返します(#722)。
- スクリプトで、mruby 3.4、4.0、4.1で加わった機能を使えます。`case`と`in`によるパターンマッチ、`Array#rfind`、メソッドの引数の末尾に付けるカンマ、メソッドの引数の`&nil`、ブロックの最初の引数を指す`it`です。パターンマッチは、4.1から文字列をパターンにできます。`[1, 2].map { it * 2 }`は`[2, 4]`です(#561, #678)。
- スクリプトで、mruby 3.3.0に無いメソッドを呼べます。例えば`Kernel#public_send`、`String#b`、`Hash#slice!`、`Array#fetch_values`、`Integer#bit_length`、`Integer.sqrt`、`Module#private_instance_methods`です。mruby 4.1は`String#scrub`を加えます。mrubyの利用者から見える変更の一覧である[`doc/mruby3.4.md`](https://github.com/mruby/mruby/blob/4.1.0-rc2/doc/mruby3.4.md)、[`doc/mruby4.0.md`](https://github.com/mruby/mruby/blob/4.1.0-rc2/doc/mruby4.0.md)、[`NEWS.md`](https://github.com/mruby/mruby/blob/4.1.0-rc2/NEWS.md)は、さらに多くを挙げています(#561, #678)。
- `Dir.children`と`Dir#each_child`は、CRubyと同じく`.`と`..`を除いてディレクトリの項目を挙げます。`Dir.empty?`は、ディレクトリに項目が無いかどうかを返します(#559, #561)。ngx_mruby 2.xは、`Dir`をiij/mruby-dirから取っていました。iij/mruby-dirには、この3つのメソッドがどれもありません。`Dir`は、今はmrubyのコアgemのmruby-dirが定義します。[Class and Method](../class_and_method/README.md)を参照してください。同梱のmrubyでは、この2つのメソッドは`.`と`..`を除きます。これはmruby 3.4からの変更で、mruby/mruby#6265です。mruby 3.3.0では、この2つは`Dir.entries`と`Dir#each`の別名で、`.`と`..`を含んでいました。ngx_mrubyのリリースに、mruby 3.3.0とmruby-dirを組み合わせたものはありません。ngx_mrubyのテストスイートでもこの変化が出ました。変化が出たのは`test/t/cases/gem_dir.rb`です。そうしたビルド向けに書いたスクリプトで、これらの呼び出しの後に`.`と`..`を飛ばしていたものは、そのコードを削除できます。`Dir.entries`を使い続けることもできます。`Dir`は`Enumerable`もインクルードします。iij/mruby-dirはインクルードしないので、`Dir.open(path) { |d| d.select { |name| name.end_with?(".txt") } }`は、このリリースから動きます。ブロック付きの`Dir.open`は、ブロックが終わると`Dir`を閉じます。

## 不具合の修正

- ブロック付きの`Dir.foreach`は、開いた`Dir`を閉じます。2.xのiij/mruby-dirでは、その`Dir`が持つworkerのファイルディスクリプタは、GCが`Dir`を解放するまで開いたままでした(#559)。
- nginxが設定を読む間に`mrb_open()`が失敗すると、httpのモジュールは`ngx_mruby: mrb_open() failed`を、streamのモジュールは`ngx_mruby-stream-module: mrb_open() failed`を、`emerg`のレベルで出します。mrubyかgemの初期化が例外を出したときは、その後に`: <class> raised while initializing mruby`が続きます。nginxはこれまでどおり止まります。ngx_mruby 2.xは、この場合に自分の行を出しませんでした(#559)。
- `Nginx::Async.sleep`を何回も呼ぶハンドラは、リクエストのプールに、呼び出しごとのタイマーとcleanupでなく、1つのタイマーと1つのcleanupを持ちます。待たないHTTPのハンドラは、ファイバーをGCのルートのholderに入れず、cleanupも足しません。sleepしないstreamのハンドラも、cleanupを足しません。fiberは最初の待ちでholderに入ります。ハンドラのコンパイルしたコードは、実行のたびでなく、コンパイルか読み込みのときに1回だけ用意します。`Nginx::Async.sleep`、`Nginx::Stream::Async.sleep`、`Nginx::Async::HTTP.sub_request`は、タイマーを設定するかsubrequestを出す前に、cleanupを足し、メモリの確保をすべて確かめます。確保に失敗したときは、何も設定せずに`RuntimeError`を出します(#714)。
- `mruby_set`のハンドラの値の`to_s`が例外を出すと、待つ前でも待った後でも500で応答し、`error.log`に`to_s`の例外が出ます。値の`to_s`がString以外のオブジェクトを返すと、変数には、`Kernel#to_s`がその値に返すStringが入ります。例えば`#<Object:0x...>`です。`Nginx::Var#set`も、2つの引数を同じように変換します(#NNN)

- CIは、変更に要るジョブだけを流します。新しいスクリプト`test/ci/changes.sh`が、変更したファイルを`code`、`tests`、`docs`、`site`、`examples`、`workflows`の分類に分けます。名前を変えたファイルは、変える前と後の両方のパスで分けます。どの分類にも当たらないファイルは、`code`として数えます。ワークフローは、このスクリプトの結果で判定します。readyのプルリクエストでコードを変えると、`test.yml`の`build`のマトリクスの4つのセルと、`soak`、`perf`を流します。4つのセルは、下の#702の項目にあります。`test/`、`test.sh`、`test.yml`だけを変えると、同じ4つのセルを流します。`soak`と`perf`の比較は、それぞれのファイルを変えたときだけ流します。ほかの変更では、これらのジョブを流しません。判定するのは、`test.yml`のジョブ`changes`です。draftのプルリクエストでは、CIを流しません。`test.yml`は、ジョブの名前を必須の`ci-ok`でなく`ci-ok (draft)`にします。ほかのワークフローは、ジョブを飛ばします。プルリクエストをready for reviewにすると、実行が始まります。`site.yml`は、プルリクエストでは、`site/`か`site.yml`を変えたときと、`docs/`を変えてブラウザのチェックの範囲がページを選んだときだけ、ブラウザのレーンを流します。`master`と`next`へのpushでは、ビルドとテストのジョブを流さず、サイトのデプロイとCodeQLのスキャンだけを流します。`nginx-tests`、`examples`、`zizmor`は、プルリクエストでだけ流します。タグのpushと「Run workflow」では、マトリクスの全部と`soak`を流します。`perf`は、プルリクエストでだけ流します。新しい入力`base`を付けた「Run workflow」は、そのブランチに向けたプルリクエストと同じ判定をし、結果を`ci-ok (dry run)`として出します。ほかの「Run workflow」は、結果を`ci-ok (manual)`として出します。必須の`ci-ok`を出すのは、プルリクエストとpushの実行だけです。`ci-ok`は、飛ばしたジョブを、`changes`が飛ばすと判定したときだけ合格と数えます。全部のセルをvalgrindの下で動かす実行は、夜間だけです。`valgrind-nightly.yml`はプルリクエストでは動かなくなりました。その実行はジョブの名前を`ci-ok (valgrind)`にし、`valgrind-nightly.yml`は実行の結果を読み直しながら待ちます。APIの呼び出しが1回失敗しても、ジョブは失敗しません。新しいワークフロー`codeql.yml`は、CとC++のコードをビルドせずに、RubyのコードとワークフローとあわせてCodeQLで調べます。対象は、`src/`、`mrbgems/`、`.github/workflows/`を変えるreadyのプルリクエストと`master`と`next`へのpushで、毎週の実行もあります。GitHubの既定の設定(default setup)の代わりです。説明は、[docs/test/README.md](../test/README.md)の「Which jobs a run starts」と「CodeQL」にあります(#676、#685、#686)。
- CI：取り消された実行は、`ci-ok`と`site-ok`に失敗ではなく結果なしを残します。CodeQLは、vendorした`mruby/`と`dependence/`のツリーを解析しません(`.github/codeql/codeql-config.yml`)。そのツリーのalertは、vendorした上流のコードとしてdismissしました。AGENTS.mdと[docs/test/README.md](../test/README.md)は、CIがクリーンな環境での最後の確認であり、作者がPRをreadyにする前に、変更が触る検査を手元で流すと書いています(#692)。
- 性能の比較は、新しいファイル`test/perf/accepted.txt`に書いた、受け入れた差を当てます。1行には、条件、シナリオ、GCを除いたリクエストあたりのIrの変化の許容幅(パーセント)を書きます。条件の`mruby-version`は、baseとheadに同梱したmrubyの`MAJOR.MINOR`です。両方のビルドが行の条件に合うとき、そのシナリオの`WARN`か`FAIL`の行は、変化が許容幅の中なら`ok (accepted: ...)`と表示され、比較を失敗にしません。許容幅を超える変化は、`WARN`か`FAIL`のままです。最初の行は、mruby 4.0から4.1で`auth`が+8%まで増えることを受け入れます。これは#678で受け入れた差で、#678より前の`next`のコミットをbaseにした比較が、この差を`FAIL`と報告しないようにします。mruby 3.3(2.7.2)と4.1の比較に当てる行はありません。報告は、両方のビルドのmrubyの版と、当てた差を示します。`PERF_ACCEPTED_FILE`で別のファイルを指定できます。説明は、[docs/test/README.md](../test/README.md)の「Known differences」にあります(#696)。
- CI：コードかテストを変えるreadyのプルリクエストは、`test.yml`の`build`のマトリクスのうち、4つのセルを流し、全部のセルは流しません。全部のセルは、nginxのバージョン、リンクの形、`--with-openssl-src`の有無の16の組み合わせと、sanitizerのセルです。4つのセルは、`--with-openssl-src`を付けたnginx 1.31.8の静的モジュール、nginx 1.30.6の動的モジュール、sanitizerのセル、valgrindの下のセルです。sanitizerのセルとvalgrindの下のセルは、nginx 1.31.8の静的モジュールをビルドします。sanitizerのセルは、AddressSanitizerとUndefinedBehaviorSanitizerを付けてビルドします。全部のセルと`soak`を流すのは、valgrindの下の夜間の実行、タグのpush、新しいラベル`full-matrix`を付けたプルリクエスト、入力`base`を付けないか入力`valgrind`を付けた「Run workflow」です。タグの前の点検のプルリクエストは、このラベルを付けます。`v*.x`のブランチへのpushは、`master`と`next`へのpushと同じく、ビルドを流しません。`test/ci/changes.sh`は、実行の種類をオプション(`--label`、`--draft`、`--push`、`--tag`、`--dispatch`、`--valgrind`)で受け取り、`build`を`standard`、`full`、`none`のどれかで出します。説明は、[docs/test/README.md](../test/README.md)の「Which jobs a run starts」にあります(#702)。
- テストスイートは、masterプロセスと複数のworkerプロセスでnginxを動かし、reloadします。`test/t/cases/workers.rb`が、preludeのヘルパー`workers_nginx`から、CRubyのヘルパー`test/t/cases/_workers.rb`を流します。このヘルパーは、`test/conf/workers/`の設定から`master_process on`でnginxを起こします。workerは、ポート18180で4つか、18181とstreamのポート12379で2つです。ヘルパーは、すべてのworkerに届くリクエストを送り、`Nginx::Async.sleep`と`Nginx::Stream::Async.sleep`が処理中のあいだにSIGHUPでnginxをreloadし、masterとすべてのworkerを止めます。masterには、pidファイルのpidでシグナルを送ります。ケースは次の3つを確かめます。各workerが自分のmrb_stateから答え、そのworkerのリクエストがそのstateを共有すること。reloadの後に新しい設定とスクリプトが答え、古いworkerが2つのsleepを終えてから終了すること。error logに`error`以上のレベルの行が無く、sanitizerの報告も無く、valgrindの下ではどのプロセスの報告にもエラーが無いこと。`test.sh`のテスト用のnginxは、1つのプロセスのままです([docs/test/README.md](../test/README.md)の「Several workers and reloads」)。`test/valgrind.supp`は、nginxがworkerプロセスの`ngx_event_process_init()`で確保して解放しないconnectionとeventの配列を抑制します。x86-64では、そのworkerがSIGTERMで終わるとき、valgrindがこの配列をlostと報告するためです(#706)。
- ソークのビルドの`Nginx::Debug.stats`は、httpモジュールの`timers`に加えて、`stream_timers`(待っている`Nginx::Stream::Async.sleep`のタイマーの数)と`stream_fibers`(GCのルートのholderにあるstreamのファイバーの数)を持ちます(#714)。

## アップグレード

サポートするnginxのバージョンは、nginxのmainlineとstableの系列です。[README.md](../../README.md)を参照してください。先に、使っているバージョンより新しい2.xのリリースのリリースノートを読み、その後でこのファイルを読んでください。同梱のmruby 4.1.0-rc2と一緒に、モジュールをビルドし直してください。自前の`build_config.rb`には、「自前の`build_config.rb`は、mruby 4.1のコアgemの変更に合わせる必要がある」の項目にある変更が必要です。[Migrating from ngx_mruby 2.x to 3.0.0](../migration/README.md)に、各項目が影響するスクリプトとビルドを見つける手順があります。アップグレードの前に、次を確かめてください。

- 同梱のmruby 4.1.0-rc2：一緒にモジュールをビルドし直し、これらの項目が扱わない変更をmrubyの一覧で確かめてください(#561, #678)。
- 自前の`build_config.rb`：mruby-print、hal-posix-io、hal-posix-dir、hal-posix-socketを除いてください。mruby-taskとmruby-encodingを使うかどうかを決めてください。`full-core.gembox`を使うときは、コアgemのmruby-env、mruby-process、mruby-regexpと、同じクラスを定義するサードパーティのgemのどちらを使うかを選んでください(#561, #678)。
- Ruby：Ruby 3.0以降でビルドしてください(#678)。
- `build_config.rb.lock`：新しいチェックアウトとソースのアーカイブでは、何もしなくてかまいません。gemを別のコミットでビルドするには項目を変えてください。ロックが変わったら、`mruby/build`を削除してください(#558)。
- `Hash#inspect`と`Hash#to_s`：データの形式として使わないでください。文字列を自分で組み立てるか、`JSON.generate`を使ってください(#561)。
- `Exception#inspect`：`mrb_run failed`の行を古い形式で読むログのパーサーとアラートを直してください(#561)。
- `"#@ivar"`、`"#@@cvar"`、`"#$global"`：文字どおりの意味で書いたそうした文字列は、`#`をエスケープするか、シングルクォートにしてください(#678)。
- 構文エラー：メッセージの文面でなく、`SyntaxError`と、ファイルと行に一致させてください(#678)。
- 自分自身を持つ`Array`、`Hash`、`Struct`：比較の`SystemStackError`を前提にするスクリプトでなければ、何もしなくてかまいません(#678)。
- nginxが設定を読む間のメッセージ：見るには、`nginx -t -e stderr`を実行するか、`nginx -t`の後で起動時のログを読むか、`error_log`を`info`にしてreloadしてください(#565)。
- `NoMethodError`：メッセージでなく、例外のクラスで判定してください(#561)。
- `private`と`protected`：そうしたメソッドは、レシーバなしで呼ぶか、`send`で呼んでください。privateメソッドは、`private_instance_methods`か`private_methods`で挙げてください(#561, #678)。
- `Module#remove_const`、`#private`、`#public`、`#protected`、`#module_function`とフック：クラスやモジュールの本体の中でレシーバなしで呼ぶか、`send`で呼んでください(#561)。
- `append_features`、`prepend_features`、`extend_object`のオーバーライド：そのコードを`included`、`prepended`、`extended`に移してください(#561)。
- Floatへの`allbits?`、`anybits?`、`nobits?`：先に`to_i`で変換してください(#561)。
- `FileTest`：メソッドを呼ぶだけなら、何もしなくてかまいません(#561)。
- メソッドの本体で代入する定数：`Object.const_set`か`Kernel.const_set`を使ってください(#561)。
- Floatのビット演算：先に`to_i`で変換するか、項目の説明に従って前の数を計算してください(#561)。
- `String#valid_encoding?`：呼び出しを削除するか、mruby-encodingを加えてビルドし、スクリプトを確かめてください(#561)。
- シードを与えた`Random`と`srand`：バージョンをまたいで、その数に依存しないでください(#561)。
- `Set#inspect`、`Set#to_s`、`Set#flatten_merge`：前の2つをデータの形式として使わないでください。`s.flatten_merge(t)`の代わりに`s.merge(Set.new(t).flatten)`を呼んでください(#561)。
- `Hash#default_proc=`：Procか`nil`を渡してください(#561)。
- キーワード引数を付けた`yield`：何もしなくてかまいません(#561)。
- ハンドラのコードのブロックや`for`の本体の中の`return`：何もしなくてかまいません(#561)。
- 出力なしで終わるcontentハンドラ：500に頼っていたハンドラは、意図したステータスを設定してください。例は`Nginx::HTTP_INTERNAL_SERVER_ERROR`です。`response body is empty. return NGX_HTTP_INTERNAL_SERVER_ERROR`に一致させるログの監視には、メインリクエストのそのようなハンドラのうち、ステータスが無いものと、nginxが自分では応答しない200から299のステータスのものが見えなくなります(#574)。
- 空のボディで終わる出力のボディフィルタ：何もしなくてかまいません(#574)。
- `Nginx::Var`のアクセサ：変数があるかどうかは`v.exist?(name)`で判断し、スクリプトのメソッドにはnginxの変数の名前でない名前を付けてください(#610)。
- `Nginx::Connection`、`Nginx::Server`、`Nginx::Request`：別の値を返すには、これらのクラスにメソッドを定義してください。変数は、`@iv_var`でなく`Nginx::Var`で読んでください(#610)。
- `Dir`：閉じることのある`Dir`の周りでは、`RuntimeError`の代わりに`IOError`をrescueしてください。両方のバージョン向けのスクリプトは、両方をrescueしてください(#559)。
- C拡張：Cのデータをラップするクラスを`MRB_SET_INSTANCE_TT(klass, MRB_TT_DATA)`で宣言し、Cのメソッドを`mrb_get_args`が読むものに合う仕様で定義してください。`mruby/io.h`、`mrb_temp_alloc()`、`MRB_OPEN_FAILURE()`を使ってください。`mrb_open()`と`mrb_open_core()`はアロケータなしで呼び、自分のアロケータには`mrb_basic_alloc_func()`を定義してください。`mruby/build/host/include`をインクルードパスに加え、`--with-mruby-incdir`で与える一覧にも加えてください(#561, #572)。
- auto-sslのmrbgemに伴うクラス：`Base64`の代わりに`pack('m0')`と`unpack1('m')`を、`Dir.tmpdir`の代わりに`ENV['TMPDIR'] || '/tmp'`を、`Dir.mktmpdir`の代わりに`Dir.mkdir`を使ってください。または、gemを自前の`build_config.rb`に加えてください(#556)。
- auto-sslのmrbgem：証明書はngx_http_acme_moduleで取得してください。`Nginx::SSL::ACME`が必要なサーバーは、2.xのビルドを使い続けてください。ビルドの環境から`NGX_MRUBY_AUTO_SSL`を除いてください(#640)。
- `Nginx::Upstream#server=`と`Nginx::Stream::Connection#upstream_server=`：serverにできない文字列には`ArgumentError`をrescueしてください。両方のバージョン向けのスクリプトは、`ArgumentError`と`RuntimeError`の両方か、`StandardError`をrescueしてください(#680)。
- ホスト名を渡す`Nginx::Upstream#server=`：スクリプトが待たずに得られるIPアドレスを渡すか、名前を`upstream {}`ブロックの`server`の行に書いてsetterを呼ばないでください。IPv4アドレスは4つの10進数で書いてください。アドレスが2つ以上ある名前では、`Nginx::Upstream.new`がそのupstreamに例外を出すので、その呼び出しも削除してください(#680)。
- `Nginx::Async.sleep`で待つaccessハンドラとpost_readハンドラ：sleepの後にリクエストを拒むaccessハンドラは、`Nginx::HTTP_FORBIDDEN`か`Nginx::HTTP_UNAUTHORIZED`を返してください(#715)。
- 出力を書くaccessハンドラとpost_readハンドラ：何もしなくてかまいません(#715)。
- 前のハンドラがすべてのリクエストで値を返す設定の、結果を設定しないハンドラ：先へ進むべきcontentハンドラと、`satisfy any`のaccessハンドラは、自分で`Nginx::DECLINED`を返してください(#715)。
- `Nginx::Async.sleep`で待つ`mruby_set`のハンドラ：sleepの後にステータスでリクエストを終えていたコードは、そのステータスを後のハンドラから返してください(#715)。
- 結果なしで終わるrewriteハンドラとserver rewriteハンドラ：リクエストを終えるハンドラは、意図するステータスを返してください(#720)。
- `Nginx::Async.sleep`の後のcontentハンドラの`Nginx::Async::HTTP.sub_request`：その`RuntimeError`の`rescue`を削除してください(#722)。
- `Nginx::Async::HTTP.sub_request`で待つハンドラ：コードがもう一度動くことに頼っていた処理は、呼び出しの後に書いてください(#722)。
- コードがsleepするUDPのstreamのセッション：データグラムごとに1回動くことに頼っていたコードは、sleepしないでください(#727)。
- `worker_shutdown_timeout`が切れたときに待っているstreamのセッション：終わらせる必要のあるsleepは、タイムアウトより短くしてください(#727)。
- `Nginx::Stream::Connection.proxy_protocol_addr`と`proxy_protocol_ip`：結果をStringと比べるコードでは、対応は要りません。結果にStringのメソッドを呼ぶコードでは、`to_s`などで`nil`を扱ってください。
- `Nginx::Stream::Async.sleep`の間の、`proxy_protocol`を付けたlistenのstreamのセッションの読み込み：対応は要りません。
- ローカルのURIへの`Nginx.redirect`：呼び出しの後にクライアントへ送るつもりのものを書かず、リダイレクト先が設定したものを読むコードはリダイレクト先へ移してください(#728)。
- `mruby_set`と`mruby_set_code`の`Nginx::Async::HTTP.sub_request`：rewriteかaccessのハンドラで呼び、そこで`Nginx::Var#set`で変数を設定してください(#NNN)。
