# ngx_mruby v2.7.2

ngx_mruby 2.7.2は、2.x系列のメンテナンスリリースです。

修正の一部で、既存の設定、Rubyのスクリプト、ビルドから見える挙動が変わります。アップグレードの前に最初の節を読んでください。各項目では、2.7.1で見えた挙動を「変更前」に、2.7.2で見える挙動を「変更後」に書きました。挙動を変える必要があった理由は「変更の理由」に書き、「不具合」か「背景」、「前の挙動を残せなかった理由」、「ドキュメントが示していた挙動」の3行に分けました。続けて、影響を受ける設定と必要な対応を書きました。テストスイートが変更を試している項目には、そのテストのポートも書きました。「このリリースで変わらない挙動」には、関係する挙動のうち変わらないものを書きました。

## アップグレードの前に読む挙動の変更

### 1. 変数を指さないメソッド名や値の無いセッターでNginx::Varを呼ぶと、例外が発生します（#589）

- 変更前：`Nginx::Var`は、自分が定義していないメソッドの呼び出しを、同じ名前のnginxの変数へのアクセスとして扱います。たとえば`v.http_host`は`$http_host`を読みます。名前が`=`で終わるメソッドは、`=`の前の名前の変数に値を設定するセッターとして扱います。たとえば`v.http_host = "a"`は`$http_host`に値を設定します。実行時に名前を組み立てるコードは、名前を`send`に渡します。次の3種類の名前では、アクセサが名前か引数の外のメモリを読んだので、結果はそのメモリの内容で決まりました。
  - `v.send("")`のように空の名前で呼ぶと、アクセサは名前の前の1バイトを読みました。結果は、たいてい`nil`でした。
  - `v.send("=", "x")`のように`=`だけでできた名前で呼ぶと、アクセサは名前の終わりより先を読みました。`nil`が返ることも、ワーカープロセスが終了することもありました。
  - `v.send("http_host=")`のように値を渡さずにセッターを呼ぶと、アクセサは引数の外から値を読みました。ワーカープロセスが終了することも、コードが渡していない値が変数に設定されることもありました。
- 変更後：空の名前と、`=`だけでできた名前では、`NoMethodError`が発生します。メッセージは、`undefined method '' for Nginx::Var`と`undefined method '=' for Nginx::Var`です。値を渡さずにセッターを呼ぶと、`ArgumentError`が発生し、変数は元の値のままです。メッセージは`wrong number of arguments (given 0, expected 1) for Nginx::Var#http_host=`です。アクセサは、名前と引数を読む前に、それらを確かめます。
- 変更の理由：
  - 不具合：「変更前」に書いたとおり、アクセサは、空の名前では名前の前の1バイトを読みました。`=`だけでできた名前では、名前のコピーの終わりより先まで`strtok`で読みました。値の無いセッターでは、空の引数の並びから最初の要素を読みました（[#589](https://github.com/matsumotory/ngx_mruby/pull/589)）。
  - 前の挙動を残せなかった理由：これらの呼び出しの結果は、名前と引数の外のメモリから来ていました。そのため、同じ呼び出しでも、`nil`が返ることも、ワーカープロセスが終了することもありました。このような名前はどの変数も指さず、引数の無いセッターには設定する値がありません。そのため、残せる結果がありません。代わりに、Rubyと同じ例外が発生します。受け手に無いメソッドを呼んだときの`NoMethodError`と、メソッドが取る数より少ない引数で呼んだときの`ArgumentError`です。
  - ドキュメントが示していた挙動：2.7.1のドキュメントには、アクセサが`Nginx::Var#VARNAME`と`Nginx::Var#VARNAME=`で呼ばれると書いてあります。名前が`=`で終わるときは、「the 2nd arg」を変数に設定するとも書いてあります（[2.7.1のNginx::Var#method_missing](https://github.com/matsumotory/ngx_mruby/blob/v2.7.1/docs/class_and_method/README.md#nginxvarmethod_missingsymbol--args---result)）。変数の名前を含まない名前と、値の無いセッターについては、何も書いてありません。
- 影響の範囲：`send`、`public_send`、`method_missing`に実行時に組み立てた名前を渡して`Nginx::Var`を呼ぶコードのうち、名前が空か`=`だけになりうるものです。値を渡さずにセッターを呼ぶコードも、影響を受けます。
- 必要な対応：呼び出しの前に名前を確かめるか、名前が空になりうるところで`NoMethodError`をrescueしてください。セッターには、必ず値を渡してください。
- このリリースで変わらない挙動：アクセサが読み書きする変数は、前と同じです。大文字を含む名前も、前と同じく、小文字にした名前の変数を指します。2つ以上の値を渡したセッターは、これまでどおり最初の値を使います。`=foo=`のような名前も、これまでどおり`$foo`に値を設定します。
- テスト：`test/t/cases/var_input.rb`のポート18153のテストです。

### 2. Nginx::Var#setは、名前として渡したStringとSymbolを変えなくなりました（#589）

- 変更前：`Nginx::Var#set(name, value)`は、小文字にした名前で変数を探しました。その名前を得るために、`name`のバイトをその場で小文字に書き換えました。そのため、呼び出しの後、`name`に渡したStringは小文字になっていました。freezeしたStringでも同じでした。バイトを共有するStringも、小文字になりました。たとえば、長いStringから`dup`で作ったコピーです。長い名前のSymbolでは、`set`は、ワーカーがそのSymbolのために持つ名前を小文字に書き換えました。そのため、そのワーカーの後のどのリクエストでも、そのSymbolの`to_s`は小文字の名前を返しました。ここで長いとは、64ビットのビルドで27バイトを超えることです。mrubyは、それより短いStringをStringのオブジェクトの中に持ち、コピーはそのバイトを共有しません。
- 変更後：`set`は、名前を小文字にしたコピーで変数を探します。`name`に渡したStringとSymbolは、元のままです。`set`が値を設定する変数と、`set`が返す値は、前と同じです。
- 変更の理由：
  - 不具合：「変更前」に書いたとおり、`set`は、`name`に渡したStringに書き込みました。その結果、freezeしたString、バイトを共有するString、Symbolの名前まで書き換わりました（[#589](https://github.com/matsumotory/ngx_mruby/pull/589)）。
  - 前の挙動を残せなかった理由：freezeしたStringは、変更できないはずのオブジェクトです。バイトを共有するStringは、コードが持つ別のオブジェクトです。Symbolの名前は、ワーカーのすべてのリクエストが使います。変数を探すには小文字の名前が要るので、`set`はコピーを小文字にします。
  - ドキュメントが示していた挙動：2.7.1のドキュメントには、`set`はnginxの変数に値を設定すると書いてあります（[2.7.1のNginx::Var#set](https://github.com/matsumotory/ngx_mruby/blob/v2.7.1/docs/class_and_method/README.md#nginxvarsetname-value)）。`set`が引数を変えるとは、書いてありません。
- 影響の範囲：`set`に渡したStringかSymbolを呼び出しの後で使い、それが小文字になっていると期待するコードです。
- 必要な対応：`set`が名前を小文字にすることに頼っていたコードでなければ、対応は要りません。そのようなコードでは、自分で名前に`downcase`を呼んでください。
- テスト：`test/t/cases/var_input.rb`のポート18153のテストです。

### 3. mruby-redisを有効にしたビルドは、どのプラットフォームでもhiredisのv1.5.0を使い、hiredisの警告では止まらなくなりました（matsumotory/mruby-redis#108）

- 変更前：[2.7.1のリリースノート](v2.7.1.ja.md#1-redisはデフォルトのビルドに含まれなくなりました)の項目1に書いたとおり、2.7.1のデフォルトの`build_config.rb`には`matsumotory/mruby-redis`が入っていません。`conf.gem github: 'matsumotory/mruby-redis'`のコメントアウトを外すか、独自の`build_config.rb`でこのgemを有効にしたビルドは、gemのビルドスクリプトからhiredisを得ます。gemのビルドディレクトリに`hiredis`ディレクトリがまだ無いとき、このスクリプトはhiredisをデフォルトブランチの先頭からcloneし、macOSではv0.13.3をcheckoutしました。スクリプトはmrubyのビルドのCのフラグでhiredisをコンパイルし、hiredisの1.2.0以降のMakefileは`-Werror`を加えます。そのため、hiredisに新しい警告が出ると、ビルドが止まりました。hiredisの1.4.0以降とmrubyのgccのツールチェーンを組み合わせると、ビルドは`ffc.h:330:5: error: "FFC_DEBUG" is not defined, evaluates to 0 [-Werror=undef]`で止まりました。
- 変更後：gemのビルドスクリプトは、macOSを含むすべてのプラットフォームで、hiredisのタグ`v1.5.0`を`hiredis-v1.5.0`にcloneします。cloneしたツリーが、このタグのコミット`5bb7f030f6631b243438cf0fdd3be84352b905bb`でないときは、両方のコミットを示すメッセージを出してビルドを止めます。スクリプトはhiredisを`USE_WERROR=0`でビルドするので、ビルドはhiredisの警告を表示して先へ進みます。また、スクリプトはhiredisを`make install`だけでビルドするので、`hiredis-test`をビルドしなくなりました。Alpineのようなmuslのシステムでは、`linux-headers`が要らなくなりました。前のビルドが残した`hiredis`ディレクトリは使いません。この変更は、gemの変更です。ngx_mrubyの2.xはgemのlockをコミットしていないので、ビルドはgemを`master`ブランチの先頭からcloneします。[matsumotory/mruby-redis#108](https://github.com/matsumotory/mruby-redis/pull/108)のマージの後にgemをcloneするビルドは、すべてこの変更を受けます。2.7.1のビルドも同じです。mrubyは、前にcloneしたgemを更新しません。そのため、マージの前にmruby-redisをビルドしたソースツリーは、mrubyのビルドディレクトリ`mruby/build`を消すまで、前にcloneしたgemとそのhiredisを使い続けます。
- 変更の理由：
  - 不具合：バージョンを固定しないcloneのため、hiredisの新しいコミットは、gemを有効にしたすべての新しいビルドに届きました。hiredisの1.4.0は、上の`FFC_DEBUG`のエラーで、そのようなビルドを止めました（[#528](https://github.com/matsumotory/ngx_mruby/pull/528)、[matsumotory/mruby-redis#108](https://github.com/matsumotory/mruby-redis/pull/108)）。
  - 前の挙動を残せなかった理由：hiredisのデフォルトブランチに追従するビルドは、hiredisのどのコミットでも壊れる可能性があります。2.7.1がgemをデフォルトのビルドから外したのは、このためです。リリースを固定してそのコミットを確かめると、どのビルドも同じhiredisを使います。`-Werror`も外す必要がありました。ngx_mrubyのsanitizerのフラグ`-fsanitize=address,undefined -fno-omit-frame-pointer`を付けると、gccの13から15では、hiredisのv1.5.0のビルドが`sds.c:525`の`null format string [-Werror=format-truncation=]`で止まります。そのため、`-Werror`を残すと、新しいコンパイラーでは、固定したビルドも壊れます。`USE_WERROR=0`は、`-Werror`を使わないビルドのために、hiredisの1.3.0以降が用意したスイッチです（[redis/hiredis#1210](https://github.com/redis/hiredis/pull/1210)）。v1.5.0は、LinuxとmacOSでビルドでき、gemのテストに通ります。そのため、macOSでもv0.13.3は要らなくなりました。
  - ドキュメントが示していた挙動：2.7.1のリリースノートの項目1には、「#528に書いたhiredisの問題が残っている間は、このgemのビルドが失敗することがあります」と書いてあります。2.7.1のドキュメントには、`build_config.rb`でこのgemの行のコメントアウトを外すと書いてあります（[2.7.1のbuilt-in mrbgems](https://github.com/matsumotory/ngx_mruby/blob/v2.7.1/docs/class_and_method/README.md#built-in-mrbgems)）。このgemのビルドについては、「clones the hiredis library from an unpinned branch, which broke the build of ngx_mruby」と書いてあります（[2.7.1のdocs/install](https://github.com/matsumotory/ngx_mruby/blob/v2.7.1/docs/install/README.md#2-configuring-mrbgems)）。hiredisのバージョンは書いてありません。
- 影響の範囲：mruby-redisを有効にした2.7.1と2.7.2のビルドと、2.7.0以前のデフォルトのビルドです。2.7.0以前のデフォルトの`build_config.rb`には、このgemが入っています。これらのビルドは、マージの後にgemをcloneすると、hiredisのデフォルトブランチの先頭の代わりに、macOSではv0.13.3の代わりに、hiredisのv1.5.0を使います。mruby-redis#108は、gemをmruby 3.3.0とmruby 4.0.0で試しました。2.6.0から2.7.2はmruby 3.3.0を同梱し、2.5.0以前はそれより古いmrubyを同梱します。gemはhiredisを静的にリンクするので、前にビルドしたバイナリは、`mruby/build`を消してビルドし直すまで前のhiredisのままです。2.7.1と2.7.2のビルドのうち、デフォルトの`build_config.rb`でのビルドは、このgemを含まないので、影響を受けません。
- 必要な対応：2.7.1以降のデフォルトのビルドでは、対応は要りません。前にこのソースツリーでmruby-redisをビルドしたときは、先に`mruby/build`を消してください。mruby-redisを有効にしたビルドと、2.7.0以前のデフォルトのビルドが、これに当たります。そのうえで、これまでどおりビルドしてください。2.7.1のリリースノートの項目1の注意「このgemのビルドが失敗することがあります」は、もう当てはまりません。ほかのhiredisのリリースでビルドするには、ビルドのときに環境変数`MRUBY_REDIS_HIREDIS_VERSION`にそのタグを設定するか、`build_config.rb`で`ENV['MRUBY_REDIS_HIREDIS_VERSION']`を設定してください。設定の方法は、[mruby-redisのREADME](https://github.com/matsumotory/mruby-redis#readme)に書いてあります。ほかのタグでは、ビルドはコミットを確かめません。mruby-redis#108では、前の先頭のコミット2cc63c1で、gccとmruby 3.3.0を使い、`v1.4.1`でもビルドとテストをしました。
- このリリースで変わらない挙動：デフォルトの`build_config.rb`には、2.7.1と同じく、mruby-redisが入っていません。mruby-redis#108は、mruby 4.0.0のために`Redis#ttl`の宣言を変えました。同梱のmruby 3.3.0では、`Redis#ttl`は前と同じに動きます。
- テスト：ngx_mrubyのテストスイートには、Redisを使うテストがありません。また、デフォルトのビルドにはこのgemが入っていません。mruby-redis#108には、ngx_mrubyの`master`（03aad7031）と`next`（75bfa6ff4）のテストスイートの結果が載っています。どちらも、そのプルリクエストの先頭のコミットでgemを有効にしてビルドし、テストに通りました。gemのCIは、Ubuntu 22.04とUbuntu 24.04でgemのテストを流します。Ubuntu 24.04では、ngx_mrubyのCIのsanitizerの設定を使います。

## 新機能

ありません。

## 不具合の修正

- nginxが値を返さない変数を`Nginx::Var`で読むと、`Nginx::Var`は`error.log`に`<name> is NULL`の行を書きます。たとえば、rootが存在しないlocationで`$realpath_root`を読んだときです。この行で、変数の名前は名前の最後の文字で終わるようになりました。前は、メモリの上で名前の後に続くバイトが、行に入ることがありました（[#589](https://github.com/matsumotory/ngx_mruby/pull/589)）。

## ビルドとテストの変更

- `test.sh`：HTTPのテストサーバーは、`test/t/cases/var_input.rb`のために、18153でも待ち受けます（[#589](https://github.com/matsumotory/ngx_mruby/pull/589)）。
- `test.sh`：最初のリクエストの前に`NGINX_HEATTIME`秒だけ止まる代わりに、テストのnginxが接続を受け付けるまで待ち、待った時間を表示します。valgrindで動かすCIのセルの1つが、`Errno::ECONNREFUSED`で失敗したためです。そのセルでは、10秒止まった後も、nginxが設定を読んでいました（[#564](https://github.com/matsumotory/ngx_mruby/pull/564#issuecomment-5977252444)）。待つポートは、`test/conf/nginx.conf`と`test/conf/conf.d/*.conf`の`listen`ディレクティブにある全部のポートです。`NGINX_HEATTIME`は待つ時間の上限になり、既定は60秒です。これまでは止まる時間で、既定は2秒、CIでは10秒でした。CIは、`NGINX_HEATTIME`を設定しなくなりました。上限までにnginxが待ち受けないときと、待ち受ける前にnginxが終了したときは、まだ接続を拒むポートを表示して失敗します。`test.sh`は、nginxを起動する前にも、それらのポートでどのプロセスも接続を受け付けなくなるまで待ちます。待ち方は、`docs/test/README.md`の「Waiting for nginx to listen」に書いてあります（[#593](https://github.com/matsumotory/ngx_mruby/pull/593)）。
- テストの無かったディレクティブとRubyのメソッドに、テストを加えました。テストは、`nginx -t`が`mruby_output_filter`と`mruby_output_filter_code`をそのメッセージで拒むことと、nginxが止まるときに`mruby_exit_worker_code`と`mruby_stream_exit_worker_code`が動くことを確かめます。次のメソッドについては、返す値か`error.log`に書く行を確かめます：`Nginx.module_version`、`Nginx.nginx_version`、`Nginx.server_version`、`Nginx::Request#content_type`、`#content_type=`、`#method=`、`#scheme`、`#document_root`、`Nginx::SSL.log`、Rackのloggerのメソッド、`Nginx::Utils.escape`と`.encode_parameters`、`Nginx::Stream::Connection`のセッションのアドレスを読むメソッド、`#upstream_server`、`Nginx::Stream.errlogger`、`Nginx::Stream.module_name`。HTTPのテストサーバーは18155から18157でも待ち受け、streamのテストサーバーは12363でも待ち受けます。`test/t/cases/config_hooks.rb`は別のnginxを起動します。そのnginxは18158で待ち受け、`nginx -s quit`で止まります（[#603](https://github.com/matsumotory/ngx_mruby/pull/603)）。

## アップグレード

サポートするnginxのバージョンは、[README.md](../../README.md)に書いたとおり、nginxのmainlineとstableの系列です。CIは、nginx 1.31.6、1.30.5、1.28.3、1.26.3をビルドします。

- 追加、改名、削除したディレクティブはありません。このリリースで、モジュールをビルドし直してください。2.7.1をビルドしたときと同じ方法でビルドし、いつもどおりバイナリか動的モジュールを置き換えてください。

アップグレードの前に、次の点を確かめてください。各行は、上の各項目の「必要な対応」です。

- 実行時に組み立てた名前での`Nginx::Var`の呼び出し：呼び出しの前に名前を確かめるか、名前が空になりうるところで`NoMethodError`をrescueしてください。セッターには、必ず値を渡してください（項目1）。
- `Nginx::Var#set`：`set`が名前を小文字にすることに頼っていたコードでなければ、対応は要りません。そのようなコードでは、自分で名前に`downcase`を呼んでください（項目2）。
- mruby-redisをビルドする場合：前にこのソースツリーでmruby-redisをビルドしたときだけ、先に`mruby/build`を消してください。ほかに対応は要りません。ビルドはhiredisのv1.5.0を使い、2.7.1のリリースノートの項目1の注意は、もう当てはまりません。ほかのhiredisのタグでビルドするには、環境変数`MRUBY_REDIS_HIREDIS_VERSION`を設定してください（項目3）。
