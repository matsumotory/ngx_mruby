# ngx_mruby v2.7.6

## Behavior changes: read before upgrading

### Output from an HTTP log handler

- Before: a log handler could append the text of `Nginx.rputs` or `Nginx.echo` after the response body.
- Now: the calls convert their argument as usual and write no bytes. The script continues after a successful call.
- Why it changed:
  - The defect: the shared handler finalizer could flush an output chain while nginx was freeing the request.
  - Why the old behavior could not be kept: extra bytes could be read as another response on the connection.
  - What the documentation promised: the [log directives](../directives/README.md#mruby_log_handler-and-mruby_log_handler_code) run at the end of request processing for logging.
- Affected: HTTP file and inline log handlers, including calls from their helper methods.
- What to do: log messages with `Nginx.log`. Write response bodies in a content handler.
- Not changed by this release: argument conversion errors and output from ordinary content handlers.

### Output of an mruby content handler or body filter in an SSI subrequest

- Before: the output of a subrequest's mruby content handler (`Nginx.rputs`, `Nginx.echo`, `Nginx.send_header`) or mruby body filter could end the parent response at the subrequest's output. Over HTTP/1.1 the chunked filter emitted the response-terminator chunk mid-stream, so a length-delimited reader saw two responses where there was one; over HTTP/1.0 or when the parent used `Content-Length`, the parent response was cut short at the subrequest's bytes and the connection closed; and a static file read through the mruby body filter of a subrequest held the main request until `send_timeout`.
- Now: a subrequest marks its last buffer with `last_in_chain` (and `sync` for an empty buffer), as nginx's own handlers do. The parent response goes on until the main request's own last buffer. The static file case no longer stops the main request.
- Why it changed:
  - The defect: ngx_mruby's response finalization set `last_buf` on every chain, which is correct only for the main request. Nginx's chunked filter, Content-Length framing and body-end detection act on `last_buf`.
  - Why the old behavior could not be kept: a subrequest's `last_buf` ended the parent response early (a split chunked response, a truncated Content-Length or HTTP/1.0 response, read as another response on a shared connection), and the body-filter path held the main request until `send_timeout` closed the connection.
  - What the documentation promised: [Nginx.rputs](https://github.com/matsumotory/ngx_mruby/blob/v2.7.5/docs/class_and_method/README.md#nginxrputsstring) and [Nginx::Filter](https://github.com/matsumotory/ngx_mruby/blob/v2.7.5/docs/class_and_method/README.md#nginxfilter-class) in 2.7.5 said nothing about how a subrequest's output interacts with the parent response.
- Affected: locations whose mruby content handler calls `Nginx.rputs`, `Nginx.echo` or `Nginx.send_header`, or whose mruby body filter produces a body, when another location includes them with SSI `<!--# include virtual=... -->` or by another form of subrequest.
- What to do: nothing. The subrequest output is framed correctly as part of the parent response.

### A value of mruby_set or Nginx::Var whose to_s is missing, raises or does not return a String no longer ends the worker (#768)

- Before: ngx_mruby converted a value that is not a String with its `to_s` and used the result as a String without checking its type. For the value that the code of `mruby_set` or `mruby_set_code` returned, it called `to_s` where mruby does not raise an exception of `to_s` but returns it. A `to_s` that returns something other than a String ended the worker process with a segmentation fault, before and after `Nginx::Async.sleep`. A value without `to_s` (a `BasicObject`) or whose `to_s` raises was read as a String although it was the exception, and the exception stayed in the mruby state of the worker: the request got 500 or no response, and the next mruby handler that the worker ran, in the same request or a later one, could fail with that exception and answer 500. The setter of `Nginx::Var` (`Nginx::Var#<name>=`) and `Nginx::Var#set` ended the worker process when they got a value, or `Nginx::Var#set` a name, whose `to_s` returns something other than a String. A `to_s` that is missing or raises made these two methods raise its exception, as it does now.
- Now: a value of `mruby_set` and `mruby_set_code` that cannot be converted counts as an exception of the code. Before the code waits in `Nginx::Async.sleep`, ngx_mruby logs the exception, the variable is set to an empty string, and the request goes on. After the sleep, ngx_mruby logs the exception and the request gets 500. The exception is `TypeError` (`... cannot be converted to String`) for a `to_s` that returns something other than a String, `NoMethodError` for a value without `to_s`, and the exception of `to_s` otherwise. The setter of `Nginx::Var` and `Nginx::Var#set` raise `TypeError` when `to_s` returns something other than a String, and the variable keeps its value. No exception stays for a later handler.
- Why it changed:
  - The defect: ngx_mruby read the result of `to_s` as a String without checking its type, and at the end of an `mruby_set` handler it called `to_s` outside Ruby code, where mruby returns the exception of a `to_s` that is missing or raises instead of raising it. The review of [#735](https://github.com/matsumotory/ngx_mruby/pull/735), which fixed the same conversion on `next`, found it.
  - Why the old behavior could not be kept: the old behavior ended the worker process, with the other requests of that worker, or made a later handler fail with an exception that was not its own. The variable needs a String, and such a value gives none, so the fix handles the value as the exception that ngx_mruby already handles for this code.
  - What the documentation promised: [mruby_set and mruby_set_code](https://github.com/matsumotory/ngx_mruby/blob/v2.7.5/docs/directives/README.md#mruby_set-and-mruby_set_code) and [Nginx::Var](https://github.com/matsumotory/ngx_mruby/blob/v2.7.5/docs/class_and_method/README.md#nginxvar-class) in 2.7.5 said nothing about values that are not Strings. The documentation of `mruby_set` described how the variable and the request go on after an exception of the code, which this release applies to these values.
- Affected: `mruby_set` and `mruby_set_code` whose code returns a value whose `to_s` is missing, raises or does not return a String; calls of the setter of `Nginx::Var` and of `Nginx::Var#set` with a value, or a name, whose `to_s` does not return a String.
- What to do: return a String, `nil` or a value whose `to_s` returns a String from the code of `mruby_set`, and pass such values to `Nginx::Var`. Code that returned or passed the other values did not work on 2.7.5 either: it ended the worker or made a handler fail.
- Not changed by this release: a String, `nil`, an Integer and any other value whose `to_s` returns a String give the variable the same value as before, and a `to_s` that is missing or raises in a call of `Nginx::Var` raises the same exception as before.

### Nginx.rputs, Nginx.echo, Nginx.redirect and Nginx::Filter#body= raise TypeError when to_s of the argument does not return a String (#775)

- Before: `Nginx.rputs`, `Nginx.echo`, `Nginx.redirect`, `Nginx::Filter#body=` and `Nginx::Filter#output` converted an argument that is not a String with its `to_s` and used the result as a String without checking its type. A `to_s` that returns an Integer ended the worker process with a segmentation fault, with the other requests of that worker. A `to_s` that returns another object that is not a String made the method read the memory of that object as a String. A `to_s` that is missing or raises made these methods raise its exception, as it does now.
- Now: these methods raise `TypeError` (`... cannot be converted to String`) when `to_s` of the argument returns something other than a String, as the setter of `Nginx::Var` does since #768. The exception ends the handler like any other exception of the script: a `rescue` in the script catches it, and otherwise ngx_mruby logs it and the request gets 500. Nothing is written, no redirect is made, and the body of the filter stays as it was.
- Why it changed:
  - The defect: these methods read the result of `to_s` as a String without checking its type. #768 fixed the same reading for `mruby_set` and `Nginx::Var`, and the tests of that change found it in these methods.
  - Why the old behavior could not be kept: the old behavior ended the worker process, with the other requests of that worker, or read memory that was not a String. These methods need a String, and such a value gives none, so they raise the exception that the setter of `Nginx::Var` raises for the same value.
  - What the documentation promised: [Nginx.rputs](https://github.com/matsumotory/ngx_mruby/blob/v2.7.5/docs/class_and_method/README.md#nginxrputsstring) in 2.7.5 said that an argument that is not a String is converted with `to_s`, and said nothing about a `to_s` that does not return a String. The documentation of `Nginx.echo`, `Nginx.redirect` and `Nginx::Filter#body=` said nothing about arguments that are not Strings.
- Affected: calls of `Nginx.rputs`, `Nginx.echo`, `Nginx.redirect`, `Nginx::Filter#body=` and `Nginx::Filter#output` with an argument whose `to_s` does not return a String.
- What to do: pass a String, `nil` or a value whose `to_s` returns a String to these methods. Code that passed other values did not work on 2.7.5 either: it ended the worker or read memory that was not a String.
- Not changed by this release: a String, `nil` and any other value whose `to_s` returns a String give the same output as before, and a `to_s` that is missing or raises makes these methods raise the same exception as before.

### An mruby body filter, with or without an mruby header filter, runs once on a proxied response that needs more than one write after an earlier `Nginx.rputs` (#786)

- Before: in a location with `mruby_output_body_filter` (or `mruby_output_body_filter_code`), with or without `mruby_output_header_filter` (or `mruby_output_header_filter_code`), when an earlier handler of the request had written with `Nginx.rputs` and let the request go on (for example a rewrite handler that returns `Nginx::DECLINED`), the response came from `proxy_pass`, and nginx could not send it in one write (for example with `sendfile_max_chunk` or `limit_rate`), the code of the body filter ran twice: once on the body of the upstream response, and once more on an empty body when the upstream response ended. The client got the body of the first run with its `Content-Length`, but `$sent_http_content_length` gave `0` in `log_format`.
- Now: the code of the body filter runs once for such a response, and `$sent_http_content_length` gives the length of the body that the client got. A response that nginx sends in one write is not changed by this release: there the code of the body filter still runs a second time on an empty body.
- Why it changed:
  - The defect: when an earlier handler's `Nginx.rputs` output is still in the state of the request after the body filter has run, ngx_mruby drops that state, so that a later handler does not send the output after the response. The dropped state also held the flag that makes the body filter pass the rest of the same response on to the next filter, and the body filter then waited for a new body. A response from a static file stopped after its first write until `send_timeout` closed the connection (see "Fixes"). A proxied response went on only because the end of the upstream response made the body filter run once more, on an empty body. The review of [#785](https://github.com/matsumotory/ngx_mruby/pull/785) found it.
  - Why the old behavior could not be kept: the stop and the second run have the same cause, and the fix gives the request a new state with that flag whenever nginx still holds a part of the response. Keeping the second run for proxied responses would mean leaving the flag out for them alone, and the code of their body filter would still run on an empty body after it has made the response. The new behavior is the one that the same location already has without the earlier `Nginx.rputs`: there the code of the body filter runs once and `$sent_http_content_length` gives the length of the body, whether nginx sends the response in one write or in more.
  - What the documentation promised: [mruby_output_body_filter](https://github.com/matsumotory/ngx_mruby/blob/v2.7.5/docs/directives/README.md#mruby_output_body_filter-mruby_output_body_filter_code-mruby_output_header_filter-and-mruby_output_header_filter_code) and [Nginx::Filter](https://github.com/matsumotory/ngx_mruby/blob/v2.7.5/docs/class_and_method/README.md#nginxfilter-class) in 2.7.5 said nothing about how many times the code of a body filter runs for one response.
- Affected: the code of `mruby_output_body_filter` and `mruby_output_body_filter_code` that counts its runs or acts on an empty body, and `log_format` with `$sent_http_content_length`, for responses from `proxy_pass` (or another upstream) after an earlier `Nginx.rputs` in a location with an mruby body filter, with or without an mruby header filter, which nginx sends in more than one write.
- What to do: nothing for a body filter that only transforms the body, because the body that the client gets is the same. A body filter whose code relied on its second run on an empty body, for example to count responses or to act at the end of one, has to do that in the first run, which now is the only one for such a response.

## New features

None.

## Fixes

- When a rewrite or access handler calls `Nginx::Async::HTTP.sub_request` after a rewrite or access handler of the same request waited in `Nginx::Async.sleep`, the subrequest now starts at once. This holds when the handler that slept calls it and when a handler of a later phase calls it, for example an access handler after a rewrite handler that returned `Nginx::DECLINED` after its sleep. Before, the subrequest started only when the next event of the client connection arrived, and until then the client got no response (#772)
- When a content or rewrite handler writes its response with `Nginx.rputs` in a location with `mruby_output_body_filter` or `mruby_output_body_filter_code`, and nginx cannot send the response in one write (for example with `limit_rate` or `sendfile_max_chunk`, or to a client that reads slowly), nginx now sends the rest of the response. Before, the client received the header with the full `Content-Length` and only the part of the body that the first write sent, and nginx closed the connection when `send_timeout` passed (#784)
- When an mruby body filter runs, with or without an mruby header filter in the location, after an earlier handler wrote with `Nginx.rputs` and let the request go on (for example a rewrite handler that returns `Nginx::DECLINED` before a static file is served), and nginx cannot send the response in one write (for example with `sendfile_max_chunk` or `limit_rate`, or to a client that reads slowly), nginx now sends the rest of the response. Before, the client received the header with the full `Content-Length` and only the part of the body that the first write sent, and nginx closed the connection when `send_timeout` passed (#786)
