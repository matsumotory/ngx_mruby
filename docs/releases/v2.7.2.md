# ngx_mruby v2.7.2

ngx_mruby 2.7.2 is a maintenance release of the 2.x line.

Some of its fixes change what an existing configuration, Ruby script or
build can observe. Read the first section before you upgrade. Each entry says what you
could observe in 2.7.1 ("Before"), what you observe in 2.7.2 ("Now"), why the
behavior had to change ("Why it changed": "The defect" or "The reason", "Why
the old behavior could not be kept" and "What the documentation promised"),
which configurations are affected, what to do, and, where the test suite
covers the change, the port of its tests. "Not changed by this release" names
a related behavior that stays as it was.

## Behavior changes: read before upgrading

### 1. Nginx::Var raises for a method name that names no variable and for a setter without its value (#589)

- Before: `Nginx::Var` treats a call of a method that it does not define as
  access to the nginx variable of that name (`v.http_host` reads
  `$http_host`), and a method name that ends with `=` as a setter of the
  variable named before the `=` (`v.http_host = "a"`). Code that builds the
  name at run time passes it to `send`. For three kinds of names the accessor
  read memory outside the name or outside the arguments, so the result
  depended on that memory:
  - an empty name (`v.send("")`) read the byte before the name, and usually
    returned `nil`;
  - a name made only of `=` (`v.send("=", "x")`) read past the end of the
    name, and returned `nil` or ended the worker process;
  - a setter called without its value (`v.send("http_host=")`) read a value
    from outside its arguments. It could end the worker process, or set the
    variable to a value that the code did not pass.
- Now: an empty name and a name made only of `=` raise `NoMethodError`
  (`undefined method '' for Nginx::Var`, `undefined method '=' for
  Nginx::Var`). A setter called without its value raises `ArgumentError`
  (`wrong number of arguments (given 0, expected 1) for
  Nginx::Var#http_host=`) and leaves the variable as it was. The accessor
  checks the name and the arguments before it reads them.
- Why it changed:
  - The defect: the accessor read the byte before an empty name, ran `strtok`
    past the end of its copy of a name made only of `=`, and read the first
    element of an empty argument list for a setter without its value, as
    "Before" says ([#589](https://github.com/matsumotory/ngx_mruby/pull/589)).
  - Why the old behavior could not be kept: the results of these calls came
    from memory outside the name and the arguments, so the same call could
    return `nil` once and end the worker process another time. Such a name
    names no variable, and a setter has no value to set without its
    argument, so there is no result to keep. The calls raise what Ruby raises
    for a method that the receiver does not have (`NoMethodError`) and for a
    call with fewer arguments than the method takes (`ArgumentError`).
  - What the documentation promised: the 2.7.1 documentation says that the
    accessor is called for `Nginx::Var#VARNAME` and `Nginx::Var#VARNAME=` and
    sets "the 2nd arg" to the variable when the name ends with `=`
    ([Nginx::Var#method_missing of 2.7.1](https://github.com/matsumotory/ngx_mruby/blob/v2.7.1/docs/class_and_method/README.md#nginxvarmethod_missingsymbol--args---result)).
    It says nothing about a name without a variable name in it, or about a
    setter without its value.
- Affected: code that calls `Nginx::Var` with a name that it builds at run
  time (`send`, `public_send`, `method_missing`) when the name can be empty
  or made only of `=`, and code that calls a setter without a value.
- What to do: check the name before the call, or rescue `NoMethodError`
  where the name can be empty. Pass a value to each setter.
- Not changed by this release: the accessor reads and sets the same
  variables as before, also for names with uppercase letters, which name the
  variable in lowercase. A setter called with more than one value still uses
  the first one, and a name like `=foo=` still sets `$foo`.
- Tests: port 18153 (`test/t/cases/var_input.rb`).

### 2. Nginx::Var#set leaves the String or Symbol of the name unchanged (#589)

- Before: `Nginx::Var#set(name, value)` looked the variable up by the
  lowercased name, and lowercased the bytes of `name` in place to get it.
  After the call, the String passed as `name` was in lowercase, also when it
  was frozen, and so was a String that shared its bytes, such as a copy that
  `dup` made of a long String. For a Symbol with a long name, `set`
  lowercased the name that the worker keeps for the Symbol, so `to_s` of that
  Symbol returned the name in lowercase in every later request of the
  worker. Long means more than 27 bytes on a 64-bit build: mruby keeps a
  shorter String inside the String object, and a copy does not share it.
- Now: `set` looks the variable up by a lowercased copy of the name. The
  String or Symbol passed as `name` stays as it was. `set` sets the same
  variable and returns the same value as before.
- Why it changed:
  - The defect: `set` wrote into the String passed as `name`, and through it
    into frozen Strings, into the Strings that shared its bytes and into the
    names of Symbols, as "Before" says ([#589](https://github.com/matsumotory/ngx_mruby/pull/589)).
  - Why the old behavior could not be kept: a frozen String must not change,
    a String that shares its bytes is another object of the code, and the
    name of a Symbol belongs to every request of the worker. The lookup needs
    the name in lowercase, so it takes a copy.
  - What the documentation promised: the 2.7.1 documentation says that `set`
    sets the value to the nginx variable
    ([Nginx::Var#set of 2.7.1](https://github.com/matsumotory/ngx_mruby/blob/v2.7.1/docs/class_and_method/README.md#nginxvarsetname-value)).
    It does not say that `set` changes its arguments.
- Affected: code that uses the String or Symbol that it passed to `set`
  after the call, and expects it in lowercase.
- What to do: nothing, unless the code relied on `set` lowercasing the name.
  Such code calls `downcase` on the name itself.
- Tests: port 18153 (`test/t/cases/var_input.rb`).

### 3. Redis is in the default build again, and mruby-redis builds hiredis v1.5.0 on every platform without stopping on hiredis warnings (#604, matsumotory/mruby-redis#108)

- Before: the default `build_config.rb` of 2.7.1 leaves
  `matsumotory/mruby-redis` out (entry 1 of the
  [2.7.1 notes](v2.7.1.md#1-redis-is-no-longer-in-the-default-build)), so
  a binary built with it has no `Redis` class, and code that refers to
  `Redis` raises `NameError` (uninitialized constant Redis). A build that
  enables the gem, by uncommenting
  `conf.gem github: 'matsumotory/mruby-redis'` or with its own
  `build_config.rb`, gets hiredis from the build script of the gem. When the
  build directory of the gem had no `hiredis` directory yet, the script
  cloned hiredis from the head of its default branch, and on macOS checked
  out v0.13.3. The script compiled hiredis with the C flags of the mruby
  build, and the Makefile of hiredis 1.2.0 and later adds `-Werror`, so a
  new warning in hiredis stopped the build. With hiredis 1.4.0 and later and
  the gcc toolchain of mruby, the build stopped at
  `ffc.h:330:5: error: "FFC_DEBUG" is not defined, evaluates to 0 [-Werror=undef]`.
- Now: the default `build_config.rb` includes `matsumotory/mruby-redis`
  again ([#604](https://github.com/matsumotory/ngx_mruby/pull/604)), as
  the default `build_config.rb` of 2.7.0 and earlier did. A binary built
  with it has the `Redis` class, and its build clones the gem and hiredis
  from GitHub. The build script of the gem clones the hiredis tag `v1.5.0` into
  `hiredis-v1.5.0` on every platform, macOS included. It stops, with a
  message that names both commits, when the clone is not at commit
  `5bb7f030f6631b243438cf0fdd3be84352b905bb`, the commit of that tag. It
  builds hiredis with `USE_WERROR=0`, so the build prints the warnings of
  hiredis and goes on. It builds hiredis with `make install` only, so
  `hiredis-test` is no longer built, and musl systems such as Alpine no
  longer need `linux-headers`. A `hiredis` directory left by an earlier
  build is not reused. The change of hiredis is in the gem: ngx_mruby 2.x commits no
  gem lock, so the build clones the gem at the head of its `master` branch.
  Every build that clones the gem after the merge of
  [matsumotory/mruby-redis#108](https://github.com/matsumotory/mruby-redis/pull/108)
  gets the change, a build of 2.7.1 included. mruby does not update a gem
  that it cloned before: a source tree that built mruby-redis before the
  merge keeps that checkout of the gem, and its hiredis, until its mruby
  build directory `mruby/build` is removed.
- Why it changed:
  - The defect: the unpinned clone let every new hiredis commit reach every
    new build that enables the gem, and hiredis 1.4.0 stopped such builds
    with the `FFC_DEBUG` error above
    ([#528](https://github.com/matsumotory/ngx_mruby/pull/528),
    [matsumotory/mruby-redis#108](https://github.com/matsumotory/mruby-redis/pull/108)).
    2.7.1 left the gem out of the default build because of this defect
    (entry 1 of the 2.7.1 notes).
  - Why the old behavior could not be kept: a build that follows the default
    branch of hiredis can break with any hiredis commit, which is why 2.7.1
    left the gem out of the default build. A pinned release with a checked
    commit gives every build the same hiredis. `-Werror` had to go as well:
    with ngx_mruby's sanitizer flags
    (`-fsanitize=address,undefined -fno-omit-frame-pointer`), gcc 13 to 15
    stop the build of hiredis v1.5.0 at `sds.c:525` with
    `null format string [-Werror=format-truncation=]`, so a newer compiler
    would break the pinned build too. `USE_WERROR=0` is the switch that
    hiredis 1.3.0 and later provide for builds that do not want `-Werror`
    ([redis/hiredis#1210](https://github.com/redis/hiredis/pull/1210)).
    v1.5.0 builds and passes the tests of the gem on Linux and macOS, so
    macOS no longer needs v0.13.3. With hiredis pinned, the reason for
    leaving the gem out of the default build no longer holds: entry 1 of
    the 2.7.1 notes kept the gem out of the default list "until
    mruby-redis pins hiredis". Leaving it out longer would keep `Redis`
    from the scripts that used it with the default build of 2.7.0 and
    earlier, the examples in the README and in `docs/use_case` and the
    client of the bundled `auto-ssl` mrbgem among them.
  - What the documentation promised: entry 1 of the 2.7.1 notes says that
    the build of the gem "can fail while hiredis has the problem that #528
    describes". The 2.7.1 documentation says to uncomment the line of the
    gem in `build_config.rb`
    ([built-in mrbgems of 2.7.1](https://github.com/matsumotory/ngx_mruby/blob/v2.7.1/docs/class_and_method/README.md#built-in-mrbgems)).
    It says that the build of the gem "clones the hiredis library from an
    unpinned branch, which broke the build of ngx_mruby"
    ([docs/install of 2.7.1](https://github.com/matsumotory/ngx_mruby/blob/v2.7.1/docs/install/README.md#2-configuring-mrbgems)),
    and does not name a version of hiredis. It also says that the `Redis`
    class "is not in the default build since 2.7.1". The 2.7.0
    documentation listed mruby-redis among "the default mrbgems"
    ([docs/install of 2.7.0](https://github.com/matsumotory/ngx_mruby/blob/v2.7.0/docs/install/README.md#2-configuring-mrbgems))
    and `Redis` among the classes that can be used "with default build
    configuration"
    ([built-in mrbgems of 2.7.0](https://github.com/matsumotory/ngx_mruby/blob/v2.7.0/docs/class_and_method/README.md#built-in-mrbgems)).
- Affected: the default builds of 2.7.2. Their binaries have the `Redis`
  class again, so code that refers to `Redis` no longer raises
  `NameError`. Their build clones three more repositories from GitHub:
  matsumotory/mruby-redis, and matsumotory/mruby-pointer, which
  mruby-redis depends on and which adds no class, at the heads of their
  `master` branches, and the hiredis tag `v1.5.0`. It links hiredis
  statically into nginx or into
  the dynamic module, which grows by about 190 KB: a stripped static
  nginx built as `test/build_release.sh` builds it, on Linux aarch64 with
  gcc 11.4, grows from 3.88 MB to 4.08 MB. Only a script that calls
  `Redis` needs a Redis server. The change of hiredis affects the default
  builds of 2.7.2, builds of 2.7.1 that enable mruby-redis, and the
  default builds of 2.7.0 and earlier, whose default `build_config.rb`
  includes the gem. When they clone the gem after the merge, they get
  hiredis v1.5.0 instead of the head of the default branch of hiredis, and
  on macOS instead of v0.13.3. mruby-redis#108 tested the gem with mruby
  3.3.0, which 2.6.0 to 2.7.2 bundle, and with mruby 4.0.0; 2.5.0 and
  earlier bundle older mruby releases. The gem links hiredis statically, so a binary built before
  keeps its hiredis until it is built again after `mruby/build` is
  removed. A build of 2.7.1 with the default `build_config.rb` is not
  affected, because it does not include the gem.
- What to do: nothing for the default build of 2.7.2, unless this source
  tree built mruby-redis before, in a build that enabled it or in the
  default build of 2.7.0 or earlier: then remove `mruby/build` first.
  Then build as before: the warning of entry 1 of the 2.7.1 notes ("The
  build of that gem can fail ...") no longer applies. To build without the
  gem, as the default build of 2.7.1 did, comment out
  `conf.gem github: 'matsumotory/mruby-redis'` in `build_config.rb`. To
  build with another hiredis release, set the environment variable
  `MRUBY_REDIS_HIREDIS_VERSION` to its tag when you build, or set
  `ENV['MRUBY_REDIS_HIREDIS_VERSION']` in `build_config.rb` (see the
  [README of mruby-redis](https://github.com/matsumotory/mruby-redis#readme)).
  The build does not check the commit of another tag. mruby-redis#108 also
  built and tested `v1.4.1`, on its earlier head 2cc63c1 with gcc and mruby
  3.3.0.
- Not changed by this release: as in 2.7.0 and in builds of 2.7.1 that
  enable the gem, each call of `Redis` waits in the worker until the Redis
  server answers, because the gem uses the blocking API of hiredis, so the
  worker serves no other request meanwhile. `Redis#ttl`, whose declaration
  mruby-redis#108 changed for mruby 4.0.0, behaves as before with the
  bundled mruby 3.3.0.
- Tests: the test suite of ngx_mruby has no test that calls Redis, and it
  starts no Redis server. Its default build builds the gem since #604,
  so every CI cell builds the gem and links hiredis, the cell with the
  sanitizers included, and the test nginx has the `Redis` class. #604
  quotes the suite on `master` with the static and the dynamic module and
  with the sanitizers, the symbols of the gem and of hiredis in the nginx
  binary, and a request that calls Redis without and with a running Redis
  server. mruby-redis#108 quotes the suite of
  ngx_mruby `master` (03aad7031) and `next` (75bfa6ff4), each built with the
  gem enabled at the head of that pull request, and both pass. The CI of
  the gem runs its tests on Ubuntu 22.04 and on Ubuntu 24.04, the latter
  with the sanitizer settings of ngx_mruby's CI.

## New features

None.

## Fixes

- When nginx has no value for a variable that `Nginx::Var` reads, for
  example `$realpath_root` in a location whose root does not exist, the line
  that `Nginx::Var` writes to `error.log` (`<name> is NULL`) ends the name of
  the variable at its last character. Before, the line could carry the bytes
  that followed the name in memory ([#589](https://github.com/matsumotory/ngx_mruby/pull/589)).

## Build and test changes

- `test.sh`: the HTTP test servers also listen on 18153, for
  `test/t/cases/var_input.rb` ([#589](https://github.com/matsumotory/ngx_mruby/pull/589)).
- `test.sh`: instead of sleeping for `NGINX_HEATTIME` seconds before the
  first request, `test.sh` waits until the test nginx accepts connections on
  every port of the `listen` directives in `test/conf/nginx.conf` and
  `test/conf/conf.d/*.conf`, and prints how long that took. A CI cell under
  valgrind had failed with `Errno::ECONNREFUSED`, because nginx was still
  reading its configuration when the 10 seconds of the sleep had passed
  ([#564](https://github.com/matsumotory/ngx_mruby/pull/564#issuecomment-5977252444)). `NGINX_HEATTIME` is now the upper bound of the wait, 60
  seconds by default; it was the length of the sleep, 2 seconds by default
  and 10 in CI, and CI no longer sets it. The run fails, and names the ports
  that still refuse connections, when nginx does not listen within the bound
  or ends before it listens. Before it starts nginx, `test.sh` also waits
  until no process accepts connections on those ports. "Waiting for nginx to
  listen" in `docs/test/README.md` describes the wait ([#593](https://github.com/matsumotory/ngx_mruby/pull/593)).

## Upgrading

Supported nginx versions: the nginx mainline and stable lines (see
[README.md](../../README.md)); CI builds nginx 1.31.6, 1.30.5, 1.28.3 and
1.26.3.

- No directive was added, renamed or removed. Rebuild the module with this
  release the way you built 2.7.1, and replace the binary or the dynamic
  module as usual.

Check these before upgrading. Each line is the "What to do" of its entry
above.

- `Nginx::Var` with a name built at run time: check the name before the
  call, or rescue `NoMethodError` where the name can be empty, and pass a
  value to each setter (entry 1).
- `Nginx::Var#set`: nothing, unless the code relied on `set` lowercasing the
  name; such code calls `downcase` on the name itself (entry 2).
- mruby-redis, which the default build includes again: nothing, unless
  this source tree built it before; then remove `mruby/build` first. The
  build gets hiredis v1.5.0, and the warning of entry 1 of the 2.7.1 notes
  no longer applies. To build without the gem, comment out its line in
  `build_config.rb`. Set the environment variable
  `MRUBY_REDIS_HIREDIS_VERSION` to build another hiredis tag (entry 3).
