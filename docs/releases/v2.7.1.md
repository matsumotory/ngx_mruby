# ngx_mruby v2.7.1

## Behavior changes: read before upgrading

### The default build no longer includes mruby-redis (#528)

- Before: the default `build_config.rb` included `matsumotory/mruby-redis`, so
  Ruby code could use the `Redis` class.
- Now: the line is commented out in the default `build_config.rb`. In a module
  built from it, `Redis` is not defined, and code that uses it raises
  `NameError`.
- Affected: scripts that use `Redis`, in a module built with the default
  `build_config.rb`.
- What to do: if your scripts use `Redis`, build with a `build_config.rb` that
  includes `conf.gem github: 'matsumotory/mruby-redis'`. The comment in the
  default `build_config.rb` gives the reason it was disabled: the gem's build
  clones hiredis without a pinned version, and that clone failed to build in
  CI.

### A handler that resumes after `Nginx::Async.sleep` no longer sets the variable of an earlier `mruby_set` (#548)

- Before: when a handler other than `mruby_set` or `mruby_set_code` resumed
  after `Nginx::Async.sleep`, its last expression was assigned to the variable
  of an earlier `mruby_set` or `mruby_set_code` of the same request, a
  server-level `mruby_set_code` included.
- Now: only an `mruby_set` or `mruby_set_code` whose own code slept assigns its
  result to its variable. A later handler that sleeps leaves the variable as it
  was.
- Affected: requests in which `mruby_set` or `mruby_set_code` sets a variable
  and a later handler of the same request calls `Nginx::Async.sleep`, and
  everything that reads that variable afterwards (other directives,
  `log_format`, a content handler).
- What to do: nothing, unless a configuration relied on the variable being
  overwritten. Such a configuration should set the variable explicitly in the
  handler that sleeps, for example with `Nginx::Var#set`.

### An exception after `Nginx::Async.sleep` or `Nginx::Async::HTTP.sub_request` resumes the handler now answers 500 (#550)

- Before: when a handler raised after one of these calls returned, the client
  got one of the following, depending on the handler: no response (the
  connection closed with 0 bytes); the status the handler had set before the
  exception, for example 503 from `Nginx.return`; 200 with the output of
  `Nginx.rputs` so far; or, after a server-level handler that had returned
  `Nginx::DECLINED`, the normal response of the next phases, for example a
  static file with 200. When the response had already been started, by the
  content handler that runs while `mruby_set_code` waits or by the location
  that `Nginx.redirect` ran, the client got that response.
- Now: the client gets nginx's 500 page, and the output of `Nginx.rputs` before
  the exception is dropped. When the response has already been started, the 500
  cannot be sent: nginx logs `[alert] header already sent` in `error.log` and
  terminates the request, and the client can get no response at all (0 bytes).
  A handler that raises without calling these methods behaves as before.
- Affected: handlers that call `Nginx::Async.sleep` or
  `Nginx::Async::HTTP.sub_request` and can raise after the call returns.
- What to do: rescue exceptions after these calls in the handler when the
  client should get something other than 500. Do not raise after
  `Nginx.redirect`, or in an `mruby_set_code` whose location has a content
  handler that answers while it waits; `[alert] header already sent` in
  `error.log` shows where that happens.

### After `Nginx.redirect` in a resumed handler, nginx closes the connection once the target has answered (#550)

- Before: when a handler called `Nginx.redirect` to a local URI after
  `Nginx::Async.sleep` or `Nginx::Async::HTTP.sub_request`, and then raised or
  called `Nginx.return` with a status, the connection stayed open after the
  target's response. With HTTP/1.1 keep-alive, a request pipelined behind it
  got 500 after an exception, or no response until the client closed the
  connection after `Nginx.return`.
- Now: nginx closes the connection right after the target's response, also
  when that response says `Connection: keep-alive`, and logs
  `[alert] header already sent`. A request pipelined behind it gets no
  response, and the client has to send it again on a new connection.
- Affected: handlers that call `Nginx.redirect` after one of these calls and
  then raise or call `Nginx.return` with a status, and HTTP/1.1 clients that
  send more requests on that connection.
- What to do: after `Nginx.redirect`, end the handler without raising and
  without `Nginx.return`: the redirect target answers the request.

### `Nginx::Async.sleep` and `Nginx::Async::HTTP.sub_request` raise `RuntimeError` in log handlers and output filters (#551)

- Before: in a log handler, a sleep left a timer on the freed request, which
  could crash the worker, and a `sub_request` started the subrequest. In an
  output header or body filter, a sleep made the filter stop at that point and
  the response went out unfiltered with status 200; a `sub_request` in a header
  filter started the subrequest, and the response went out unfiltered with
  status 200. A direct `Fiber.yield` in these handlers stopped the handler
  without an error line.
- Now: both methods raise `RuntimeError` before they do anything, with a
  message that names the handler, for example
  `Nginx::Async.sleep is not available in a log handler`. The exception is
  handled like any exception in a handler: `error.log` gets an `[error]` line,
  and a filter ends the request with status 500 (in the tested configuration
  the client gets status 500 with the unfiltered body). A direct `Fiber.yield`
  in these handlers also ends the handler with an `[error]` line, and in a
  filter with status 500.
- Affected: `mruby_log_handler`, `mruby_log_handler_code`,
  `mruby_output_header_filter`, `mruby_output_header_filter_code`,
  `mruby_output_body_filter` and `mruby_output_body_filter_code` code that
  calls these methods or `Fiber.yield`.
- What to do: remove these calls from log handlers and output filters. Wait or
  make the subrequest in a rewrite or access handler, and pass the result to
  the filter or the log handler in a variable.

## Fixes

- nginx starts with a configuration that has no `http {}` block, for example a
  stream-only configuration. Before, the worker crashed at start (#536).
- The stream module frees the compiler context of a directive that a later
  directive of the same kind replaces (#540).
- Each async fiber is registered in the GC root once and released when its
  request ends. Before, every `Nginx::Async::HTTP.sub_request` that raised
  kept its fiber alive until the worker exited. When the memory for the fiber
  cannot be allocated, a phase handler now fails the request with 500 (#547).
- After an exception in a resumed handler, the next request on the same worker
  no longer fails with 500 because of the earlier exception (#550).
- `Nginx::Async::HTTP.sub_request` to a location whose handler waits in
  `Nginx::Async.sleep` completes. Before, the client got no response until
  `send_timeout` or until it closed the connection (#550).

## Build and test changes

- `nginx_version`, the nginx that `build.sh` and `test.sh` download by
  default, is 1.31.6 (v2.7.0: 1.27.2) (#528, #529).
- CI tests nginx 1.31.6, 1.30.5, 1.28.3 and 1.26.3 (v2.7.0: 1.27.2 and
  1.26.2) (#528, #529).
- `test.sh` compares nginx versions correctly. Before, it checked the minor
  and the patch number separately (#529).
- CI runs on pull requests, has a `ci-ok` check and a job built with
  AddressSanitizer and UndefinedBehaviorSanitizer, and Dependabot updates the
  GitHub Actions (#530, #541).
- A workflow mirrors `master` to `v2.x` until v3 is promoted (#532).
- `test.sh` runs the case files in `test/t/cases/`, and its HTTP test ports
  moved from 58xxx to 18xxx; `AGENTS.md` lists them (#544). CI reserves the
  test ports so that other connections on the runner cannot take them (#538).
  The SSL tests read only the validity lines of the certificate (#535).

## Upgrading

- nginx: CI tests 1.31.6, 1.30.5, 1.28.3 and 1.26.3. `build.sh` builds nginx
  1.31.6 unless `NGINX_SRC_ENV` points to another nginx source tree.
- Rebuild the module, static or dynamic, against your nginx. The bundled mruby
  is unchanged.
- Check the changes above:
  - if your scripts use `Redis`, build with a `build_config.rb` that includes
    mruby-redis (#528);
  - if a configuration relied on a later handler overwriting an `mruby_set`
    variable after a sleep, set the variable explicitly (#548);
  - rescue exceptions after `Nginx::Async.sleep` and
    `Nginx::Async::HTTP.sub_request` when 500 is not the response you want,
    and do not raise after `Nginx.redirect` (#550);
  - after `Nginx.redirect`, do not raise or call `Nginx.return` (#550);
  - remove `Nginx::Async.sleep`, `Nginx::Async::HTTP.sub_request` and
    `Fiber.yield` from log handlers and output filters (#551).
