# ngx_mruby v2.7.7

## Behavior changes: read before upgrading

### The line of `error.log` for an exception whose class redefines `inspect` or `backtrace` (#803)

- Before: when Ruby code raised an exception whose class redefines `inspect` in Ruby, ngx_mruby wrote no line for the exception to `error.log`, whatever the redefined method did. ngx_mruby called the method while the exception was still pending in the mruby state, and the bundled mruby then returns the pending exception instead of the result of the method, so the result was never a String. In a build with `--with-debug`, a redefined `backtrace` gave the same exception, and ngx_mruby wrote `backtrace must be Array. mrb_type=18` at the debug level and no frame. When such an `inspect` or `backtrace` raised in the content handler of a location that `Nginx.redirect` ran from an `mruby_set` handler, the exception went on to the `mruby_set` handler, which logged it in place of the original exception. nginx then answered 404 from the static files of the target location instead of 500, and did not finish the request: the connection stayed open until the client gave up.
- Now: ngx_mruby calls `inspect` and `backtrace` with the pending exception set aside, and stops an exception that they raise in the logging. When `inspect` returns a String, the line has that String, as for an exception whose class does not redefine it. When `inspect` raises, the line has `#<Class> (inspect raised Class)`, with the class of the exception and the class of the exception of `inspect`; when it returns another value, the line has `#<Class> (inspect did not return a String)`. In a build with `--with-debug`, the String elements of the result of a redefined `backtrace` are logged, one line each, and its other elements are skipped; a `backtrace` that raises or does not return an Array is logged at the debug level as before. The request ends with its 500 or its aborted session also inside another mruby call, and the worker goes on to the next request.
- Why it changed:
  - The defect: the call of `inspect` and `backtrace` ran while the exception was pending, so a redefined method could not give its result, and an exception of the method was not stopped in the logging. Inside another mruby call it left the request unfinished. The same calls are fixed on `next` by #796 and #799; this pull request brings the fix to 2.x.
  - Why the old behavior could not be kept: an exception that leaves the logging past the nginx functions of the request keeps the request and its connection open, and an exception that writes no line leaves the operator without the error. The class name in place of an `inspect` that cannot give a String is the line that 3.x writes for the same exception, so 2.x and 3.x write the same line.
  - What the documentation promised: the documentation said nothing about exceptions whose class redefines `inspect` or `backtrace`.
- Affected: scripts of every kind of handler (HTTP and stream, and the code that runs when nginx reads the configuration or a worker starts or exits) that raise an exception whose class redefines `inspect` or `backtrace` in Ruby. An exception whose class does not redefine them gets the same line as before, byte for byte.
- What to do: nothing, unless you parse `error.log` for these exceptions: the line now exists, with the text of the redefined `inspect` or the class name.

## New features

None.

## Fixes

- When the class of an exception redefines `inspect` or `backtrace` and the method raises in the content handler of a location that `Nginx.redirect` runs from an `mruby_set` handler, nginx now finishes the request with 500. Before, the exception went on to the `mruby_set` handler, nginx answered 404, and the connection stayed open until the client gave up (#803)
- In a build with `--with-debug`, an element of the result of a redefined `backtrace` that is not a String is skipped. Before, ngx_mruby read every element as a String (#803)

## Build and test changes
