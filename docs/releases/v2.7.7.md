# ngx_mruby v2.7.7

## Behavior changes: read before upgrading

### The line of `error.log` for an exception whose class redefines `inspect` or `backtrace` (#803)

- Before: when Ruby code raised an exception whose class redefines `inspect` in Ruby, ngx_mruby wrote no line for the exception to `error.log`, whatever the redefined method did. ngx_mruby called the method while the exception was still pending in the mruby state. In that state the bundled mruby does not run the method to its end: it goes on with the pending exception, so neither the String that the method would return nor an exception of the method itself reached ngx_mruby. In a build with `--with-debug`, a `backtrace` redefined in Ruby went the same way, and ngx_mruby wrote `backtrace must be Array. mrb_type=18` at the debug level and no frame. In the content handler of a location that `Nginx.redirect` ran from an `mruby_set` handler, this left the request unfinished, whatever the redefined `inspect` did, or in a build with `--with-debug` the redefined `backtrace`, also when it returned a String or an Array: the pending exception went on to the `mruby_set` handler, past the nginx functions in between. The `mruby_set` handler logged that exception again, which for a redefined `inspect` again wrote no line of the exception, and for a redefined `backtrace` wrote the line of the exception a second time and no frame. nginx then answered 404 from the static files of the target location instead of 500, and the connection stayed open until the client gave up.
- Now: ngx_mruby calls `inspect` and `backtrace` with the pending exception set aside, and stops an exception that they raise in the logging. When `inspect` returns a String, the line has that String, as for an exception whose class does not redefine it. When `inspect` raises, the line has `#<Class> (inspect raised Class)`, with the class of the exception and the class of the exception of `inspect`; when it returns another value, the line has `#<Class> (inspect did not return a String)`. In a build with `--with-debug`, the String elements of the result of a redefined `backtrace` are logged, one line each, and its other elements are skipped; a `backtrace` that raises or does not return an Array is logged at the debug level as before. Inside another mruby call, the request ends with 500 as it does directly under nginx, and the worker goes on to the next request.
- Why it changed:
  - The defect: `inspect` and `backtrace` were called while the exception was pending, so a method written in Ruby never gave its result. Inside another mruby call, the pending exception left the logging and the request unfinished, whatever the method did. The same calls are fixed on `next` by #796 and #799; this pull request brings the fix to 2.x.
  - Why the old behavior could not be kept: when an exception leaves the logging and jumps past the nginx functions that handle the request, the request and its connection stay open. When no line of the exception is written, the operator cannot learn from the log that the error happened. The class name in place of an `inspect` that cannot give a String is the line that 3.x writes for the same exception, so 2.x and 3.x write the same line.
  - What the documentation promised: the documentation said nothing about exceptions whose class redefines `inspect` or `backtrace`.
- Affected: scripts of every kind of handler (HTTP and stream, and the code that runs when nginx reads the configuration or a worker starts or exits) that raise an exception whose class redefines `inspect` or `backtrace` in Ruby. An exception whose class does not redefine them gets the same line as before, byte for byte.
- What to do: nothing, unless you parse `error.log` for these exceptions: the line now exists, with the text of the redefined `inspect` or the class name.

## New features

None.

## Fixes

- When the class of an exception redefines `inspect` (or, in a build with `--with-debug`, `backtrace`) in Ruby and the exception is raised in the content handler of a location that `Nginx.redirect` runs from an `mruby_set` handler, nginx now finishes the request with 500, whatever the method does. Before, the exception went on to the `mruby_set` handler, nginx answered 404, and the connection stayed open until the client gave up (#803)
- In a build with `--with-debug`, an element of the result of a redefined `backtrace` that is not a String is skipped, as on 3.x. Before, the code read every element as a String without checking its type (#803)
