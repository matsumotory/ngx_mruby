# ngx_mruby v2.7.5

## Behavior changes: read before upgrading

### A rewrite or access handler that returns Nginx::DECLINED after Nginx::Async.sleep no longer makes a later handler answer 500 (#740)

- Before: when a rewrite handler (`mruby_rewrite_handler`, `mruby_rewrite_handler_code`) or an access handler (`mruby_access_handler`, `mruby_access_handler_code`) returned `Nginx::DECLINED` with `Nginx.return` after `Nginx::Async.sleep`, the request went on to the next phase with its status set to 500. A later mruby handler of the request that set no status and wrote no output then answered 500: for example an access handler after the rewrite handler, also in a location that serves a static file, or a content handler without output after the access handler. Without such a later mruby handler, nginx answered as usual, because its own handlers set their status: a static file was served with 200.
- Now: the request goes on to the next phase as it does when the handler declines without a sleep, and a later mruby handler that sets no status answers as it does then, not with 500: after a rewrite handler, the content handler answers with its output, and nginx serves the static file of the location with 200.
- Why it changed:
  - The defect: the code that resumes a handler after its sleep set the status of the request to 500 for every result other than `Nginx::OK`, also for `Nginx::DECLINED`, with which the request goes on. This was reported by mail.
  - Why the old behavior could not be kept: a handler declines to let the later handlers answer; the 500 that it left made them answer an error that no handler had set.
  - What the documentation promised: [Nginx::Async#sleep](https://github.com/matsumotory/ngx_mruby/blob/v2.7.4/docs/class_and_method/README.md#nginxasyncsleepmsec) of 2.7.4 said that the sleep is supported in rewrite and access handlers, and said nothing about a status after it.
- Affected: rewrite and access handlers that call `Nginx::Async.sleep` and then return `Nginx::DECLINED`, in locations where a later mruby handler of the request sets no status and writes no output.
- What to do: nothing. A configuration that relied on the 500 returns that status from a handler with `Nginx.return`.

### A HEAD response with an output body filter keeps its connection available

- Before: a HEAD request to a location with `mruby_output_body_filter` or `mruby_output_body_filter_code`, whose response had a known content length, received its response headers, but nginx then closed the connection even when the headers advertised keep-alive. A following GET on that connection received no response. This occurred with both empty and nonempty replacement bodies.
- Now: for those responses, after the HEAD headers are sent successfully, the filter sends no body bytes and leaves an otherwise reusable connection available for the next request. GET responses, other header-only responses and header-filter errors keep their behavior.
- Why it changed:
  - The defect: the body-filter finalizer returned `NGX_ERROR` after a successful header-only response. nginx treated that return as an output error and closed the connection. The [review of #574](https://github.com/matsumotory/ngx_mruby/pull/574#issuecomment-6166201549) recorded the HEAD case, and [the review of #628](https://github.com/matsumotory/ngx_mruby/pull/628#issuecomment-6488574325) confirmed it with a following GET.
  - Why the old behavior could not be kept: a successfully sent HEAD response did not represent an output error, and closing the connection prevented the next request advertised by keep-alive.
  - What the documentation promised: [Nginx::Filter#body=](https://github.com/matsumotory/ngx_mruby/blob/v2.7.4/docs/class_and_method/README.md#nginxfilterbodystring) described replacement bodies and their content length, but did not describe a HEAD connection-close exception.
- Affected: HEAD responses with a known content length that are finalized by an mruby output body filter, when the connection can otherwise be kept alive.
- What to do: nothing. To close a connection deliberately, configure nginx's keep-alive policy rather than relying on this filter error.

## Build and test changes

- CI: a pull request to `master` runs no job of `site-v2.yml`, which built the 2.x pages of the site with the pull request's `docs/`. Its author checks the 2.x pages locally: the relative links of the Markdown files with `check_links.py` of `next`, and the 2.x pages built from the pull request with `NGX_MRUBY_V2_TREE=DIR npm run check:ci` in `site/` of `next`. `site-v2.yml` runs only on "Run workflow". Every push to `master` still starts `site.yml` on `next` through `site-dispatch.yml`, which builds and checks `/v2/` from the new `master` before it deploys the site. When the base of a pull request moves, CI runs again only when both the pull request and the new commits of the base change the code or the tests (condition 2 of "Review and merge" in [AGENTS.md](../../AGENTS.md); "The 2.x pages of the site" in [docs/test/README.md](../test/README.md)) (#739)
- New test case: `test/t/cases/async_rewrite_declined.rb`, with the server of `test/conf/conf.d/82-async-rewrite-declined.conf` on port 18187 (#740)

- New regression case: `test/t/cases/head_body_filter.rb` sends HEAD and then GET on one TCP connection, covering both output origins, an empty replacement and ordinary HEAD/GET controls.
