# ngx_mruby v2.7.5

## Behavior changes: read before upgrading

### A rewrite handler that returns Nginx::DECLINED after Nginx::Async.sleep no longer makes a later handler answer 500 (#740)

- Before: when a rewrite handler (`mruby_rewrite_handler`, `mruby_rewrite_handler_code`) returned `Nginx::DECLINED` with `Nginx.return` after `Nginx::Async.sleep`, the request went on to the next phase with its status set to 500. A later mruby handler that set no status, for example an access handler, then answered 500, and so did a static file that the location would serve.
- Now: the request goes on to the next phase as it does when the rewrite handler declines without a sleep. A later handler that sets no status does not answer 500: a content handler answers with its output, and nginx serves the static file with 200.
- Why it changed:
  - The defect: the code that resumes a handler after its sleep set the status of the request to 500 for every result other than `Nginx::OK`, also for `Nginx::DECLINED`, with which the request goes on. This was reported by mail.
  - Why the old behavior could not be kept: a rewrite handler declines to let the later phases answer; the 500 that it left made them answer an error that no handler had set.
  - What the documentation promised: [Nginx::Async#sleep](https://github.com/matsumotory/ngx_mruby/blob/v2.7.4/docs/class_and_method/README.md#nginxasyncsleepmsec) of 2.7.4 said that the sleep is supported in rewrite handlers, and said nothing about a status after it.
- Affected: rewrite handlers that call `Nginx::Async.sleep` and then return `Nginx::DECLINED`, and the locations where a later mruby handler sets no status or nginx serves a static file.
- What to do: nothing. A configuration that relied on the 500 returns that status from a handler with `Nginx.return`.
