# ngx_mruby v3.0.0

## Behavior changes: read before upgrading

### A content handler that ends without output answers 200 with an empty body instead of 500 (#574)

- Before: on 2.7.1, a content handler on the main request that ended without output (it wrote nothing, or only `""` or `nil` with `Nginx.rputs`, or only set response headers) got 500 with nginx's error page (or the `error_page` configured for 500) and `Connection: close` when it set no status, `Nginx::HTTP_OK` (with `Nginx.return`, `Nginx.send_header` or `Nginx.status_code=`) or another status below 300 other than 201 and 204 (for example `Nginx::HTTP_ACCEPTED`), also after `Nginx::Async::HTTP.sub_request` resumed it (#566). error.log got a line at the `error` level: `status code is 200, but response body is empty. return NGX_HTTP_INTERNAL_SERVER_ERROR`, `status code is not set, and response body is empty. return NGX_HTTP_INTERNAL_SERVER_ERROR` or `status code is <N>, but response body is empty. return NGX_HTTP_INTERNAL_SERVER_ERROR`. On 2.7.0 and earlier, `Nginx::HTTP_OK` without output got the same 500, and the other cases got no response at all: nginx closed an HTTP/1.0 connection without sending a byte and kept a keep-alive connection open without a response until `keepalive_timeout`.
- Now: such a handler answers as nginx's own `return 200;` does: with the status it set, 200 when it set none, `Content-Length: 0` and an empty body. nginx keeps a keep-alive connection for the next request, a HEAD request gets the same header, and the header filters and body filters of the location (`mruby_output_header_filter`, `mruby_output_body_filter` and their `_code` forms) run on the empty response. error.log gets none of the lines above for it.
- Affected: `mruby_content_handler` and `mruby_content_handler_code` handlers that can end without output, for example a handler that writes only when a condition holds, one that passes a value that can be empty or `nil` to `Nginx.rputs`, one that only sets response headers, and one that ends with `Nginx.return Nginx::HTTP_OK` and no body. Unchanged: a status below 200 without output (500 and the `status code is <N>, but response body is empty` line, as on 2.7.1), 201, 204 and the statuses from 300 up (nginx answers them), handlers with output, `Nginx.redirect`, the other handlers (`Nginx.return Nginx::HTTP_OK` without output in a rewrite or access handler still answers 500 and logs `status code is 200, but response body is empty`), and subrequests (`Nginx::Async::HTTP.sub_request`, SSI includes and `auth_request`): the content handler of a subrequest that returns `Nginx::HTTP_OK` without output still sets the subrequest's status to 500, and one that writes nothing and sets no status still ends the subrequest without a response body and without a status.
- What to do: nothing for most configurations: a handler that should answer with an empty body may now return `Nginx::HTTP_OK`. A script that relied on the 500 to signal that it had nothing to send must set that status itself, for example `Nginx.return Nginx::HTTP_INTERNAL_SERVER_ERROR` or `Nginx.return Nginx::HTTP_NOT_FOUND`, which nginx answers as before. Log monitoring that matches `response body is empty. return NGX_HTTP_INTERNAL_SERVER_ERROR` finds only the statuses below 200 of content handlers, and `Nginx::HTTP_OK` in the other handlers and in subrequests. Why the behavior changes: nginx answers `return 200;` with a 200 and an empty body, and an empty body is a valid response for 200; answering it with 500 was a defect of the 2.x line (#200), which 2.7.1 kept because the 2.x line keeps compatibility ([v2.7.1.md](v2.7.1.md)). v3 follows nginx (section 7, item 8 of [docs/proposals/v3-plan.md](../proposals/v3-plan.md)).

### An output body filter that ends with an empty body sends the response instead of closing the connection (#574)

- Before: when an output body filter (`mruby_output_body_filter`, `mruby_output_body_filter_code`) ended with an empty body, because it set `""` with `Nginx::Filter#body=` or `Nginx::Filter#output`, or because the response had no body and the filter left it empty, nginx logged `zero size buf in writer` at the `alert` level and closed the connection before it wrote the status line: the client received no byte. This holds on 2.7.1 and on earlier releases.
- Now: the response is sent with its status, `Content-Length: 0` and an empty body, and error.log gets no `alert` line for it.
- Affected: locations with an output body filter that can end with an empty body, including a location whose content handler ends without output (the entry above): without this change, such a location would send no response at all instead of the empty 200.
- What to do: nothing. Why the behavior changes: a response that is never sent is a defect. The body filter now passes an empty last buffer the way nginx's own `return 200;` does (`ngx_http_send_response`), and the empty 200 of the entry above needs it.

## Upgrading

Supported nginx versions: the nginx mainline and stable lines (see
[README.md](../../README.md)). Rebuild the module with this release. Read
the "Behavior changes" sections of the 2.x release notes newer than the
version you run first, then check these:

- A content handler that relied on the 500 for a response without output: set the status it means, for example `Nginx::HTTP_INTERNAL_SERVER_ERROR` (#574).
- Log monitoring that matches `response body is empty. return NGX_HTTP_INTERNAL_SERVER_ERROR` no longer sees content handlers of the main request that end without output and with no status or a 2xx status (#574).
