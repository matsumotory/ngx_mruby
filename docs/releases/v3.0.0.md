# ngx_mruby v3.0.0

## Behavior changes: read before upgrading

### The local start example binds to loopback and adds mock model routing (#672)

- Before: `examples/start/compose.yaml` published host port 8080 on all interfaces, and the trial demonstrated only the `/hello` Ruby handler.
- Now: the host binding is `127.0.0.1:8080:8080`. The trial retains `/hello` and adds `/v1/responses`, which checks a public demonstration key and selects one of two loopback mock endpoints by model. The bilingual walkthrough checks route selection, credential replacement, rejected requests, editing, restoration and reload.
- Why it changed:
  - The reason: the first exercise should demonstrate the model-routing use case without a provider account or real key.
  - Why the old behavior could not be kept: exposing the trial on every host interface is unnecessary for a local-only exercise; `/hello` remains available.
  - What the documentation promised: [the earlier start page](https://github.com/matsumotory/ngx_mruby/blob/9221ea4ed2b513eb083d55195b0004db5cacc968/examples/start/README.md) showed a Hello response and explained that the host port was broadly published.
- Affected: users running the development example from `examples/start/`; no runtime API or stable 2.x configuration is changed.
- What to do: run the updated walkthrough locally. The bundled keys are demonstration values, and the mock response is not LLM inference, a provider compatibility test or API-format conversion. Do not publish this trial as a service.

### The bundled mruby is 4.1.0-rc2 instead of 3.3.0 (#561, #678)

- Before: ngx_mruby 2.x bundles mruby 3.3.0 and builds the core gems that `full-core.gembox` of mruby 3.3.0 selects, mruby-print included.
- Now: this release bundles mruby 4.1.0-rc2, a release candidate of 4.1.0: the tag `4.1.0-rc2` of mruby (commit `c17ffcc24190`, 2026-09-11), whose `MRUBY_VERSION` is `4.1.0`. The default `build_config.rb` takes the core gems that `NGX_MRUBY_CORE_GEMS` names: the set that `full-core.gembox` of mruby 3.3.0 selected, without mruby-print (mruby 3.4 removed it; `Kernel#print`, `#puts` and `#p` come from mruby-io). It leaves out these core gems, which `full-core.gembox` of 4.1.0-rc2 takes: mruby-task, mruby-encoding, mruby-strftime (`Time#strftime`) and mruby-benchmark (`Benchmark`), and the gems that are new in 4.1, mruby-env, mruby-process, mruby-regexp, mruby-signal, mruby-string-bitops and mruby-bin-mrb. `ENV`, `Process` and `Regexp` still come from the third-party gems iij/mruby-env, iij/mruby-process and mattn/mruby-onig-regexp. It keeps mruby-sleep, which `full-core.gembox` leaves out. mruby 4.1 compiles Ruby code with Prism. The line that nginx logs at the `info` level when it reads the configuration ends in `(mruby/4.1.0) mechanism enabled`. The entries below list the differences that scripts, log monitoring, C extensions and builds see, as far as they were found and measured for ngx_mruby: they are not a complete list of the changes between mruby 3.3.0 and 4.1.0-rc2. mruby lists its user-visible changes in [`doc/mruby3.4.md`](https://github.com/mruby/mruby/blob/4.1.0-rc2/doc/mruby3.4.md), [`doc/mruby4.0.md`](https://github.com/mruby/mruby/blob/4.1.0-rc2/doc/mruby4.0.md) and, for 4.1, [`NEWS.md`](https://github.com/mruby/mruby/blob/4.1.0-rc2/NEWS.md). The cost per request, measured for ngx_mruby against the bundled mruby 4.0.0 (the callgrind lane, user-space instructions of nginx per request, 2026-10-31, #678): in `auth` (a server rewrite handler with two Hash lookups and three variable assignments, then a proxy), 44228 → 52761 instructions, 42599 → 45621 without the GC; in `headers`, 30040 → 34903, and 28044 → 27612 without the GC. At 3 GHz and 1 to 2 instructions per cycle, an instruction takes 0.17 to 0.33 ns, so `auth` takes about 7.4 to 14.7 µs of CPU per request with 4.0.0 and 8.8 to 17.6 µs with 4.1.0-rc2 (+1.4 to +2.8 µs), and at 10,000 requests per second it uses 8.8% to 17.6% of a core instead of 7.4% to 14.7%. The GC runs more often and does more each time: in `auth`, 12.2 → 24.4 GC calls per 1000 requests, 134,000 → 293,000 instructions per call. mruby 4.1 runs a full GC instead of adding a heap page when its last mark left room (mruby commit c009f1633, which bounds the heap of small targets), and its VM spends more instructions on the same bytecode ("Known differences" under "Performance comparison with callgrind" in [docs/test/README.md](../test/README.md)).
- Why it changed:
  - The reason: the v3 plan puts stability, performance and current dependencies before new capabilities, and mruby publishes no maintenance releases of 3.x (`docs/proposals/v3-plan.md`, sections 3.3 and 6). Decision 1 of the plan (section 7) sets mruby 4.1.0 as the mruby of v3, because 4.1 counts the registrations of `mrb_gc_register()`: a second `mrb_gc_unregister()` of an object no longer drops the registration of another owner (mruby/mruby#7277), and `Nginx::Async` registers its fibers this way. The owner chose on 2026-10-29 to bundle 4.1.0-rc2 instead of waiting for the tag `4.1.0`; `next` moves to 4.1.0 when it is tagged. 4.1.0-rc2 has the fix of mruby/mruby#7032 (commit `c6866eed4`).
  - Why the old behavior could not be kept: mruby 3.3.0 gets no more fixes. The `NEWS.md` of 4.1 alone has 20 entries under "Security Fixes" since 4.0, among them a use-after-free in `String#lstrip!`, `#rstrip!` and `#strip!` and one in the incremental GC; keeping 3.3.0 would have kept such defects in every worker.
  - What the documentation promised: the documentation of 2.x said nothing about which version of mruby a later release bundles. [docs/install/README.md](https://github.com/matsumotory/ngx_mruby/blob/v2.7.0/docs/install/README.md#2-configuring-mrbgems) of 2.7.0 lists the default mrbgems as "mruby/mruby default mrbgems" without a version.
- Affected: every build of the module, and every Ruby script that it runs.
- What to do: rebuild the module together with the bundled mruby, then check the entries below and, for the changes that they do not cover, mruby's three lists; [Migrating from ngx_mruby 2.x to 3.0.0](../migration/README.md) has the steps. ngx_mruby keeps mruby's GC defaults: `GC.interval_ratio` did not change the GC share, and a larger heap lowered it but raised the work without the GC.

### A `build_config.rb` of your own needs the core gem changes of mruby 4.1 (#561, #678)

- Before: a `build_config.rb` of your own could name mruby-print, or take `full-core.gembox` and get the core gems of mruby 3.3.0, mruby-sleep included.
- Now: mruby 4.1.0-rc2 has no mruby-print and no hal-* gems, and `ngx_mruby_core_gems` in `build_config.rb` stops the build on a name that the bundled mruby does not have. A list written for mruby 4.0.0 that names hal-posix-io, hal-posix-dir and hal-posix-socket stops there too: in 4.1 the POSIX back ends are part of mruby-io, mruby-dir and mruby-socket. `full-core.gembox` of 4.1.0-rc2 takes mruby-task, which redefines `Kernel#sleep`, arms a SIGALRM interval timer (`setitimer`) in every process that opens an mrb_state and allows at most 8 mrb_states (`MRB_TASK_MAX_VMS`), and mruby-encoding (see the entry of `String#valid_encoding?`), and leaves out mruby-sleep. It also takes mruby-env, mruby-process and mruby-regexp, which define `ENV`, `Process` and `Regexp`, the classes that iij/mruby-env, iij/mruby-process and mattn/mruby-onig-regexp define; the two gems of iij have the same names as these core gems. `for_windows?` in `mruby/lib/mruby/gem.rb` treats a one-letter directory at the root as a Windows drive: a 4.0.0 build whose work directory was mounted at `/s` in a container chose the Windows back ends by itself and stopped at `windows.h: No such file or directory`, and the `for_windows?` of 4.1.0-rc2 makes the same test (read from the source, not measured).
- Why it changed:
  - The reason: these are changes of mruby 3.4, 4.0 and 4.1 that come with the bundled mruby (see the entry above).
  - Why the old behavior could not be kept: a core gem that the bundled mruby no longer has cannot be built, and `ngx_mruby_core_gems` stops on such a name on purpose, so that an update of mruby cannot drop a gem from the list unnoticed.
  - What the documentation promised: [docs/install/README.md](https://github.com/matsumotory/ngx_mruby/blob/v2.7.0/docs/install/README.md#2-configuring-mrbgems) of 2.7.0 lists "mruby/mruby default mrbgems" and says nothing about core gems in a `build_config.rb` of your own.
- Affected: builds with a `build_config.rb` other than the one of this release that name mruby-print or the hal-* gems, or take `full-core.gembox`.
- What to do: start from the `build_config.rb` of this release, or select the core gems by name as `NGX_MRUBY_CORE_GEMS` does: remove mruby-print, hal-posix-io, hal-posix-dir and hal-posix-socket, and decide on mruby-task and mruby-encoding as [Core gems](../install/README.md#core-gems) describes. A build that takes `full-core.gembox` and also iij/mruby-env, iij/mruby-process or mattn/mruby-onig-regexp chooses between them and the core gems mruby-env, mruby-process and mruby-regexp.

### Building the bundled mruby needs Ruby 3.0 or later (#678)

- Before: the rake of mruby 3.3.0, which 2.x bundles, builds with Ruby 2.x: its `mrbc` builds with Ruby 2.6.10 (the Ruby of macOS).
- Now: the rake of mruby 4.1.0-rc2 stops while it links `mrbc` when it runs on Ruby 2.6.10, with `ArgumentError: unknown keywords: flags, flags_before_libraries, flags_after_libraries, libs, outfile, objs` (`mruby/lib/mruby/build/command.rb`, line 47). It builds with Ruby 3.0.2 (Ubuntu 22.04, the Ruby of CI and of the test container) and with Ruby 4.0.5. `Command::Linker#run` passes the parameters of the link as a Hash to `_run(options, params={}, chdir: nil)`, and a Ruby before 3.0 reads a last Hash with Symbol keys as keyword arguments when the method takes keywords. Ruby 2.7 was not measured; by that rule it stops in the same way. mruby's own `doc/guides/compile.md` still says "Ruby 2.5 or later".
- Why it changed:
  - The reason: the build of mruby 4.1 changed (see "The bundled mruby is 4.1.0-rc2 instead of 3.3.0"); this release bundles mruby 4.1.0-rc2.
  - Why the old behavior could not be kept: keeping Ruby 2.x would have meant changing `mruby/`, which ngx_mruby updates only from mruby's own tree.
  - What the documentation promised: [docs/install/README.md](https://github.com/matsumotory/ngx_mruby/blob/v2.7.0/docs/install/README.md) of 2.7.0 asks for Ruby with rake and names no version.
- Affected: builds that run on Ruby 2.x, for example the `ruby` package of Ubuntu 20.04 (2.7) or the Ruby of macOS (2.6).
- What to do: build with Ruby 3.0 or later; for a version-managed Ruby, put its `bin` directory on `PATH` before the build.

### The third-party mrbgems are built at the commits that `build_config.rb.lock` records (#558)

- Before: `build_config.rb` names the third-party mrbgems without a commit, and `.gitignore` lists the `build_config.rb.lock` that mruby's rake writes, so the lock stays out of the repository. A build from a new checkout or a source archive clones the head of each gem's branch with `git clone --depth 1`, so two builds of the same ngx_mruby commit made on different days can get different gem code.
- Now: `build_config.rb.lock` is committed. It records a commit for each third-party gem of the default build and for each gem that those depend on, for example ksss/mruby-stringio, which the bundled rack-based-api needs. A build from a new checkout or a source archive clones each of them with its whole history and checks the recorded commit out, so every build of an ngx_mruby commit gets the same gem code. A gem that a `build_config.rb` of your own adds is cloned at the head of its branch, and rake adds its entry to the lock in your tree, which `git status` then shows as modified. rake does not fetch into a clone that exists: after a change of the lock, a build in a tree that keeps `mruby/build` stops with `fatal: reference is not a tree` when a clone does not have the new commit. symisc/vedis, which matsumotory/mruby-vedis clones by itself, is not pinned.
- Why it changed:
  - The reason: the v3 plan pins every third-party gem by commit and commits `build_config.rb.lock`, so that the same tag builds the same binary (`docs/proposals/v3-plan.md`, section 4, Pillar A).
  - Why the old behavior could not be kept: without the pins, the gem code of a build depends on the day of the build. A change in any of the gem repositories reaches every later build of a released tag, and every CI run, without a change in ngx_mruby.
  - What the documentation promised: the documentation of 2.x said nothing about the commits of the third-party gems. [docs/install/README.md](https://github.com/matsumotory/ngx_mruby/blob/v2.7.0/docs/install/README.md#2-configuring-mrbgems) lists the default mrbgems by name only.
- Affected: builds from source that expect the newest commits of the third-party gems, `build_config.rb` files of your own that add gems, and trees that keep `mruby/build` when the lock changes.
- What to do: nothing for a new checkout or a source archive. To build a gem at another commit, change its entry in the lock as [Gem commits](../install/README.md#gem-commits-build_configrblock) describes. After a change of the lock, for example one that a pull brings in, remove `mruby/build` before the next build.

### `Hash#inspect` and `Hash#to_s` use a new format (#561)

- Before: `{"a"=>1}` and `{:a=>1}`.
- Now: `{"a" => 1}` and `{a: 1}` (since mruby 3.4). Everything that prints a Hash with these methods changes with them: string interpolation (`"#{h}"`), `sprintf("%s", h)` and `Array#inspect`.
- Affected: scripts that put the `inspect` or `to_s` of a Hash into a response body or a header, or compare it with a fixed string. The test suite of ngx_mruby saw the change (`/async_http_sub_request` in `test/t/ngx_mruby.rb`).
- What to do: do not use the `inspect` or `to_s` of a Hash as a data format, in a response body or in a header. Build the string yourself, or use `JSON.generate`.

### `Exception#inspect`, and so the `mrb_run failed` lines of `error.log`, use a new format (#561)

- Before: `boom (RuntimeError)`. ngx_mruby writes the exception of a script with `Exception#inspect` into the `mrb_run failed` lines of `error.log` (level `error`; the line that an exception in `mruby_stream_server_context_code` logs while nginx reads the configuration, `mrb_run failed: ngx_mruby stream module configuration failed: error: ...`, is at level `emerg`), for example `mrb_run failed: return 500 HTTP status code to client: error: boom (RuntimeError)`.
- Now: `#<RuntimeError: boom>`, so the line ends in `error: #<RuntimeError: boom>`. `Exception#message` and `#to_s` are unchanged.
- Affected: log parsers and alerts that match the old form, and scripts that use `Exception#inspect`. The test suite of ngx_mruby saw the change in `error.log`.
- What to do: update log parsers and alerts that match the old form.

### The messages logged while nginx reads the configuration are at the `info` level instead of `notice` (#565)

- Before: while nginx reads the configuration, ngx_mruby logs these messages at the `notice` level: `ngx_mruby/<version> (mruby/<version>) mechanism enabled`, once for the `http {}` block; `ngx_mruby NOTICE ...: compile info: ...` for each directive with Ruby code, and `ngx_mruby-stream-module NOTICE ...: compile info: ...` for each one in `stream {}`; and `ngx_mruby NOTICE ...: target variable=(...)` for each `mruby_set` and `mruby_set_code`. nginx writes what it logs while it reads the configuration to its startup log, at the `notice` level whatever `error_log` says, so every start of nginx writes these lines, also with `error_log ... warn;`.
- Now: the same messages are logged at the `info` level, and their text says `INFO` instead of `NOTICE` (`ngx_mruby INFO ...`, `ngx_mruby-stream-module INFO ...`). A start of nginx writes none of them. `nginx -t` writes them at `[info]` to the startup log only: nginx copies a line of the startup log to the terminal only at `warn` and above, so the output of `nginx -t` does not show them. A reload writes them to the `error_log` of the running configuration when that `error_log` is at `info` or `debug`. Errors while nginx reads the configuration, such as a script file that cannot be opened, are still logged at `emerg`.
- Why it changed:
  - The defect: every start of nginx wrote these lines, and an `error_log` at a level above `notice` did not stop them (#320).
  - Why the old behavior could not be kept: nginx writes what it logs while it reads the configuration to its startup log at the `notice` level, before the configured `error_log` takes over, so no `error_log` setting filters a message at `notice`. Only a level below `notice` keeps the lines out of a start.
  - What the documentation promised: the documentation of 2.x said nothing about these messages.
- Affected: log monitoring and scripts that look for these lines when nginx starts, for example to see that the module is loaded.
- What to do: to see them, run `nginx -t -e stderr`, which writes the startup log to the terminal; read the startup log after `nginx -t`; or reload with `error_log` at `info`. The startup log is the file given with `-e`, or else the error log path compiled into nginx (`logs/error.log` under the prefix by default), as [Messages logged while nginx reads the configuration](../directives/README.md#messages-logged-while-nginx-reads-the-configuration) describes.

### The message of `NoMethodError` names the class of the receiver (#561)

- Before: `undefined method 'foo'`.
- Now: `undefined method 'foo' for NilClass`.
- Affected: scripts and log monitoring that match the message of a `NoMethodError`.
- What to do: match on the exception class, not on the message.

### `private` and `protected` are enforced (#561, #678)

- Before: not enforced: a method defined after `private` or `protected`, `initialize`, a method defined with `def` at the top level, and the `Kernel` methods could be called with an explicit receiver, `Kernel` itself included (`Kernel.Integer("12")` is `12`). `Module#instance_methods` and `#methods` of an object list private methods too: for a class with a method `pub` and a private method `priv`, `instance_methods(false)` is `[:priv, :pub]`.
- Now: enforced (since mruby 3.4): these methods raise `NoMethodError` (`private method '<name>' called for <class>`) when called with an explicit receiver other than `self`. This includes the `Kernel` methods such as `raise`, `sprintf`, `puts`, `Integer` and `rand` called on another object (`1.Integer("3")` raises `private method 'Integer' called for Integer`), and `initialize_copy`, `respond_to_missing?` and `method_missing`, which mruby 4 defines as private (`"a".initialize_copy("b")` raises). Called on `Kernel` itself, the methods of `Kernel` work as on 2.x (`Kernel.Integer("12")` is `12`; mruby 4.0.0 raised `NoMethodError` there, and 4.1 calls them again, mruby/mruby#6976). A `protected` method can be called with an explicit receiver from a method of the same class, as in CRuby, and raises `NoMethodError` (`protected method '<name>' called for <class>`) from anywhere else. `respond_to?` returns `true` for a private method on both versions, so it does not tell whether such a call works. `Module#instance_methods` and `#methods` of an object leave private methods out (`instance_methods(false)` of the class above is `[:pub]`); `Module#private_instance_methods` and `#private_methods` list them. In handler code, a method defined with `def` at the top level stays public, so a call of it with an explicit receiver still works ([the proposal for #502](../proposals/archive/handler-code-frame.md#14-what-handler-code-shares-today), section 1.4).
- Why it changed:
  - The reason: mruby 3.4 enforces the visibility of methods as CRuby does, and mruby 4.1 checks the receiver of a `protected` method against the class of the caller's `self` (mruby/mruby#6975, commit 534efe0 in mruby's `NEWS.md`); this release bundles mruby 4.1.0-rc2 (see "The bundled mruby is 4.1.0-rc2 instead of 3.3.0").
  - Why the old behavior could not be kept: the VM of the bundled mruby checks the visibility; ngx_mruby has no option to turn the check off.
  - What the documentation promised: the documentation of 2.x said nothing about the visibility of methods.
- Affected: scripts that call such a method with an explicit receiver other than `self` and `Kernel`, and scripts that look for private methods in the result of `instance_methods` or `methods`.
- What to do: call them without a receiver, or with `send` (`obj.send(:name)` works on both versions). To list private methods, use `private_instance_methods` or `private_methods`.

### `Module#remove_const`, `#private`, `#public`, `#protected`, `#module_function` and the hooks are private (#561)

- Before: public: `Foo.remove_const(:X)`, `M.included(Foo)`, `M.prepended(Foo)` and `obj.singleton_method_added(:m)` work. The hooks are `#included`, `#extended`, `#prepended`, `#inherited` and `#method_added` of `Module` and `Class`, and `BasicObject#singleton_method_added`.
- Now: private: called with an explicit receiver, they raise `NoMethodError: private method ... called`. `send` works, and mruby still calls the hooks itself: `prepend` calls `prepended`, and `def obj.m` calls `singleton_method_added`.
- Affected: scripts that call one of these methods with an explicit receiver.
- What to do: call them in the body of the class or module without a receiver, or with `send` (`Foo.send(:remove_const, :X)`).

### Overrides of `append_features`, `prepend_features` and `extend_object` are not called (#561)

- Before: `include`, `prepend` and `extend` call these three methods, so a module can override them.
- Now: the three methods are gone (`Module.new.respond_to?(:append_features, true)` is `false`, and the same for the other two). `include`, `prepend` and `extend` add the module without calling them, so an override is skipped without an error. The hooks `included`, `prepended` and `extended` are still called.
- Affected: modules that override one of the three methods.
- What to do: move the code to `included`, `prepended` or `extended`.

### `allbits?`, `anybits?` and `nobits?` are methods of `Integer` only (#561)

- Before: methods of `Numeric`, so they work on a Float (`1.5.allbits?(1)` is `true`).
- Now: methods of `Integer` only; on a Float they raise `NoMethodError`. On an Integer they work as before (`6.allbits?(2)` is `true`).
- Affected: scripts that call them on a Float.
- What to do: convert a Float with `to_i` first.

### `FileTest` is a module (#561)

- Before: `FileTest` is a class.
- Now: `FileTest` is a module. `FileTest.exist?` and its other methods are called as before.
- Affected: scripts that use `FileTest` as a class, other than by calling its methods.
- What to do: nothing for calls of its methods.

### Assigning a constant in a method body is a `SyntaxError` (#561)

- Before: allowed (`def m; X = 1; end`).
- Now: `SyntaxError` (`syntax error, dynamic constant assignment`), when the script is compiled.
- Affected: scripts that assign a constant inside a method body. The Rack-style `Kernel#run` of ngx_mruby sets `Server` with `Kernel.const_set`.
- What to do: use `Object.const_set(:X, 1)` (or `Kernel.const_set`).

### `"#@ivar"`, `"#@@cvar"` and `"#$global"` in a string interpolate the variable (#678)

- Before: in a double-quoted string, a heredoc or a backquoted command, `#` followed by `@`, `@@` or `$` and a name is plain text: `@x = 5; "a#@x"` is `"a#@x"`.
- Now: they interpolate the variable, as in CRuby: `"a#@x"` is `"a5"`, `"#$gv"` is the value of `$gv`, and an instance variable that is not set gives an empty string (`"a#@nope"` is `"a"`). `#{...}` works as before (since mruby 4.1, [d4aad5d](https://github.com/mruby/mruby/commit/d4aad5d)).
- Why it changed:
  - The reason: mruby 4.1 adds this form of interpolation (see "The bundled mruby is 4.1.0-rc2 instead of 3.3.0"), as CRuby has it.
  - Why the old behavior could not be kept: the compiler of the bundled mruby reads the form; ngx_mruby has no option to turn it off.
  - What the documentation promised: the documentation of 2.x said nothing about it.
- Affected: scripts whose double-quoted strings contain `#@`, `#@@` or `#$` followed by a name, for example a text such as `"Ticket #@id"` or `"price #$total"` meant literally, also in response bodies and headers.
- What to do: find such strings (see [Scripts](../migration/README.md#scripts)) and escape the `#` (`"a\#@x"`) or use a single-quoted string (`'a#@x'`). The string is the same on both versions.

### Syntax errors have the messages of Prism (#678)

- Before: the parser of mruby 3.3.0 gives messages such as `syntax error, unexpected end of file` and `dynamic constant assignment`.
- Now: mruby 4.1 compiles with Prism, and a `SyntaxError` has its messages: `eval("1 +")` raises `SyntaxError` with `syntax error, unexpected end-of-input; expected an expression after the operator`, `eval("foo(")` with ``syntax error, unexpected end-of-input; expected a `)` to close the arguments``, and `eval("x = ")` with ``syntax error, expected an expression after `=` `` (measured with the `mruby` command of the build). The messages that mruby reports when ngx_mruby compiles a script file or inline code that does not parse come from the same compiler.
- Why it changed:
  - The reason: mruby 4.1 replaced its parser generated from `parse.y` with Prism ([`NEWS.md`](https://github.com/mruby/mruby/blob/4.1.0-rc2/NEWS.md), "the compiler is Prism").
  - Why the old behavior could not be kept: the bundled mruby has no other compiler.
  - What the documentation promised: the documentation of 2.x said nothing about the messages of syntax errors.
- Affected: log monitoring and scripts that match the text of a syntax error, for example of `eval` or of a script that nginx fails to load.
- What to do: match on `SyntaxError` and the file and line, not on the text after `syntax error`.

### An `Array`, a `Hash` or a `Struct` that holds itself can be compared (#678)

- Before: `==` and `eql?` of two arrays, hashes or structs that hold themselves recurse without end and raise `SystemStackError`: `a = []; a << a; b = []; b << b; a == b` raises `SystemStackError` (`stack level too deep`).
- Now: such a comparison works as in CRuby. A pair that is already being compared counts as equal, and the other elements decide: `a == b` above is `true`, and with `a = [1]; a << a; b = [2]; b << b`, `a == b` is `false` (since mruby 4.1, mruby/mruby#7425; measured with the `mruby` command of mruby 3.3.0 and of the host build of this release).
- Why it changed:
  - The reason: mruby 4.1 changes `#==` and `#eql?` of `Array`, `Hash` and `Struct` for containers that hold themselves (see "The bundled mruby is 4.1.0-rc2 instead of 3.3.0").
  - Why the old behavior could not be kept: the bundled mruby has only the new methods; ngx_mruby has no option to bring the old ones back.
  - What the documentation promised: the documentation of 2.x said nothing about it.
- Affected: scripts that compare containers that hold themselves and rescue the `SystemStackError`.
- What to do: nothing for most scripts. A script that relies on the `SystemStackError` checks for the container itself before the comparison.

### Float values have no bit operations (#561)

- Before: `~`, `&`, `|` and `^` work on the integer part (`1.5 & 1` is `1`, `~1.5` is `-2`). For a shift count from 1 up, `<<` multiplies the Float by that power of two and truncates (`1.5 << 1` is `3`, `-1.5 << 1` is `-3`, `1.5 << 40` is `1649267441664`), and gives a Float when the result is outside the Integer range (`1.5 << 70` is `1.77088743107612e+21`). For a shift count from 1 to 32, `>>` divides a positive Float by that power of two and truncates (`8.0 >> 1` is `4`, `1.5 >> 1` is `0`), and returns `-1` for every negative Float (`-8.0 >> 1` is `-1`). For a count above 32, `>>` returns `0` for a positive and `-1` for a negative Float (`1e20 >> 32` is `23283064365`, `1e20 >> 33` is `0`). A count of 0 returns the Float unchanged (`-1.5 >> 0` is `-1.5`), and a negative count shifts the other way (`1.5 >> -1` is `3`).
- Now: `~`, `&`, `|`, `^`, `>>` and `<<` raise `NoMethodError` on a Float (mruby 3.4 removed all six).
- Affected: scripts that apply one of the six operators to a Float.
- What to do: for `~`, `&`, `|` and `^`, convert with `to_i` first. For `<<` and `>>`, `to_i` first can give another number (`1.5.to_i << 1` is `2`, `-8.0.to_i >> 1` is `-4`). Where the old number matters: for `<<` by a count from 1 up, multiply the Float by the power of two and call `to_i`; for `>>` by a count from 1 to 32, divide a positive Float by the power of two and call `to_i`, and use `-1` for a negative Float; for `>>` by a count above 32, use `0` for a positive and `-1` for a negative Float (dividing would give another number: `(1e20 / 2**40).to_i` is `90949470`, where `1e20 >> 40` was `0`); for a count of 0, keep the Float.

### `String#valid_encoding?` is not in the default build (#561)

- Before: defined by mruby-string-ext. With the default `build_config.rb`, ngx_mruby 2.x builds mruby without `MRB_UTF8_STRING`, and the method returns `true` for every string, even `"\xfe"`. A build whose `build_config.rb` defines `MRB_UTF8_STRING` gets `false` for a string that is not valid UTF-8.
- Now: since mruby 3.4 only mruby-encoding defines the method, and the default build leaves that gem out, so a call raises `NoMethodError` (`undefined method 'valid_encoding?' for String`) and a handler that calls it answers 500.
- Affected: scripts that call `String#valid_encoding?`.
- What to do: with the default `build_config.rb` of 2.x, drop the call (it never returned `false` there), or build with mruby-encoding and check the scripts as [Core gems](../install/README.md#core-gems) says. A 2.x build that defined `MRB_UTF8_STRING` needs mruby-encoding to keep the check. Why the default build leaves mruby-encoding out: the gem defines `MRB_UTF8_STRING` for the whole build, so `String#size`, `#[]` and `#index` count characters instead of bytes, and a script that computes a `Content-Length` from `String#size` would get another number; the owner decided on 2026-10-04 to leave it out of the default build and keep it opt-in.

### A seeded `Random` gives other numbers (#561)

- Now: another sequence for the same seed: mruby 4.0 uses PCG instead of xoshiro.
- Affected: scripts that depend on the numbers of a seeded generator.
- What to do: do not depend on the numbers of a seeded generator across versions.

### `Set#inspect` and `Set#to_s` use a new format, and `Set#flatten_merge` is removed (#561)

- Before: `#<Set: {1, 2}>`. `Set#flatten_merge` is a public method: `Set.new([1]).flatten_merge(Set.new([2, Set.new([3])]))` is the Set of 1, 2 and 3.
- Now: `Set[1, 2]`. Everything that prints a Set with these methods changes with them: string interpolation (`"#{set}"`), `sprintf("%s", set)` and `Array#inspect`. mruby 4.0.0 removed `Set#flatten_merge`, and a call raises `NoMethodError`; mruby's lists of user-visible changes do not name it.
- Affected: scripts that use the `inspect` or `to_s` of a Set as a data format, or compare it with a fixed string, and scripts that call `Set#flatten_merge`.
- What to do: as for `Hash#inspect`: build the string yourself (`set.to_a.join(",")` gives the same string on both versions). In place of `s.flatten_merge(t)`, call `s.merge(Set.new(t).flatten)`, which gives on both versions the Set that `s.flatten_merge(t)` gave on 2.x, for a Set and for an Array `t`.

### `Hash#default_proc=` raises `TypeError` for an object that is not a Proc (#561)

- Before: accepted.

- Affected: scripts that pass `Hash#default_proc=` an object that is not a Proc.

### `yield` with keyword arguments to a block with keyword parameters works (#561)

- Before: `ArgumentError: missing keyword`.
- Now: the block gets the keyword arguments.
- Affected: scripts that yield keyword arguments to a block that takes keyword parameters, for example a script that rescued the `ArgumentError`.
- What to do: nothing; it is a bug fix of mruby.

### A `return` inside a block or a `for` body of handler code ends the code (#561)

- Before: a `return` inside a block, such as `[0].each do ... end` or `3.times { ... }`, or inside the body of `for`, at the top level of handler code raised `LocalJumpError`, and the handler answered 500 with `mrb_run failed: return 500 HTTP status code to client: error: unexpected return (LocalJumpError)` in `error.log`. A content handler that had written output before it answered 500 as well and did not send that output. 2.7.0 sent that output with 200 and only logged the exception; 2.7.1 changed this for every exception after `Nginx.rputs` ([entry 3 of the 2.7.1 release notes](v2.7.1.md#3-an-exception-after-nginxrputs-answers-500)). The variable of `mruby_set_code` got an empty value. A `return` at the top level of the code, outside a block, ended the code.
- Now: such a `return` ends the code, as a `return` at the top level does. The code after it does not run, and the response is the one that the code set before it: the status that `Nginx.return` set and the output that `Nginx.rputs` wrote. In `mruby_set_code`, the value of a `return` in a block becomes the variable. `error.log` has no line for it.
- Why it changed:
  - The defect: [#502](https://github.com/matsumotory/ngx_mruby/issues/502): the `return` that ends a handler early raised `LocalJumpError` when it was written inside a block or a `for` body, and the handler answered 500 instead of the response that the code had set.
  - Why the old behavior could not be kept: the error came from mruby 3.3.0. ngx_mruby runs handler code in the first frame of a fiber; mruby 3.3.0 refuses that frame as the frame that such a `return` leaves, and mruby 4.0.0 and 4.1.0-rc2 accept it ([section 1.3 of the proposal for the frame of handler code](../proposals/archive/handler-code-frame.md#13-why-502-fails-on-master-and-not-on-next)). Keeping the error would have meant changing the bundled mruby back to the rule of 3.3.0, for a behavior that #502 reports as a defect.
  - What the documentation promised: [docs/class_and_method/README.md](https://github.com/matsumotory/ngx_mruby/blob/v2.7.0/docs/class_and_method/README.md#nginxreturnnginx_status_code) of 2.x says that ngx_mruby supports the `return` statement in handler code and that it returns from the handler, with no exception for a block.
- Affected: handler code with a `return` inside a block or the body of `for` at its top level; a `return` inside a method or a lambda is not affected. Log alerts and scripts that relied on the 500 or on the `LocalJumpError` line are affected as well.
- What to do: nothing. The two ways around it on 2.x, a `return` at the top level of the code and the code in a method or a lambda, work on both versions.
- Not changed by this release: the frame in which handler code runs. `self` is `main`, local variables belong to one run of the code, and constants, globals, instance variables of `main` and methods defined with `def` persist in the worker ([section 1.4 of the proposal](../proposals/archive/handler-code-frame.md#14-what-handler-code-shares-today)).

### A content handler that ends without output answers 200 with an empty body instead of 500 (#574)

- Before: on 2.7.1 and 2.7.2, a content handler on the main request that ended without output (it wrote nothing, or only `""` or `nil` with `Nginx.rputs`, or only set response headers) got 500 with nginx's error page (or the `error_page` configured for 500) and `Connection: close` when it set no status, `Nginx::HTTP_OK` (with `Nginx.return`, `Nginx.send_header` or `Nginx.status_code=`) or another status below 300 other than 201 and 204 (for example `Nginx::HTTP_ACCEPTED`), also after `Nginx::Async::HTTP.sub_request` resumed it ([entry 13 of the 2.7.1 release notes](v2.7.1.md#13-a-content-handler-that-ends-without-output-answers-500)). error.log got a line at the `error` level: `status code is 200, but response body is empty. return NGX_HTTP_INTERNAL_SERVER_ERROR`, `status code is not set, and response body is empty. return NGX_HTTP_INTERNAL_SERVER_ERROR` or `status code is <N>, but response body is empty. return NGX_HTTP_INTERNAL_SERVER_ERROR`. On 2.7.0 and earlier, `Nginx::HTTP_OK` without output got the same 500, and the other cases got no response at all: nginx closed an HTTP/1.0 connection without sending a byte and kept a keep-alive connection open without a response until `keepalive_timeout`.
- Now: such a handler answers as nginx's own `return 200;` does: with the status it set, 200 when it set none, `Content-Length: 0` and an empty body. It sends no `Content-Type`, as ngx_mruby's answers with output do not; nginx's `return 200;` sends the one of `default_type`. A HEAD request gets the same header. The header filters and body filters of the location (`mruby_output_header_filter`, `mruby_output_body_filter` and their `_code` forms) run on the empty response. The empty answer discards an unread request body first, as the answer with output does since 2.7.1 ([entry 12 of the 2.7.1 release notes](v2.7.1.md#12-an-unread-request-body-is-discarded-before-the-answer)), so the next request on a kept connection is the one that the client sent after the body. nginx keeps a keep-alive connection for the next request, with one exception: after a HEAD request to a location with an mruby output body filter, nginx sends the header and closes the connection, as it does there for a handler with output on 2.7.1 and on this release. error.log gets none of the lines above for it.
- Why it changed:
  - The defect: [#200](https://github.com/matsumotory/ngx_mruby/issues/200): a content handler that ended with `Nginx.return Nginx::HTTP_OK` and no body answered 500, where nginx's own `return 200;` answers 200 with an empty body. HTTP allows that response: "a 200 response is expected to contain message content unless the message framing explicitly indicates that the content has zero length" ([RFC 9110, section 15.3.1](https://www.rfc-editor.org/rfc/rfc9110#section-15.3.1)), which `Content-Length: 0` does. 2.7.1 gave the same 500 to no status and to the other statuses below 300 that nginx does not answer by itself, because those requests had got no response at all ([#566](https://github.com/matsumotory/ngx_mruby/pull/566)).
  - Why the old behavior could not be kept: with the 500, a content handler cannot answer 200 with an empty body at all; the only empty answer that it can choose is 204, which is another status for clients and caches. The v3 plan accepts the empty 200 as a behavior change of v3 (section 7, item 8 of [docs/proposals/v3-plan.md](../proposals/v3-plan.md)); the 2.x line keeps the 500 because it puts compatibility first.
  - What the documentation promised: the documentation of 2.7.1 described the old behavior: a content handler that ends without output answers 500, and an empty body takes `Nginx::HTTP_NO_CONTENT` ([Nginx.return of 2.7.1](https://github.com/matsumotory/ngx_mruby/blob/v2.7.1/docs/class_and_method/README.md#nginxreturnnginx_status_code)). Before 2.7.1, it said only that `Nginx.return` "Returns nginx status code to send back HTTP status to the client" ([Nginx.return of 2.7.0](https://github.com/matsumotory/ngx_mruby/blob/v2.7.0/docs/class_and_method/README.md#nginxreturnnginx_status_code)).
- Affected: `mruby_content_handler` and `mruby_content_handler_code` handlers that can end without output, for example a handler that writes only when a condition holds, one that passes a value that can be empty or `nil` to `Nginx.rputs`, one that only sets response headers, and one that ends with `Nginx.return Nginx::HTTP_OK` and no body, and log monitoring of the lines above. Unchanged: a status below 200 without output (500 and the `status code is <N>, but response body is empty` line, as on 2.7.1 and 2.7.2), 201, 204 and the statuses from 300 up (nginx answers them), handlers with output, `Nginx.redirect`, the other handlers (`Nginx.return Nginx::HTTP_OK` without output in a rewrite or access handler still answers 500 and logs `status code is 200, but response body is empty`), and subrequests (`Nginx::Async::HTTP.sub_request`, SSI includes and `auth_request`): the content handler of a subrequest that returns `Nginx::HTTP_OK` without output still sets the subrequest's status to 500, and one that writes nothing and sets no status still ends the subrequest without a response body and without a status.
- What to do: nothing for most configurations: a handler that should answer with an empty body may now return `Nginx::HTTP_OK`. A script that relied on the 500 to signal that it had nothing to send must set that status itself, for example `Nginx.return Nginx::HTTP_INTERNAL_SERVER_ERROR` or `Nginx.return Nginx::HTTP_NOT_FOUND`, which nginx answers as before. Log monitoring that matches `response body is empty. return NGX_HTTP_INTERNAL_SERVER_ERROR` finds only the statuses below 200 of content handlers, and `Nginx::HTTP_OK` in the other handlers and in subrequests.
- Tests: port 18136 (`test/conf/conf.d/54-content-empty-body.conf`, `test/t/cases/content_empty_body.rb`, with two `POST` requests whose body the handler does not read on one connection), and the cases "Nginx.return 200 dont have body" of `test/t/ngx_mruby.rb` and "send_header 200 without a body answers 200 with an empty body" of `test/t/cases/request_api.rb`.

### An output body filter that ends with an empty body sends the response instead of closing the connection (#574)

- Before: when an output body filter (`mruby_output_body_filter`, `mruby_output_body_filter_code`) ended with an empty body, because it set `""` with `Nginx::Filter#body=` or `Nginx::Filter#output`, or because the response had no body and the filter left it empty, nginx logged `zero size buf in writer` at the `alert` level and closed the connection before it wrote the status line: the client received no byte. This holds on 2.7.2, 2.7.1 and earlier releases.
- Now: the response is sent with its status, `Content-Length: 0` and an empty body, and error.log gets no `alert` line for it.
- Why it changed:
  - The defect: the body filter passed on the empty body as a buffer of zero bytes marked as being in memory, which nginx's writer rejects (`zero size buf in writer`), so the response was never sent. nginx's own `return 200;` passes an empty last buffer that is not marked so (`ngx_http_send_response`). The 2.x line has this defect up to 2.7.2: `test/t/cases/filter_connection.rb` of 2.7.1 records it as the behavior of 2.x ("an empty String closes the connection without a response"). 2.7.3 fixes it on the 2.x line in the same way ([entry 8 of the 2.7.3 release notes](v2.7.3.md#8-an-output-body-filter-can-send-an-empty-body-664)).
  - Why the old behavior could not be kept: a response that is never sent leaves the client without an answer. The empty 200 of the entry above also passes through the body filter of its location, so without this change such a location would send no response at all instead of the empty 200.
  - What the documentation promised: [Nginx::Filter#body= of 2.7.1](https://github.com/matsumotory/ngx_mruby/blob/v2.7.1/docs/class_and_method/README.md#nginxfilterbodystring) says that the response is sent with exactly the body that the filter sets, and that `Content-Length` is its length, with no exception for an empty String.
- Affected: locations with an output body filter that can end with an empty body, including a location whose content handler ends without output (the entry above), and log monitoring of the `zero size buf in writer` line, which these responses no longer log.
- What to do: nothing.
- Tests: port 18112 (`test/t/cases/filter_connection.rb`, "an empty String sends the status with Content-Length: 0") and the locations with a body filter on port 18136 (`test/t/cases/content_empty_body.rb`).

### The accessors of `Nginx::Var` become methods of `Nginx::Var` at their first use in a worker (#610)

- Before: every `v.NAME` and `v.NAME = value` on an `Nginx::Var` went through `Nginx::Var#method_missing`. `Nginx::Var` had three methods of its own, `method_missing`, `exist?` and `set`: `v.respond_to?(:request_method)` returned `false`, and `Nginx::Var.instance_methods(false)` listed only those three. When a script defined a method on `Object` or `Kernel` whose name was also the name of a variable, for example with a `def` at the top level of handler code, `v.NAME` called that method instead of reading the variable.
- Now: the first `v.NAME` or `v.NAME = value` of a name in a worker process also defines `NAME` or `NAME=` as a method of `Nginx::Var`, and the later accesses of the name in that worker call the method. The method reads and writes the variable as `method_missing` does: the values, `nil` for a name that is not a variable, the exceptions and the lines of `error.log` are the same. A worker defines a getter and a setter for each declared variable that scripts use (the variables of nginx and its modules, and the ones that `set` declares), and a getter for the first 16 names of prefix variables that scripts use, such as `arg_q` or `http_x_request_id`. A name gets a method only when it is made of `a` to `z`, `0` to `9` and `_`, with `=` at the end for a setter; `v.Request_Method` keeps reading `$request_method` through `method_missing`. A name that is not a variable, a setter of a prefix variable, an instance of a subclass of `Nginx::Var`, a frozen `Nginx::Var`, and a name that `Nginx::Var` or one of its ancestors already has as a method get no method. After the first access, `v.respond_to?(:NAME)`, `v.methods`, `Nginx::Var.instance_methods(false)` and `Nginx::Var.method_defined?(:NAME)` show the method. What they show depends on the requests that the worker has served, so two workers can answer differently. Once the method exists, a method of the same name that a script defines later on `Object` or `Kernel` no longer hides the variable from `v.NAME`.
- Why it changed:
  - The reason: with mruby 4.0.0, the lookup of a method name that no class defines compares the name with every method of `Nginx::Var`, `Object`, `Kernel` and `BasicObject`, more than 110 entries, and mruby does not cache a name that it did not find. Each `v.NAME` paid that search before `method_missing` ran. In the callgrind comparison of #561, the search made 74% of the difference of the `var` scenario and 59% of that of the `auth` scenario against mruby 3.3.0 ([section 1.1 of the proposal](../proposals/archive/nginx-var-method-lookup.md#11-what-the-comparison-of-561-counts)). A method of the name is found in mruby's method cache instead.
  - Why the old behavior could not be kept: mruby's method cache answers only for a method that the lookup found, so a change that lets `v.NAME` skip the search has to define a method, and introspection shows it. The other ways of the proposal leave the scripts as they are written today on the slow path, or wait for a release of mruby ([section 2 of the proposal](../proposals/archive/nginx-var-method-lookup.md#2-candidates)). The owner accepted the change to introspection as a behavior change of 3.0.0 on 2026-10-15, and confirmed it on 2026-10-19 ([the status of the proposal](../proposals/archive/nginx-var-method-lookup.md)).
  - What the documentation promised: [the Nginx::Var class of 2.7.1](https://github.com/matsumotory/ngx_mruby/blob/v2.7.1/docs/class_and_method/README.md#nginxvar-class) says that `Nginx::Var#method_missing` is called when `Nginx::Var#VARNAME` or `Nginx::Var#VARNAME=` is evaluated. It said nothing about `respond_to?` or the methods of `Nginx::Var`.
- Affected: scripts that call `respond_to?`, `methods`, `instance_methods` or `method_defined?` on `Nginx::Var` or its instances, for example to tell whether a name is a variable, scripts that define a method on `Object` or `Kernel` with the name of a variable that they also read with `v.NAME`, and scripts that wrap `Nginx::Var#method_missing`, for example with a module prepended to `Nginx::Var` whose `method_missing` calls `super`: the wrapper runs only for the first access of a name that gets a method.
- What to do: use `v.exist?(name)` to tell whether a variable exists. Give the methods of your scripts names that are not names of nginx variables.
- Tests: port 18159 (`test/conf/conf.d/68-var-accessor.conf`, `test/t/cases/var_method_lookup.rb`).

### `Nginx::Connection`, `Nginx::Server` and `Nginx::Request` read their variables without calling `Nginx::Var` (#610)

- Before: `Nginx::Connection#remote_ip`, `#remote_port`, `#local_ip` and `#local_port`, `Nginx::Server#document_root`, `#realpath_root` and `#path`, and `Nginx::Request#hostname`, `#authority`, `#filename`, `#user` and `#get_body` called the accessor of their variable (`remote_addr`, `remote_port`, `server_addr`, `server_port`, `document_root`, `realpath_root`, `host`, `http_host`, `request_filename`, `remote_user` and `request_body`) on an `Nginx::Var` that the object created and kept in its instance variable `@iv_var`. A script that defined such a method on `Nginx::Var`, defined a `method_missing` of its own there, or put another object in `@iv_var`, changed what these methods returned.
- Now: these methods read the variable from nginx in C. They return the value that nginx has for the variable, whatever methods a script defines on `Nginx::Var`, and they neither create an `Nginx::Var` nor set `@iv_var`. `Nginx::Request#var` still creates the `Nginx::Var` of the object and keeps it in `@iv_var`. Outside a request they raise the same `RuntimeError` as before.
- Why it changed:
  - The reason: the names of these variables are fixed, and "Design principles" in `AGENTS.md` asks that nothing fixed is looked up or allocated per request when it can be prepared once at initialization. The Ruby call looked the method up on `Nginx::Var` on each call, which takes the search of the entry above, and each object created an `Nginx::Var` and looked up its class. The names and their hash keys are now prepared once ([candidate (d) of the proposal](../proposals/archive/nginx-var-method-lookup.md#d-ngx_mrubys-own-methods-read-the-variable-in-c)).
  - Why the old behavior could not be kept: the Ruby call on the object in `@iv_var` is what let a script change the values. Reading the variable without that call removes both the cost and that effect.
  - What the documentation promised: [the Nginx::Connection class of 2.7.1](https://github.com/matsumotory/ngx_mruby/blob/v2.7.1/docs/class_and_method/README.md#nginxconnection-class) says that `remote_ip`, `remote_port`, `local_ip` and `local_port` are the same as the nginx variables `$remote_addr`, `$remote_port`, `$server_addr` and `$server_port`, and [Nginx::Server#realpath_root](https://github.com/matsumotory/ngx_mruby/blob/v2.7.1/docs/class_and_method/README.md#nginxserverrealpath_root) says the same of `$realpath_root`. That is what they return now in every case.
- Affected: scripts that change what these methods return by defining methods on `Nginx::Var`, a `method_missing` of their own on it, or another object in `@iv_var`, and scripts that read `@iv_var` of these objects without calling `Nginx::Request#var` first.
- What to do: to return another value, define the method on `Nginx::Connection`, `Nginx::Server` or `Nginx::Request` itself, or call a method of your own. Read variables with `Nginx::Var` (`Nginx::Request#var`, `Nginx.var` or `Nginx::Var.new`) instead of `@iv_var`.
- Tests: port 18159 (`test/t/cases/var_method_lookup.rb`).

### `Dir` comes from mruby's core gem, and a closed `Dir` raises `IOError` instead of `RuntimeError` (#559)

- Before: `Dir` comes from iij/mruby-dir. Reading, iterating or closing a `Dir` that is closed raises `RuntimeError` (`closed directory`), and so does `Dir.open` with a block when the block closes the `Dir`. `Dir#each` and `Dir.foreach` without a block raise `NoMethodError`.
- Now: `Dir` comes from mruby-dir, a core gem of mruby 4 that started from iij/mruby-dir and has every method of it. Reading, iterating or closing a `Dir` that is closed raises `IOError` (`closed directory`). `Dir.open` with a block returns the value of the block also when the block closes the `Dir`. `Dir#each` and `Dir.foreach` without a block return an `Enumerator`. `Dir.foreach` with a block closes the `Dir` that it opened (see "Fixes"), and `Dir` has methods that iij/mruby-dir does not have (see "New features").
- Why it changed:
  - The reason: the v3 plan replaces the third-party gems iij/mruby-env, iij/mruby-process and iij/mruby-dir with core gems of mruby (`docs/proposals/v3-plan.md`, section 4, Pillar A). mruby 4.0.0 had a core gem only for `Dir`; 4.1 also has mruby-env and mruby-process, and replacing the two gems of iij with them is a later change.
  - Why the old behavior could not be kept: the `RuntimeError` comes from iij/mruby-dir, which raises it for a closed directory unless it is compiled with `ENABLE_IO`, and the default build does not define it. Keeping the `RuntimeError` would have meant keeping iij/mruby-dir, which has had no commit since 2018-09-14 and leaves the `Dir` that `Dir.foreach` opens open until the GC frees it.
  - What the documentation promised: [docs/class_and_method/README.md](https://github.com/matsumotory/ngx_mruby/blob/v2.7.0/docs/class_and_method/README.md#built-in-mrbgems) of 2.x lists the `Dir` class among the classes of the default build and links it to iij/mruby-dir, whose README lists the methods and says nothing about the exception for a closed `Dir`.
- Affected: scripts that rescue `RuntimeError` around the methods of a `Dir` that can be closed, or around `Dir.open` with a block that closes the `Dir`. When the `rescue RuntimeError` no longer catches the exception, the handler answers 500 (`mrb_run failed: ... error: #<IOError: closed directory>`).
- What to do: rescue `IOError`. A script that runs on both versions rescues `IOError` and `RuntimeError`, or `StandardError`.

### C extensions: an object of a class not declared `MRB_TT_DATA` cannot wrap C data (#561)

- Before: mruby 3.x did not check a class whose instance type was not set: a gem that wraps a C struct with `Data_Wrap_Struct` or `mrb_data_object_alloc` in an object of its own class got the object.
- Now: mruby 4.0 raises `TypeError: allocation failure of <class>` at the allocation, unless the class is declared with `MRB_SET_INSTANCE_TT(klass, MRB_TT_DATA)`.
- Affected: mrbgems and C extensions that wrap C data in a class without that declaration. matsumotory/mruby-uname at its commits before matsumotory/mruby-uname#1 is one: every method of `Uname` raises `TypeError: allocation failure of Uname`, and a handler that calls one answers 500 (the test suite of ngx_mruby saw it, `test/t/cases/gem_uname.rb`).
- What to do: declare the class with `MRB_SET_INSTANCE_TT(klass, MRB_TT_DATA)`. The default build pins matsumotory/mruby-uname to a commit that does this (see "Build and test changes"); a `build_config.rb` of your own that takes mruby-uname needs that commit or a later one.

### C extensions: mruby checks the argument count of a C method against its spec (#561)

- Before: mruby 3.3 checked the argument count of a C method against the argument spec it was defined with (`MRB_ARGS_REQ(2)` and so on) only when the spec was `MRB_ARGS_NONE()`. For other specs, only `mrb_get_args` checked the arguments, against what it reads.
- Now: mruby 4.0 checks it for every C method before the call: a call with fewer arguments than the spec requires, or, unless the spec has a rest (`MRB_ARGS_REST()`, `MRB_ARGS_ANY()`), more than it allows, raises `ArgumentError`, whatever `mrb_get_args` would accept. A non-empty keyword hash counts as one argument when the spec takes no keywords. A method defined with `MRB_ARGS_REQ(1)` that reads `"o|o"` raises `ArgumentError: wrong number of arguments (given 2, expected 1)` when called with two arguments, and one defined with `MRB_ARGS_REQ(2)` that reads `"S"` raises `(given 1, expected 2)` when called with one; with mruby 3.3 both calls worked.
- Affected: C methods of mrbgems and C extensions whose spec differs from what their `mrb_get_args` reads, in either direction. The C methods of ngx_mruby itself are not affected: for each of the 110 definitions in `src/`, the spec accepts every argument count that its `mrb_get_args` accepts.
- What to do: define the method with the spec that its `mrb_get_args` reads (for `"o|o"`, `MRB_ARGS_ARG(1, 1)`).

### C extensions: renamed headers and functions, and `mrb_open()` on failure (#561)

- Before: `mruby/ext/io.h`, `mrb_alloca()`, `mrb_open_allocf(f, ud)` and `mrb_open_core(f, ud)`, which take an allocator of the type `mrb_allocf` (by default `mrb_default_allocf()`, which a program could redefine), and `mrb_open()` returns `NULL` when a gem initializer fails.
- Now: `mruby/io.h` (there is no `mruby/ext/io.h`), `mrb_temp_alloc()` (`mruby.h` keeps `mrb_alloca()` as a macro for it, "for compatibility"), and no `mrb_open_allocf()`, `mrb_allocf` or `mrb_default_allocf()`: `mrb_open_core()` takes no arguments, and mruby allocates its memory with `mrb_basic_alloc_func(void *ptr, size_t size)`, which a program can define to replace mruby's allocator ([`doc/guides/memory.md`](https://github.com/mruby/mruby/blob/4.1.0-rc2/doc/guides/memory.md) of mruby). `mrb_open()` returns the state with `mrb->exc` set, instead of `NULL`, when a gem initializer fails.
- Affected: C sources of mrbgems and of programs that embed mruby that include `mruby/ext/io.h`, call `mrb_open_allocf()` or call `mrb_open_core()` with arguments (their build stops), that define their own `mrb_default_allocf()` (mruby no longer calls it), or that test the result of `mrb_open()` only for `NULL`. Calls of `mrb_alloca()` still compile.
- What to do: include `mruby/io.h`, call `mrb_temp_alloc()`, call `mrb_open()` instead of `mrb_open_allocf(f, ud)` and `mrb_open_core()` without arguments, define `mrb_basic_alloc_func()` instead of `mrb_default_allocf()` where a program replaces the allocator, and test the result of `mrb_open()` with `MRB_OPEN_FAILURE()` (`mruby.h`), which is true for `NULL` and for a state with `exc` set.

### C extensions: sources that include `mruby.h` need the generated headers (#561)

- Before: `mruby.h` did not include `mruby/presym.h`, so a source that did not use `MRB_SYM()` compiled with `mruby/include` alone; presym could also be turned off (`MRB_NO_PRESYM`). ngx_mruby 2.x compiled its own sources this way: its `config.in` puts only `mruby/src` and `mruby/include` on the include path.
- Now: `mruby.h` includes `mruby/presym.h`, which includes the generated `mruby/presym/id.h` (mruby/mruby#6733), and `MRB_NO_PRESYM` is gone, so every source that includes `mruby.h` needs `build/host/include`. Compiled with `mruby/include` alone, such a source stops with `fatal error: mruby/presym/id.h: No such file or directory`.
- Affected: C sources compiled outside the mruby build that include `mruby.h`, among them the sources of ngx_mruby in a build whose `./configure --with-mruby-incdir` gives a list of directories without that directory.
- What to do: add the `include` directory of the mruby build (`mruby/build/host/include`) to the include path. The build of ngx_mruby does this for its own sources: the default list of `--with-mruby-incdir` is `<mruby_root>/src <mruby_root>/include <mruby_root>/build/host/include` (#559). A list that you give with `--with-mruby-incdir` needs the directory too, because the sources of ngx_mruby include `mruby.h` and `mruby/presym.h` (#572, [3-B. Using Makefile](../install/README.md#3-b-using-makefile)).

### The default build leaves out the auto-ssl mrbgem and the classes that came with it (#556)

- Before: the default `build_config.rb` of 2.x builds the bundled auto-ssl mrbgem (`mrbgems/auto-ssl`, the `Nginx::SSL::ACME` classes) and the gems that it depends on: pyama86/mruby-acme-client, pyama86/mruby-polarssl, matsumotory/mruby-httprequest, matsumotory/mruby-simplehttp, mattn/mruby-http, mattn/mruby-base64, takahashim/mruby-forwardable and iij/mruby-tempfile. Scripts can use what these gems define: `Nginx::SSL::ACME::Client` and `Nginx::SSL::ACME::Dehydrated`; the classes and modules `Acme`, `CustomHttpRequest`, `OpenSSL`, `PolarSSL`, `HttpRequest`, `SimpleHttp`, `HTTP`, `Base64`, `Forwardable`, `FORWARDABLE`, `Tempfile` and `TempfilePath`; and `Dir.tmpdir` and `Dir.mktmpdir`.
- Now: the default build has none of them. The constants are not defined, `Dir.tmpdir` and `Dir.mktmpdir` raise `NoMethodError`, and a handler that uses one of them answers 500 (`mrb_run failed: ... error: #<NameError: uninitialized constant Base64>`). The `Dir` class itself stays. This release has no auto-ssl mrbgem at all (see the next entry).
- Why it changed:
  - The reason: decision 6 of the v3 plan (`docs/proposals/v3-plan.md`, section 7) removes auto-ssl from the default build of v3, to be replaced by nginx-acme and by examples that look certificates up in a store. Its ACME client, `Nginx::SSL::ACME::Client`, speaks ACMEv1, which Let's Encrypt no longer serves (sections 2.2 and 3.4 of the plan).
  - Why the old behavior could not be kept: the gem cannot get a certificate from Let's Encrypt, and it brought into every default build eight third-party gems that no other gem of the default build needs, pyama86/mruby-polarssl under the GPL among them. With mruby 4 the default build would also stop, because pyama86/mruby-polarssl includes `mruby/ext/io.h` (see the next entry).
  - What the documentation promised: [docs/class_and_method/README.md](https://github.com/matsumotory/ngx_mruby/blob/v2.7.0/docs/class_and_method/README.md#auto-ssl-mrbgem) of 2.x calls auto-ssl an optional bundled mrbgem in an early phase of development, without saying whether the default build has it. Its example of `mruby_set_code` under [Nginx::Var Class](https://github.com/matsumotory/ngx_mruby/blob/v2.7.0/docs/class_and_method/README.md#nginxvar-class) calls `Base64.encode`, which the default build had only through auto-ssl.
- Affected: scripts that use one of the constants above, `Dir.tmpdir` or `Dir.mktmpdir` inside nginx.
- What to do: use `[s].pack('m0')` in place of `Base64.encode(s)` and `s.unpack1('m')` in place of `Base64.decode(s)`, both from the core gem mruby-pack, `ENV['TMPDIR'] || '/tmp'` in place of `Dir.tmpdir`, and `Dir.mkdir(path, 0700)` under a name of your own in place of `Dir.mktmpdir`, as [The auto-ssl mrbgem and the classes that came with it](../install/README.md#the-auto-ssl-mrbgem-and-the-classes-that-came-with-it) shows. For the other constants, add the gem that defines them with a `conf.gem` line in a `build_config.rb` of your own; the gems that depend on pyama86/mruby-polarssl do not build with mruby 4. A server that needs `Nginx::SSL::ACME` keeps a 2.x build (see the next entry).

### The auto-ssl mrbgem and `NGX_MRUBY_AUTO_SSL` are removed (#640)

- Before: ngx_mruby 2.x bundles the auto-ssl mrbgem (`mrbgems/auto-ssl`) and takes it in the default build. It defines `Nginx::SSL::ACME::Client`, a client of the ACME protocol, and `Nginx::SSL::ACME::Dehydrated`, helpers for the dehydrated ACME client; `test/conf/auto-ssl/` has example configurations for both.
- Now: this release has no `mrbgems/auto-ssl` and no `test/conf/auto-ssl/`, and `build_config.rb` no longer reads `NGX_MRUBY_AUTO_SSL`, so no build of this release has `Nginx::SSL::ACME`. A build with `NGX_MRUBY_AUTO_SSL=1` in its environment builds the default gems as without it. A script that uses `Nginx::SSL::ACME` raises `NameError`, and its handler answers 500 with a `mrb_run failed` line in `error.log`.
- Why it changed:
  - The reason: decision 6 of the v3 plan (`docs/proposals/v3-plan.md`, section 7) replaces auto-ssl with nginx-acme and with examples that look certificates up in a store, and the gem cannot work with the bundled mruby. It needs pyama86/mruby-polarssl for TLS, a gem that ngx_mruby does not maintain and that has had no commit since 2017-03-03. That gem includes `mruby/ext/io.h`, which mruby 4.0 renamed to `mruby/io.h`, so the mruby build with auto-ssl stops with `fatal error: mruby/ext/io.h: No such file or directory` (#561). Its ACME client, pyama86/mruby-acme-client, speaks ACMEv1, which Let's Encrypt turned off in 2021-06 (sections 2.2 and 3.4 of the plan).
  - Why the old behavior could not be kept: the gem cannot be built with mruby 4 until pyama86/mruby-polarssl changes, and even built it could not get a certificate from Let's Encrypt. Keeping it on `next` would have kept a gem that no build of v3 can use, with an opt-in variable that ends in a stopped build. ngx_mruby 2.x keeps the gem.
  - What the documentation promised: [docs/class_and_method/README.md](https://github.com/matsumotory/ngx_mruby/blob/v2.7.0/docs/class_and_method/README.md#auto-ssl-mrbgem) of 2.x calls auto-ssl an optional bundled mrbgem in an early phase of development and points to the scripts in `mrbgems/auto-ssl/mrblib` for its API. It says nothing about how long the gem is kept.
- Affected: scripts that use `Nginx::SSL::ACME::Client` or `Nginx::SSL::ACME::Dehydrated`, configurations built from the examples in `test/conf/auto-ssl/`, and builds that set `NGX_MRUBY_AUTO_SSL=1`.
- What to do: get certificates from an ACME server with nginx's own module [ngx_http_acme_module](https://nginx.org/en/docs/http/ngx_http_acme_module.html) (nginx-acme), or keep a 2.x build for a server that needs `Nginx::SSL::ACME`; the [documentation of 2.x](https://github.com/matsumotory/ngx_mruby/blob/v2.7.2/docs/class_and_method/README.md#auto-ssl-mrbgem) describes the gem. Remove `NGX_MRUBY_AUTO_SSL` from the environment of your builds: it has no effect.

### `Nginx::Upstream#server=` and `Nginx::Stream::Connection#upstream_server=` raise `ArgumentError` for a string that cannot be a server (#680)

- Before: for an empty string or one of 256 bytes or more, and for a string with a NUL byte (since 2.7.3, entry 9 of [the 2.7.3 release notes](v2.7.3.md)), `Nginx::Upstream#server=` raised `ArgumentError` and `Nginx::Stream::Connection#upstream_server=` raised `RuntimeError`. For a string that nginx could not read as an address, such as `192.0.2.1:notaport`, both raised `RuntimeError`, and so did `upstream_server=` for a host name.
- Now: both raise `ArgumentError` for all of these. The messages stay (`invalid upstream server (empty or too long)`, `invalid upstream server (contains a NUL byte)`, `invalid port in upstream 192.0.2.1:notaport`), except for a host name, whose message is `upstream server NAME is not an IP address or a unix: path`. The server stays as it was, as before. `RuntimeError` is left for a failure of nginx while it reads the string, and for an upstream with a `zone`.
- Why it changed:
  - The reason: the same argument raised different classes in the two setters, and a script could not tell an argument that it can correct from a failure of nginx. The owner decided on this change for v3 ([question 3 of the proposal](../proposals/archive/upstream-server-setters.md#4-questions-for-the-owner-with-recommendations)).
  - Why the old behavior could not be kept: keeping it would leave two rules for one kind of mistake. The 2.x line, which puts compatibility first, keeps them; v3 is the release that can change them.
  - What the documentation promised: [#648](https://github.com/matsumotory/ngx_mruby/pull/648), for 2.7.3, wrote the old classes into `docs/class_and_method/README.md`. The documentation of 2.7.2 said nothing about the exceptions ([`Nginx::Upstream#server=`](https://github.com/matsumotory/ngx_mruby/blob/v2.7.2/docs/class_and_method/README.md#nginxupstreamserverstring), [`Nginx::Stream::Connection#upstream_server=`](https://github.com/matsumotory/ngx_mruby/blob/v2.7.2/docs/class_and_method/README.md#nginxstreamconnectionupstream_server-1)).
- Affected: scripts that rescue `RuntimeError` around `Nginx::Stream::Connection#upstream_server=`, or around `Nginx::Upstream#server=` for a string that nginx cannot read. Such a `rescue` no longer catches the exception, and the handler ends with it: a handler of a request phase answers 500, and `mruby_set` leaves its variable empty. A script that rescues `ArgumentError` around `Nginx::Upstream#server=` now also catches these cases.
- What to do: rescue `ArgumentError`. A script for both versions rescues `ArgumentError` and `RuntimeError`, or `StandardError`.
- Not changed by this release: `TypeError` for an argument that is not a String, and `RuntimeError` for an upstream with a `zone`, which is about the upstream and not about the argument.

### `Nginx::Upstream#server=` raises `ArgumentError` for a host name instead of resolving it (#680)

- Before: `Nginx::Upstream#server=` resolved a host name with the system resolver when it was called and used the first address. The worker served no other client while it waited for the answer. A name that did not resolve raised `RuntimeError` (`host not found in upstream NAME`).
- Now: the method resolves nothing. A string that is not an IP address or a `unix:` path raises `ArgumentError` (`upstream server NAME is not an IP address or a unix: path`), and the server stays as it was. The worker does not wait. `Nginx::Stream::Connection#upstream_server=` already refused a host name.
- Why it changed:
  - The reason: the design principle "No blocking" of [AGENTS.md](../../AGENTS.md#design-principles), which listed this setter among the places that block until this change. The owner decided on this change for v3 ([question 3 of the proposal](../proposals/archive/upstream-server-setters.md#4-questions-for-the-owner-with-recommendations)).
  - Why the old behavior could not be kept: while the resolver answers, every other request of the worker waits, and a slow resolver stops the worker for as long as it takes. Resolving without waiting would need a resolver for scripts, which ngx_mruby does not have.
  - What the documentation promised: [#648](https://github.com/matsumotory/ngx_mruby/pull/648), for 2.7.3, wrote the old behavior into `docs/class_and_method/README.md`, said that the worker waits and said to give an IP address. The [documentation of 2.7.2](https://github.com/matsumotory/ngx_mruby/blob/v2.7.2/docs/class_and_method/README.md#nginxupstreamserverstring) said nothing about a host name.
- Affected: scripts that give `Nginx::Upstream#server=` a host name, `localhost` included, and scripts that give it an IPv4 address in a form that only the system resolver read, such as `127.1`, `2130706433` or `0x7f.0.0.1`, or `255.255.255.255`; for those strings the worker did not wait. Unless the script rescues the exception, a handler of a request phase answers 500, and `mruby_set` leaves its variable empty.
- What to do: give an IP address that the script has without waiting, for example from its configuration, and write an IPv4 address as four decimal numbers. For a name that does not change while nginx runs, write the name in the `server` line of the `upstream {}` block, which nginx resolves when it reads the configuration, and do not call the setter. nginx uses all the addresses of such a name: when it has more than one, `Nginx::Upstream.new` raises `RuntimeError` for that upstream, so remove that call too, or write an IP address in the `server` line. A name that does not resolve stops nginx at start.
- Not changed by this release: the 2.x line still resolves a host name. A host name in a `server` line of an `upstream {}` block, which nginx resolves, is not affected.

### An access or post_read handler that waits in `Nginx::Async.sleep` ends as without the wait (#715)

- Before: when the timer of `Nginx::Async.sleep` fired, ngx_mruby resumed the code and ended the handler itself, with the rules of the content phase instead of those of the handler's phase. An access handler (under `satisfy all` or `satisfy any`) or a post_read handler that ended after the sleep without a result (no `Nginx.return`, `Nginx.send_header` or `Nginx.status_code=`) or with `Nginx::OK` let the request reach its content, and nginx then closed the connection instead of answering the next request on it. Under `satisfy any`, a 401 or 403 after the sleep ended the request with that status, where nginx tries the next access handler without the sleep. On a server whose earlier handler had stored `Nginx::DECLINED` (see the entry "A handler that sets no result does not take the result of an earlier handler"), these ends were hidden.
- Now: nginx calls the handler again when the sleep ends, the handler goes on with the code after the sleep, and the checker of the handler's phase handles its result as for a handler that did not wait: without a result, an access handler goes on with the next access handler under `satisfy all` and allows the request under `satisfy any`, and a post_read handler goes on with the next phase; the next request on a kept-alive connection is answered. Under `satisfy any`, a 401 or 403 after the sleep lets nginx try the next access handler, such as `allow` or `auth_request`. While the handler waits, nginx does not run its code again.
- Why it changed:
  - The defect: gap 2 of [docs/proposals/core-stabilization.md](../proposals/core-stabilization.md) (section 2.3): the same code ended in another way after `Nginx::Async.sleep` than without it, because the timer replaced nginx's phase checker with a copy of the content phase's. The owner decided the design on 2026-11-01 (section 8, step 3).
  - Why the old behavior could not be kept: a script cannot rely on an end that depends on whether it waited, and closing the connection after the response drops the next request of a kept-alive client.
  - What the documentation promised: [Nginx::Async#sleep](https://github.com/matsumotory/ngx_mruby/blob/v2.7.3/docs/class_and_method/README.md#nginxasyncsleepmsec) of 2.7.3 said that the sleep is supported in access handlers and that the code after it runs, and said nothing about how the handler ends.
- Affected: `mruby_access_handler`, `mruby_access_handler_code`, `mruby_post_read_handler` and `mruby_post_read_handler_code` handlers that call `Nginx::Async.sleep`, in particular under `satisfy any`, where an access handler that sleeps and then ends without a result now allows the request.
- What to do: an access handler that sleeps and should deny the request returns `Nginx::HTTP_FORBIDDEN` (or `Nginx::HTTP_UNAUTHORIZED`) after the sleep. Under `satisfy any`, nginx then tries the other access handlers, as without the sleep.
- Tests: ports 18176 and 18178 (`test/conf/conf.d/82-async-resume-result.conf`, `test/t/cases/async_resume_result.rb`: every end of access handlers under `satisfy all`, `satisfy any`, `satisfy any` before `allow all`, and before `auth_request`, and of post_read handlers, without a wait and after a sleep).

### An access or post_read handler that writes output ends the request after the response (#715)

- Before: an access or post_read handler that wrote output with `Nginx.rputs` or `Nginx.echo` and set no other status sent the response, and nginx then went on with the phases of the request: the content phase tried to answer again, nginx logged `header already sent`, and it closed the connection before it answered the next request on it. After `Nginx::Async.sleep`, the same handler ended the request after the response.
- Now: with or without a wait, the request ends after the response, as after the output of a rewrite or content handler, and nginx answers the next request on a kept-alive connection.
- Why it changed:
  - The defect: the handler returned `NGX_OK` to nginx after the response, which the access and post_read phases read as "go on". This is the end of a run with output that step 3 of section 8 of [docs/proposals/core-stabilization.md](../proposals/core-stabilization.md) makes the same with and without a wait.
  - Why the old behavior could not be kept: the response of the handler was already sent, and the later phases could only fail on it and close the connection.
  - What the documentation promised: [Nginx.rputs](https://github.com/matsumotory/ngx_mruby/blob/v2.7.3/docs/class_and_method/README.md#nginxrputsstring) of 2.7.3 said "Puts response text" for every handler, and said nothing about the phases after it.
- Affected: `mruby_access_handler*` and `mruby_post_read_handler*` handlers that write output, and log monitoring of the `header already sent` lines that they caused.
- What to do: nothing; a handler that wrote output to answer the request now answers it once.
- Tests: ports 18176, 18178 and 18179 (`test/t/cases/async_resume_result.rb` and `test/t/cases/async_result_isolation.rb`, the cases "that ends with output").

### A handler that sets no result does not take the result of an earlier handler (#715)

- Before: `Nginx.return`, `Nginx.send_header` and `Nginx.status_code=` stored their value in the status of the response, also a return code below 0 such as `Nginx::DECLINED`, and a later handler of the same request that set no result returned that value. On a server whose `mruby_server_rewrite_handler` returned `Nginx::DECLINED` for every request, a content handler that ended without output and without a status went on to the next content handler or to the static module, which answered 404 when no file matched; under `satisfy any`, an access handler without a result was taken to have declined, and `deny` refused the request with 403. After a handler that its timer resumed (`Nginx::Async.sleep`) or that the end of its subrequest resumed, ngx_mruby itself stored 500 for every result but `Nginx::OK`, `Nginx::DECLINED` included, so that a later content handler without output and without a status answered 500.
- Now: the result of a handler is its own. A handler that sets none has no result, whatever an earlier handler of the request set: a content handler of the main request without output answers 200 with an empty body (see "A content handler that ends without output answers 200 with an empty body instead of 500"), and an access or post_read handler goes on as with `Nginx::OK`. A rewrite or server rewrite handler without a result goes on to the next phase handler (see "A rewrite or server rewrite handler that ends without a result goes on to the next phase handler").
- Why it changed:
  - The defect: gap 3 of [docs/proposals/core-stabilization.md](../proposals/core-stabilization.md) (section 2.1): what a handler did depended on handlers that it does not contain, and the same script behaved in another way on two servers. The owner decided on 2026-11-01 that the result of a handler is its own (Q6 of section 9).
  - Why the old behavior could not be kept: a script cannot see what an earlier handler of the request returned, so it cannot know how it ends without a result.
  - What the documentation promised: [Nginx.return](https://github.com/matsumotory/ngx_mruby/blob/v2.7.3/docs/class_and_method/README.md#nginxreturnnginx_status_code) of 2.7.3 said that it returns a status to the client or controls nginx's request processing, and did not say that the value carries over to later handlers.
- Affected: configurations with an `mruby_server_rewrite_handler*`, `mruby_rewrite_handler*`, `mruby_post_read_handler*` or `mruby_access_handler*` that returns `Nginx::DECLINED` or another value for every request, together with a content handler that can end without output and without a status, or an access handler under `satisfy any` that can end without a result.
- What to do: a content handler that should go on to the next content handler returns `Nginx::DECLINED` itself; an access handler under `satisfy any` that should leave the decision to the other access handlers returns `Nginx::DECLINED` itself.
- Tests: port 18179 (`test/conf/conf.d/82-async-result-isolation.conf`, `test/t/cases/async_result_isolation.rb`: a server rewrite handler returns `Nginx::DECLINED`, and the later access and content handlers end by their own result).

### An `mruby_set` handler that waits in `Nginx::Async.sleep` sets its variable, and the request goes on (#715)

- Before: when the sleep ended, ngx_mruby set the variable and then ended the request without a response, unless an earlier handler of the request had stored `Nginx::DECLINED` (as the server rewrite handler of a server that returns it for every request). A status that the code set with `Nginx.return` after the sleep ended the request with that status; without the sleep, such a status does not end it.
- Now: when the code returns, the variable is set and the request goes on with the next handler of the phase, as without the sleep, so the later phases read the value (a content handler, `proxy_pass`). A status that the code sets does not end the request. An exception after the sleep answers 500, as before.
- Why it changed:
  - The defect: gap 2 of [docs/proposals/core-stabilization.md](../proposals/core-stabilization.md) (section 2.3): the end of an `mruby_set` handler after the sleep depended on a status stored by another handler (section 4.4 of the proposal, step 3 of section 8, decided by the owner on 2026-11-01).
  - Why the old behavior could not be kept: a request that ends without a response leaves the client waiting until a timeout, and the end of the handler cannot depend on handlers that it does not contain.
  - What the documentation promised: [Nginx::Async#sleep](https://github.com/matsumotory/ngx_mruby/blob/v2.7.3/docs/class_and_method/README.md#nginxasyncsleepmsec) of 2.7.3 said that the sleep is supported in set handlers, and said nothing about how the request goes on.
- Affected: `mruby_set` and `mruby_set_code` whose code calls `Nginx::Async.sleep`.
- What to do: nothing for most configurations. Code that ended the request with a status after the sleep returns that status from a later handler instead, for example a rewrite handler that reads the variable. The directives of the same rewrite script after the `mruby_set` still run before the sleep ends, without the value.
- Tests: port 18182 (`test/conf/conf.d/83-async-set-var.conf`, `test/t/cases/async_set_var.rb`).

### A rewrite or server rewrite handler that ends without a result goes on to the next phase handler (#720)

- Before: an `mruby_rewrite_handler*` or `mruby_server_rewrite_handler*` handler that ended without output and without `Nginx.return`, `Nginx.send_header` or `Nginx.status_code=`, or with `Nginx.return Nginx::OK`, returned `NGX_OK` to the rewrite phase, and nginx finalized the request without a response: with `Connection: close` it closed the connection without a byte, and a kept-alive connection stayed open until `keepalive_timeout`; `error.log` had no line at the `error` level. On a server whose earlier handler had returned `Nginx::DECLINED` for every request, such a handler took that value and went on. `Nginx.return` with a return code below 0, such as `Nginx::DECLINED`, also stored the code in the status of the response.
- Now: such a handler goes on to the next phase handler, as with `Nginx::DECLINED`, with or without a wait in `Nginx::Async.sleep` or `Nginx::Async::HTTP.sub_request`, whatever an earlier handler of the request set. A return code below 0 is the result of the handler only, and the status of the response does not change. A handler with output, with a status from 100 up or with an exception ends as before.
- Why it changed:
  - The defect: gap 1 of [docs/proposals/core-stabilization.md](../proposals/core-stabilization.md) (section 2.3): an end without a response helps no script. The owner decided on 2026-10-04 that a rewrite handler that ends with no output and no `Nginx.return` goes on, as with `NGX_DECLINED`, on `next` (decision (b), recorded in [docs/HANDOFF.md](../HANDOFF.md)), and extended it to server rewrite handlers on 2026-11-01 (Q6 of section 9 of the proposal).
  - Why the old behavior could not be kept: the client got no response at all, and nothing in `error.log` said why.
  - What the documentation promised: the documentation of 2.7.3 did not say what a rewrite handler without `Nginx.return` does.
- Affected: `mruby_rewrite_handler*` and `mruby_server_rewrite_handler*` handlers that can end without a result or with `Nginx::OK`, for example a handler that only sets variables or headers; they now let the request go on to the content of the location. The test of 2.x behavior "rewrite handler without output or DECLINED sends no response" in `test/t/cases/request_api.rb` expects the content handler's 200 now.
- What to do: nothing for a handler that should let the request go on; a handler that should end the request returns the status it means, for example `Nginx.return Nginx::HTTP_FORBIDDEN`.
- Tests: ports 18176, 18177 and 18179 (`test/t/cases/async_resume_result.rb` and `test/t/cases/async_result_isolation.rb`: rewrite and server rewrite handlers without a result and with `Nginx::OK`, without a wait, after a sleep and after a subrequest), and port 18111 (`test/t/cases/request_api.rb`).

### `Nginx::Async::HTTP.sub_request` works in a content handler, also after `Nginx::Async.sleep` (#722)

- Before: since 2.7.3, `Nginx::Async::HTTP.sub_request` in a content handler (`mruby_content_handler*`) that had waited in `Nginx::Async.sleep` raised a `RuntimeError` (`Nginx::Async::HTTP.sub_request is not available after Nginx::Async.sleep in a content handler`), and the request got 500. Without a sleep before, a content handler could call it, although the documentation named only the set, rewrite and access handlers.
- Now: a content handler waits for the subrequest, before or after a sleep, and answers with the output or the status that its code sets after the call; nginx answers the next request on a kept-alive connection.
- Why it changed:
  - The defect: gap 4 of [docs/proposals/core-stabilization.md](../proposals/core-stabilization.md) (section 2.3). 2.7.3 raised there because nothing would finalize the request after the subrequest. Since the end of a subrequest wakes the request through nginx, which calls the handler again (gap 5, step 5 of section 8), the checker of the content phase finalizes it. The owner decided on 2026-11-01 that 3.0.0 supports it (Q1 of section 9).
  - Why the old behavior could not be kept: a content handler that answers from a subrequest is the base of the plan's row on calls from a handler to other services, and the raise is not needed any more.
  - What the documentation promised: [Nginx::Async::HTTP#sub_request](https://github.com/matsumotory/ngx_mruby/blob/v2.7.3/docs/class_and_method/README.md#nginxasynchttpsub_requestlocation-string_or_hashnil) of 2.7.3 said that it raises in a content handler after a sleep, and [entry 2 of the 2.7.3 release notes](v2.7.3.md) said the same.
- Affected: content handlers that call `Nginx::Async::HTTP.sub_request` after `Nginx::Async.sleep`, and code that rescued its `RuntimeError`.
- What to do: remove such a `rescue`; the call returns the response of the subrequest.
- Tests: ports 18133 (`test/t/cases/async_sleep_in_content.rb`, the case "Nginx::Async::HTTP.sub_request after a sleep in a content handler waits for the subrequest, and the handler answers") and 18183 (`test/conf/conf.d/84-async-subrequest-return.conf`, `test/t/cases/async_subrequest_return.rb`).

### A handler that waits for `Nginx::Async::HTTP.sub_request` runs its code once and ends as without the wait (#722)

- Before: when the subrequest ended, ngx_mruby resumed the code inside the end of the subrequest and ended the handler there, with the rules of the content phase instead of those of the handler's phase. While it waited, the handler returned `NGX_AGAIN`; for an access or post_read handler, nginx then ran the phases of the request again when it went on after the subrequest, which ran the handler's code again from its start, with another subrequest.
- Now: the handler returns `NGX_DONE` while it waits, and nginx ignores the events of the request until the subrequest ends. Then nginx wakes the request and calls the handler again, which goes on with the code after the call, and the checker of the handler's phase handles its result as for a handler that did not wait. The code of the handler runs once for the request, and its subrequest is sent once.
- Why it changed:
  - The defect: gap 5 of [docs/proposals/core-stabilization.md](../proposals/core-stabilization.md) (section 2.3): the end of the subrequest and the end of the parent's handler ran as one call, outside nginx's phase checker. Step 5 of section 8, decided by the owner on 2026-11-01, moves the resume into the parent's own run of the phases.
  - Why the old behavior could not be kept: a handler whose code runs again repeats what the code does, its subrequest included, and its end depended on the handler kind of another phase.
  - What the documentation promised: [Nginx::Async::HTTP#sub_request](https://github.com/matsumotory/ngx_mruby/blob/v2.7.3/docs/class_and_method/README.md#nginxasynchttpsub_requestlocation-string_or_hashnil) of 2.7.3 said "Sends a sub request in non-blocking way" and that it is supported in access handlers, and nothing about how the handler ends.
- Affected: `mruby_access_handler*` and `mruby_post_read_handler*` handlers that call `Nginx::Async::HTTP.sub_request`, and the other handlers that call it, whose results nginx now handles in their own phase.
- What to do: nothing for most scripts. A script that counted on its code running again after the subrequest does the work after the call instead, where the response of the subrequest is available.
- Tests: ports 18176 to 18179 (`test/t/cases/async_resume_result.rb` and `test/t/cases/async_result_isolation.rb`: every end of access, post_read and content handlers after a subrequest), and ports 18183 and 18184 (`test/t/cases/async_subrequest_return.rb`: an access or post_read handler that waits for a subrequest and sets no result, or returns `Nginx::DECLINED`, runs once, sends one subrequest, and the request goes on).

### A UDP stream session runs its code once: datagrams that arrive while the code waits do not start it again (#727)

- Before: nginx called the stream handler for each datagram from the client of a UDP session (`listen ... udp`), and while the code of the session waited in `Nginx::Stream::Async.sleep`, each datagram started the code again from its start, in another fiber of the same session. The sleep of the newer run replaced the pending one, so only the last run went on after its sleep.
- Now: a session runs its code once. A datagram that arrives while the code waits does not start it again; nginx gives the datagram to the handler only during that call, so the code does not see it. The session goes on, or ends, by the result of the code after the sleep, as for a session whose code does not wait.
- Why it changed:
  - The defect: gap 9 of [docs/proposals/core-stabilization.md](../proposals/core-stabilization.md) (section 2.5): the code of a session ran several times at once, in fibers of one session. The owner decided on 2026-11-01 that a UDP session runs its code once (Q4 of section 9).
  - Why the old behavior could not be kept: the runs shared the session and its result, and only the last one decided how the session went on.
  - What the documentation promised: [Nginx::Stream::Async#sleep](https://github.com/matsumotory/ngx_mruby/blob/v2.7.3/docs/class_and_method/README.md#nginxstreamasyncsleep) of 2.7.3 said that the session goes on after the sleep by the result of the code, and nothing about datagrams during the sleep.
- Affected: `mruby_stream` and `mruby_stream_code` of a `listen ... udp` server whose code calls `Nginx::Stream::Async.sleep` and whose clients send more than one datagram during the sleep.
- What to do: nothing for most configurations. Code that counted on running once for each datagram does not sleep, or handles one datagram per session.
- Tests: port 12392 (`test/conf/conf.d/stream/47-async-sleep-udp-once.conf`, `test/t/cases/stream_async_sleep_udp_once.rb`: ten datagrams during the sleep start the code once).

### A stream session that waits when `worker_shutdown_timeout` expires ends then (#727)

- Before: when `worker_shutdown_timeout` expired in a worker that shut down (after a reload or SIGQUIT), nginx marked the connections to be closed and called their read handlers, but a stream session whose code waited in `Nginx::Stream::Async.sleep` went on: the code ran again from its start in another fiber, and the worker ran until the code ended.
- Now: such a session ends when the timeout expires. The code after the sleep does not run, `error.log` gets the line `shutdown timeout` at the `info` level, and the worker exits, as it does for a session of `proxy_pass`.
- Why it changed:
  - The defect: gap 10 of [docs/proposals/core-stabilization.md](../proposals/core-stabilization.md) (section 2.5): the handler did not look at the close that nginx asks for, so `worker_shutdown_timeout` did not bound the life of an old worker with such a session. Step 6 of section 8, decided by the owner on 2026-11-01.
  - Why the old behavior could not be kept: `worker_shutdown_timeout` is the setting that bounds how long an old worker runs after a reload.
  - What the documentation promised: the documentation of 2.7.3 said nothing about `worker_shutdown_timeout` and stream code that sleeps.
- Affected: stream servers whose code calls `Nginx::Stream::Async.sleep`, in configurations with `worker_shutdown_timeout`.
- What to do: nothing; code that must finish keeps its sleeps shorter than `worker_shutdown_timeout`. Without `worker_shutdown_timeout`, an old worker still finishes the sleeps in flight.
- Tests: `test/t/cases/workers.rb`, mode `shutdown` (`test/conf/workers/shutdown.conf`, ports 18185 and 12393).

### `Nginx::Stream::Connection.proxy_protocol_addr` and `proxy_protocol_ip` return `nil` for a connection without a PROXY source address

- Before: with nginx 1.17.6 and later, `Nginx::Stream::Connection.proxy_protocol_addr` and `Nginx::Stream::Connection.proxy_protocol_ip`, as class and as instance methods, did not return a value for a connection that had no source address from a PROXY protocol header: on a listen without `proxy_protocol`, and after the header `PROXY UNKNOWN` (version 1) or a version 2 header with the command `LOCAL`.
- Now: the methods return `nil` for such a connection. After a header that carries addresses, they return its source address as before. 2.7.4 makes the same change.
- Why it changed:
  - The defect: the methods returned no value for such a connection, as "Before" describes. The advisory [GHSA-xjh6-6vgm-56wj](https://github.com/matsumotory/ngx_mruby/security/advisories/GHSA-xjh6-6vgm-56wj) describes the defect, the affected versions and the conditions.
  - Why the old behavior could not be kept: such a connection has no address to return, and `nil` tells it apart from a connection with one. In HTTP code, `Nginx::Var#proxy_protocol_addr` returns `nil` in the same case.
  - What the documentation promised: the methods were not documented. [docs/class_and_method/README.md](../class_and_method/README.md#nginxstreamconnectionproxy_protocol_addrproxy_protocol_ip) describes them now.
- Affected: `mruby_stream` and `mruby_stream_code` code that calls these methods on a connection without a PROXY source address.
- What to do: nothing for code that compares the result with a String. Code that calls a String method on the result handles `nil`, for example with `to_s`.
- Tests: ports 12385 and 12386 of the mode `stream_master` of `test/t/cases/_second_instance.rb`, a second nginx with a master process and one worker.

### On a listen with `proxy_protocol`, a stream session whose code sleeps reads nothing from the client, and `worker_shutdown_timeout` ends it

- Before: while the code of a session on a listen with `proxy_protocol` waited in `Nginx::Stream::Async.sleep`, the read events of the connection were handled as before the code ran: bytes that the client sent during the sleep could end the session (status 400 in the access log), and when `worker_shutdown_timeout` expired during the sleep, the session did not end then.
- Now: while the code sleeps, nginx reads nothing from the client on such a listen, as on the other listens. The bytes that the client sends then stay for the phase after the code: `proxy_pass` sends them to the upstream. A client that closes the connection during the sleep is seen by the phase after the code, as on the other listens. When `worker_shutdown_timeout` expires during the sleep, the session ends, as the entry "A stream session that waits when `worker_shutdown_timeout` expires ends then" describes. 2.7.4 makes the same change for TCP sessions.
- Why it changed:
  - The defect: the read events during the sleep were handled as before the code ran, as "Before" describes. The advisory [GHSA-xjh6-6vgm-56wj](https://github.com/matsumotory/ngx_mruby/security/advisories/GHSA-xjh6-6vgm-56wj) describes the defect, the affected versions and the conditions.
  - Why the old behavior could not be kept: the bytes after the header belong to the protocol that the later phases carry. A session that does not end at `worker_shutdown_timeout` keeps the old worker process after the time that the directive sets.
  - What the documentation promised: [docs/class_and_method/README.md](../class_and_method/README.md#nginxstreamasync-class) said nothing about reads during the sleep. nginx's documentation of [`worker_shutdown_timeout`](https://nginx.org/en/docs/ngx_core_module.html#worker_shutdown_timeout) says that nginx tries to close the open connections when the timeout expires.
- Affected: stream servers on a listen with `proxy_protocol` whose `mruby_stream` or `mruby_stream_code` code calls `Nginx::Stream::Async.sleep`: the clients that send bytes or close the connection during the sleep, and a worker that shuts down (a reload, an upgrade, a stop) with `worker_shutdown_timeout` while the code sleeps.
- What to do: nothing. The phase after the code gets the bytes of the client, as on a session whose code does not sleep.
- Tests: port 12384 (`test/conf/conf.d/stream/48-proxy-protocol-wait.conf`, `test/t/cases/stream_proxy_protocol_wait.rb`: the reply after bytes during the sleep), and ports 12387 and 12388 of the mode `stream_master` of `test/t/cases/_second_instance.rb` (sessions with and without `proxy_protocol` when `worker_shutdown_timeout` expires).

### `Nginx.redirect` with a local URI takes effect when the handler ends (#728)

- Before: `Nginx.redirect` with a local URI made the internal redirect inside the call: nginx ran the phases of the target location there, and its mruby handlers ran inside the fiber of the calling handler. The calling handler went on after the call and returned its own result, so two handlers could answer one request: output or a status that the calling handler set after the call answered first and the target's output followed it, a content handler of the target ended the request at `Nginx::Async.sleep` without its output, and after a sleep and `Nginx.redirect` in a content handler the client got the target's 200 while the access log had 500. An exception of the calling handler after the call left the target's answer.
- Now: in a post_read, server rewrite, rewrite, access or content handler, the call records the URI, the code goes on to its end, and then nginx runs the phases of the target, whose handlers run outside the caller's fiber and can wait like any handler. One handler answers the request. The output and the status of the calling handler are not sent; when its code writes output or sets a status after the call, `error.log` gets a line at the `warn` level that ends with `set after Nginx.redirect are not sent`. Response headers that the calling handler sets and changes that it makes to the request (its arguments, for example with `Nginx::Request#args=`) stay, also when they come after the call: the target's answer carries those headers, and the target sees those arguments. An exception of the calling handler answers 500, and the redirect does not take effect. `Nginx.redirect` with a URL, and a local redirect from an `mruby_set*` handler, a log handler or a filter, are unchanged.
- Why it changed:
  - The defect: gap 6 of [docs/proposals/core-stabilization.md](../proposals/core-stabilization.md) (section 2.4): the three cases above. The owner decided on 2026-11-01 that `Nginx.redirect` takes effect when the handler ends (Q2 of section 9).
  - Why the old behavior could not be kept: two handlers that answer one request send two responses or none, and a target that waits ran inside another handler's fiber.
  - What the documentation promised: [Nginx.redirect](https://github.com/matsumotory/ngx_mruby/blob/v2.7.3/docs/class_and_method/README.md#nginxredirecturl_or_internal_location-http_statusnginxhttp_moved_temporarily) of 2.7.3 said that the internal redirect runs the handlers of the other location before the call returns, and that the calling code goes on after the call.
- Affected: handlers that call `Nginx.redirect` with a local URI and then write output, set a status, set response headers, change the arguments of the request or raise, handlers that rely on the target having run when the call returns, and log monitoring of the 500 in the access log of a redirected request.
- What to do: write nothing after `Nginx.redirect` that is meant for the client; return from the handler after the call when the code after it should not run. Code that read what the target set (a variable, a header) after the call moves to the target.
- Tests: port 18186 (`test/conf/conf.d/85-redirect-async.conf`, `test/t/cases/redirect_async.rb`), and the cases of `test/t/cases/async_sleep_in_content.rb` and `test/t/cases/async_exception_state.rb` with `Nginx.redirect`.

### `Nginx::Async::HTTP.sub_request` raises a `RuntimeError` in an `mruby_set` handler (#NNN)

- Before: in an `mruby_set` or `mruby_set_code` handler, `Nginx::Async::HTTP.sub_request` started the subrequest, but nginx did not wait for it. The directives after the `mruby_set` and the later phases ran before the code had set the variable, and the code after the call ran when the subrequest ended. An exception of that code left the client without a response.
- Now: the call raises a `RuntimeError` with the message `Nginx::Async::HTTP.sub_request is not available in an mruby_set handler`. The handler ends as after any exception there: without a wait, `error.log` gets the exception, the variable is empty, and the request goes on; after `Nginx::Async.sleep`, the request gets 500. `Nginx::Async.sleep` in an `mruby_set` handler works as before.
- Why it changed:
  - The defect: gap 7 of [docs/proposals/core-stabilization.md](../proposals/core-stabilization.md) (section 2.3): nginx does not wait for a subrequest of an `mruby_set` handler. The owner decided on 2026-11-01 that the call raises there (Q5 of section 9).
  - Why the old behavior could not be kept: the rewrite module runs an `mruby_set` handler inside its script and goes on when the handler returns, so the value of a handler that waits for a subrequest arrives after the phases that read it. A raise tells the script at once, as in log handlers since 2.7.1.
  - What the documentation promised: [Nginx::Async::HTTP#sub_request](https://github.com/matsumotory/ngx_mruby/blob/v2.7.3/docs/class_and_method/README.md#nginxasynchttpsub_requestlocation-string_or_hashnil) of 2.7.3 said that the method is supported in `set` handlers, and [Nginx.rputs](https://github.com/matsumotory/ngx_mruby/blob/v2.7.3/docs/class_and_method/README.md#nginxrputsstring) of 2.7.3 said that nginx goes on without waiting for the variable and that an exception after the call leaves the client without a response.
- Affected: `mruby_set` and `mruby_set_code` whose code calls `Nginx::Async::HTTP.sub_request`.
- What to do: call `Nginx::Async::HTTP.sub_request` in a rewrite or access handler, which waits for the subrequest, and set the variable there with `Nginx::Var#set`.
- Tests: port 18182 (`test/conf/conf.d/83-async-set-var.conf`, `test/t/cases/async_set_var.rb`: the cases with `sub_request`).

## New features

- `Nginx::Async::HTTP.sub_request` returns the response of the subrequest, an `Nginx::Async::HTTP::Response` with the same status, headers and body as `Nginx::Async::HTTP.last_response`; on 2.x it returns `nil` (#722)
- Scripts can use the additions of mruby 3.4, 4.0 and 4.1: pattern matching (`case`/`in`), with strings as patterns since 4.1, `Array#rfind`, trailing commas in method parameters, `&nil` in method parameters, and `it` for the first parameter of a block (`[1, 2].map { it * 2 }` is `[2, 4]`) (#561, #678)
- Scripts can call methods that mruby 3.3.0 does not have, for example `Kernel#public_send`, `String#b`, `Hash#slice!`, `Array#fetch_values`, `Integer#bit_length`, `Integer.sqrt` and `Module#private_instance_methods`. mruby 4.1 adds `String#scrub`. mruby's lists of user-visible changes ([`doc/mruby3.4.md`](https://github.com/mruby/mruby/blob/4.1.0-rc2/doc/mruby3.4.md), [`doc/mruby4.0.md`](https://github.com/mruby/mruby/blob/4.1.0-rc2/doc/mruby4.0.md), [`NEWS.md`](https://github.com/mruby/mruby/blob/4.1.0-rc2/NEWS.md)) name more (#561, #678)
- `Dir.children` and `Dir#each_child` list the entries of a directory without `.` and `..`, as in CRuby, and `Dir.empty?` tells whether a directory has no entries (#559, #561). ngx_mruby 2.x took `Dir` from iij/mruby-dir, which has none of the three methods. `Dir` now comes from mruby's core gem mruby-dir (see [Class and Method](../class_and_method/README.md)), and with the bundled mruby the two methods leave out `.` and `..` (since mruby 3.4, mruby/mruby#6265). With mruby 3.3.0, which no release of ngx_mruby combined with mruby-dir, they were aliases of `Dir.entries` and `Dir#each` and included `.` and `..`; the test suite of ngx_mruby saw the change (`test/t/cases/gem_dir.rb`). A script written for such a build that skipped `.` and `..` after these calls can drop that code, or keep using `Dir.entries`. `Dir` also includes `Enumerable`, which iij/mruby-dir does not, so `Dir.open(path) { |d| d.select { |name| name.end_with?(".txt") } }` works; `Dir.open` with a block closes the `Dir` when the block ends.

## Fixes

- `Dir.foreach` with a block closes the `Dir` that it opened. With iij/mruby-dir of 2.x, that `Dir` kept a file descriptor of the worker open until the GC freed it (#559)
- When `mrb_open()` fails while nginx reads the configuration, the http module logs `ngx_mruby: mrb_open() failed` and the stream module `ngx_mruby-stream-module: mrb_open() failed` at the `emerg` level, followed by `: <class> raised while initializing mruby` when the initialization of mruby or of a gem raised an exception. nginx stops as before; ngx_mruby 2.x logged no line of its own (#559)
- A handler that calls `Nginx::Async.sleep` several times keeps one timer and one cleanup in the request pool instead of one of each per call. An HTTP handler that never waits no longer stores its fiber in the GC root holder or adds a cleanup, and a stream handler that never sleeps no longer adds a cleanup; the fiber is stored at its first wait. The compiled code of a handler is prepared once, when it is compiled or loaded, instead of on every run. `Nginx::Async.sleep`, `Nginx::Stream::Async.sleep` and `Nginx::Async::HTTP.sub_request` add their cleanup and check each allocation before they arm the timer or post the subrequest, so that a failed allocation raises a `RuntimeError` with nothing armed (#714)
- An `mruby_set` handler whose value has a `to_s` that raises answers 500, with or without a wait, and `error.log` gets the exception of `to_s`. When `to_s` of the value returns an object that is not a String, the variable gets the String that `Kernel#to_s` gives for the value, for example `#<Object:0x...>`. `Nginx::Var#set` converts its two arguments in the same way (#NNN)

## Upgrading

Supported nginx versions: the nginx mainline and stable lines (see
[README.md](../../README.md)). Read the release notes of the 2.x releases
newer than the version you run first, then this file. Rebuild the module
together with the bundled mruby 4.1.0-rc2; a `build_config.rb` of your own
needs the changes of "A `build_config.rb` of your own needs the core gem
changes of mruby 4.1".
[Migrating from ngx_mruby 2.x to 3.0.0](../migration/README.md) has the
steps for finding the scripts and builds that each entry affects. Check
these before upgrading:

- The bundled mruby 4.1.0-rc2: rebuild the module together with it, and check mruby's lists for the changes that these entries do not cover (#561, #678).
- A `build_config.rb` of your own: remove mruby-print, hal-posix-io, hal-posix-dir and hal-posix-socket, decide on mruby-task and mruby-encoding, and with `full-core.gembox` choose between the core gems mruby-env, mruby-process and mruby-regexp and the third-party gems of the same classes (#561, #678).
- Ruby: build with Ruby 3.0 or later (#678).
- `build_config.rb.lock`: nothing for a new checkout or a source archive; to build a gem at another commit, change its entry, and remove `mruby/build` after a change of the lock (#558).
- `Hash#inspect` and `Hash#to_s`: do not use them as a data format; build the string yourself, or use `JSON.generate` (#561).
- `Exception#inspect`: update log parsers and alerts that match the old form of the `mrb_run failed` lines (#561).
- `"#@ivar"`, `"#@@cvar"` and `"#$global"`: escape the `#` of such strings that are meant literally, or use single quotes (#678).
- Syntax errors: match on `SyntaxError` and the file and line, not on the text of the message (#678).
- An `Array`, a `Hash` or a `Struct` that holds itself: nothing, unless a script relies on the `SystemStackError` of the comparison (#678).
- The messages logged while nginx reads the configuration: to see them, run `nginx -t -e stderr`, read the startup log after `nginx -t`, or reload with `error_log` at `info` (#565).
- `NoMethodError`: match on the exception class, not on the message (#561).
- `private` and `protected`: call such methods without a receiver, or with `send`; list private methods with `private_instance_methods` or `private_methods` (#561, #678).
- `Module#remove_const`, `#private`, `#public`, `#protected`, `#module_function` and the hooks: call them in the body of the class or module without a receiver, or with `send` (#561).
- Overrides of `append_features`, `prepend_features` and `extend_object`: move the code to `included`, `prepended` or `extended` (#561).
- `allbits?`, `anybits?` and `nobits?` on a Float: convert with `to_i` first (#561).
- `FileTest`: nothing for calls of its methods (#561).
- A constant assigned in a method body: use `Object.const_set` (or `Kernel.const_set`) (#561).
- Bit operations on a Float: convert with `to_i` first, or compute the old number as the entry says (#561).
- `String#valid_encoding?`: drop the call, or build with mruby-encoding and check the scripts (#561).
- A seeded `Random` or `srand`: do not depend on its numbers across versions (#561).
- `Set#inspect`, `Set#to_s` and `Set#flatten_merge`: do not use the first two as a data format; call `s.merge(Set.new(t).flatten)` in place of `s.flatten_merge(t)` (#561).
- `Hash#default_proc=`: pass a Proc or `nil` (#561).
- `yield` with keyword arguments: nothing (#561).
- A `return` inside a block or a `for` body of handler code: nothing (#561).
- A content handler that ends without output: a handler that relied on the 500 sets the status it means, for example `Nginx::HTTP_INTERNAL_SERVER_ERROR`; log monitoring that matches `response body is empty. return NGX_HTTP_INTERNAL_SERVER_ERROR` no longer sees such handlers of the main request with no status or a status from 200 to 299 that nginx does not answer by itself (#574).
- An output body filter that ends with an empty body: nothing (#574).
- The accessors of `Nginx::Var`: use `v.exist?(name)` to tell whether a variable exists, and give the methods of your scripts names that are not names of nginx variables (#610).
- `Nginx::Connection`, `Nginx::Server` and `Nginx::Request`: to return other values, define the methods on those classes; read variables with `Nginx::Var` instead of `@iv_var` (#610).
- `Dir`: rescue `IOError` instead of `RuntimeError` around a `Dir` that can be closed; a script for both versions rescues both (#559).
- C extensions: declare classes that wrap C data with `MRB_SET_INSTANCE_TT(klass, MRB_TT_DATA)`, define C methods with the spec that `mrb_get_args` reads, use `mruby/io.h`, `mrb_temp_alloc()` and `MRB_OPEN_FAILURE()`, call `mrb_open()` or `mrb_open_core()` without an allocator and define `mrb_basic_alloc_func()` for a custom one, and add `mruby/build/host/include` to the include path, also in a list given with `--with-mruby-incdir` (#561, #572).
- The classes that came with the auto-ssl mrbgem: use `pack('m0')` and `unpack1('m')` in place of `Base64`, `ENV['TMPDIR'] || '/tmp'` in place of `Dir.tmpdir` and `Dir.mkdir` in place of `Dir.mktmpdir`, or add the gems to a `build_config.rb` of your own (#556).
- The auto-ssl mrbgem: get certificates with ngx_http_acme_module, or keep a 2.x build for a server that needs `Nginx::SSL::ACME`; remove `NGX_MRUBY_AUTO_SSL` from the build environment (#640).
- `Nginx::Upstream#server=` and `Nginx::Stream::Connection#upstream_server=`: rescue `ArgumentError` for a string that cannot be a server; a script for both versions rescues `ArgumentError` and `RuntimeError`, or `StandardError` (#680).
- `Nginx::Upstream#server=` with a host name: give an IP address that the script has without waiting, with an IPv4 address as four decimal numbers, or write the name in the `server` line of the `upstream {}` block and do not call the setter; for a name with more than one address, `Nginx::Upstream.new` raises for that upstream, so remove that call too (#680).
- An access or post_read handler that waits in `Nginx::Async.sleep`: an access handler that should deny the request after the sleep returns `Nginx::HTTP_FORBIDDEN` or `Nginx::HTTP_UNAUTHORIZED` (#715).
- An access or post_read handler that writes output: nothing (#715).
- A handler that sets no result after an earlier handler returned a value for every request: a content handler or an access handler under `satisfy any` that should go on returns `Nginx::DECLINED` itself (#715).
- An `mruby_set` handler that waits in `Nginx::Async.sleep`: code that ended the request with a status after the sleep returns that status from a later handler (#715).
- A rewrite or server rewrite handler that ends without a result: a handler that should end the request returns the status it means (#720).
- `Nginx::Async::HTTP.sub_request` in a content handler after `Nginx::Async.sleep`: remove a `rescue` of its `RuntimeError` (#722).
- A handler that waits for `Nginx::Async::HTTP.sub_request`: do the work that counted on the code running again after the call (#722).
- A UDP stream session whose code sleeps: code that counted on running once for each datagram does not sleep (#727).
- A stream session that waits when `worker_shutdown_timeout` expires: keep the sleeps that must finish shorter than the timeout (#727).
- `Nginx::Stream::Connection.proxy_protocol_addr` and `proxy_protocol_ip`: nothing for code that compares the result with a String; code that calls a String method on the result handles `nil`, for example with `to_s`.
- The reads of a stream session on a listen with `proxy_protocol` during `Nginx::Stream::Async.sleep`: nothing.
- `Nginx.redirect` with a local URI: write nothing after the call that is meant for the client, and move code that read what the target set to the target (#728).
- `Nginx::Async::HTTP.sub_request` in `mruby_set` and `mruby_set_code`: call it in a rewrite or access handler and set the variable there with `Nginx::Var#set` (#NNN).
