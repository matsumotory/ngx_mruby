# ngx_mruby v2.7.7

## 更新前に確認する挙動の変更

### クラスが`inspect`か`backtrace`を再定義している例外の、`error.log`の行(#803)

- 変更前：Rubyのコードが出した例外のクラスが`inspect`をRubyで再定義していると、再定義したメソッドが何をしても、ngx_mrubyはその例外の行を`error.log`に書きませんでした。ngx_mrubyは、例外がmrubyの状態に残ったままこのメソッドを呼んでいました。この状態では、同梱のmrubyはメソッドを最後まで実行せず、残っている例外のまま処理を進めます。そのため、メソッドが返すはずのStringも、メソッド自身が出す例外も、ngx_mrubyには届きませんでした。`--with-debug`のビルドでは、Rubyで再定義した`backtrace`も同じように扱われ、ngx_mrubyはdebugのレベルで`backtrace must be Array. mrb_type=18`を書き、フレームを書きませんでした。`mruby_set`のハンドラから`Nginx.redirect`で移ったlocationのcontentハンドラでは、再定義した`inspect`が何をしても、また`--with-debug`のビルドでは再定義した`backtrace`が何をしても、StringやArrayを返す場合も含めて、リクエストが終わりませんでした。残っている例外が、間にあるnginxの関数を飛び越えて、`mruby_set`のハンドラまで伝わったからです。`mruby_set`のハンドラは、その例外をもう一度ログに書きました。再定義した`inspect`の場合は、ここでも例外の行は書かれませんでした。再定義した`backtrace`の場合は、例外の行がもう一度書かれ、フレームは書かれませんでした。その後、nginxは500の代わりに、移った先のlocationの静的ファイルから404を返しました。接続は、クライアントが待つのをあきらめるまで開いたままでした。
- 変更後：ngx_mrubyは、残っている例外を退避してから`inspect`と`backtrace`を呼び、これらのメソッドが出した例外をログの処理の中で止めます。`inspect`がStringを返すと、行にはそのStringが入ります。これは、`inspect`を再定義していないクラスの例外と同じ扱いです。`inspect`が例外を出すと、行には`#<Class> (inspect raised Class)`が入ります。前の`Class`は例外のクラス、後の`Class`は`inspect`が出した例外のクラスです。`inspect`がString以外を返すと、行には`#<Class> (inspect did not return a String)`が入ります。`--with-debug`のビルドでは、再定義した`backtrace`の結果のうちStringの要素を1行ずつ書き、それ以外の要素は飛ばします。例外を出すか、Arrayを返さない`backtrace`は、これまでどおりdebugのレベルで書きます。別のmrubyの呼び出しの中でも、nginxの直下と同じように、リクエストは500で終わり、workerは次のリクエストに進みます。
- 変更の理由：
  - 不具合：`inspect`と`backtrace`は、例外が残ったまま呼ばれていました。そのため、Rubyで書いたメソッドは結果を返せませんでした。別のmrubyの呼び出しの中では、メソッドが何をしても、残っている例外がログの処理を抜け、リクエストが終わりませんでした。`next`では、同じ呼び出しを#796と#799で直しています。このプルリクエストは、その直しを2.xに入れます。
  - 前の挙動を残せなかった理由：例外がログの処理を抜けて、リクエストを処理しているnginxの関数を飛び越えると、リクエストとその接続が開いたまま残ります。例外の行が書かれないと、運用者はエラーが起きたことをログから知ることができません。Stringを返せない`inspect`の代わりにクラス名を書く行は、3.xが同じ例外に書く行と同じです。これで、2.xと3.xは同じ行を書きます。
  - ドキュメントが示していた挙動：ドキュメントは、クラスが`inspect`か`backtrace`を再定義している例外について、何も書いていませんでした。
- 影響の範囲：`inspect`か`backtrace`をRubyで再定義したクラスの例外を出す、すべての種類のハンドラのスクリプトです。HTTPとstreamのハンドラに加えて、nginxが設定を読むときと、workerの開始と終了のときに動くコードも含みます。これらを再定義していないクラスの例外は、これまでと1バイトも変わらない行になります。
- 必要な対応：ありません。ただし、このような例外の行を`error.log`から読み取っている場合は、その行が書かれるようになり、再定義した`inspect`のテキストかクラス名が入ることに注意してください。

### Requestのセッター、`Nginx::Async::HTTP.sub_request`、`Nginx::Headers_in/out#[]=`へのStringでない引数

アドバイザリ：[GHSA-cjxv-4q9m-62pf](https://github.com/matsumotory/ngx_mruby/security/advisories/GHSA-cjxv-4q9m-62pf)

- 変更前：`Nginx::Request#uri=`、`#args=`、`#method=`、`#protocol=`、`#request_line=`、`#unparsed_uri=`、`#content_type=`(1つのマクロを共有)、`Nginx::Async::HTTP.sub_request`(リクエストのpath)、`Nginx::Headers_in#[]=`と`Nginx::Headers_out#[]=`(ヘッダ名と各値)は、引数がStringかどうかを確かめず、Stringでない引数をStringとして読んでいました。
- 変更後：これらのメソッドは、Stringでない引数に対して`TypeError`を出します。`Nginx.rputs`、`Nginx.echo`、`Nginx.redirect`、`Nginx::Filter#body=`、`Nginx::Var`のセッターと同じ扱いです(#775)。`nil`の引数はこれまでの意味を保ちます。セッターはメンバーを変えずに戻り、`Headers#[]=`はヘッダを削除します。
- 変更の理由：
  - 不具合：これらのメソッドは、引数の型を確かめずにStringとして読んでいました。詳細は、上にリンクした勧告が示します。
  - 前の挙動を残せなかった理由：Stringでない値にはStringとしての内容がないため、Stringとして読んでも定まった結果になりません。
  - ドキュメントが示していた挙動：これらのメソッドのドキュメントは、Stringの引数を説明しています。
- 影響の範囲：これらのメソッドのいずれかに、Stringでないかもしれない値を渡すスクリプトです。Stringだけを渡すスクリプト(リテラル、式展開した文字列、変換済みの値)は影響を受けません。
- 必要な対応：スクリプトがStringでない値をこれらのメソッドに渡しうる場合は、`.to_s`などで変換するか、`TypeError`を処理してください。

## 不具合の修正

- 例外のクラスがRubyで`inspect`を再定義しているか、`--with-debug`のビルドで`backtrace`を再定義していて、`mruby_set`のハンドラから`Nginx.redirect`で移ったlocationのcontentハンドラでその例外が出たとき、メソッドが何をしても、nginxはリクエストを500で終えるようになりました。これまでは、例外が`mruby_set`のハンドラまで伝わり、nginxは404を返し、接続はクライアントが待つのをあきらめるまで開いたままでした(#803)。
- `--with-debug`のビルドで、再定義した`backtrace`の結果のうちString以外の要素を、3.xと同じように飛ばすようになりました。これまでのコードは、型を確かめずに、すべての要素をStringとして読んでいました(#803)。
- `Nginx::Upstream#server=`とstreamの`Nginx::Stream::Connection#upstream_server=`は、nginxのcycleのpoolが解放されるときに、peerごとのストアをリセットするようになりました。これにより、`master_process off`での再読み込みの後の新しいcycleが、前のcycleのストアを再利用しなくなります([GHSA-pmjr-f94r-j47g](https://github.com/matsumotory/ngx_mruby/security/advisories/GHSA-pmjr-f94r-j47g))。

## アップグレード

- ディレクティブの追加、名前の変更、削除はありません。2.7.6と同じ方法でこのリリースのモジュールをビルドし、バイナリか動的モジュールを置き換えてください。

アップグレードの前に、次の点を確かめてください。各行は、項目の「必要な対応」です。

- `inspect`か`backtrace`を再定義したクラスの例外の行を`error.log`から読み取っているツール：このような例外の行が書かれるようになり、再定義した`inspect`のテキストかクラス名が入ります。
- Requestのセッター、`Nginx::Async::HTTP.sub_request`、`Nginx::Headers_in/out#[]=`にStringでないかもしれない値を渡すスクリプト：`.to_s`などで変換するか、これらのメソッドがStringでない引数に対して出す`TypeError`を処理してください。
