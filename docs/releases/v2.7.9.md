# ngx_mruby v2.7.9

## Behavior changes: read before upgrading

### The upstream methods raise ArgumentError on an object whose initialize raised, instead of returning nil or ending the worker (#816)

- Before: `Nginx::Upstream#initialize` and `Nginx::Stream::Connection#initialize` gave the object its upstream before they checked that an upstream had the name, and the upstream methods read it without a check. A script could keep such an object after `initialize` raised: an object from `allocate` whose `initialize` raised, an object on which the script called `initialize` again (with `send`) and that call raised, or the object of a subclass whose `initialize` rescued the exception of `super`. An object from `allocate` that never got an `initialize` was in the same state. When no upstream had the name, `Nginx::Upstream#server` and `Nginx::Stream::Connection#upstream_server` returned `nil`, and `Nginx::Upstream#server=`, `#keepalive_cache`, `#keepalive_cache=` and `Nginx::Stream::Connection#upstream_server=` read through a NULL pointer, and the worker process ended with a segmentation fault. When the upstream had more than one server, and on an object from `allocate`, every one of these methods, `#server` and `#upstream_server` included, ended the worker in the same way.
- Now: `initialize` gives the object its upstream only when it found the upstream and its server. On an object without an upstream, `Nginx::Upstream#server`, `#server=`, `#keepalive_cache` and `#keepalive_cache=` raise `ArgumentError` (`uninitialized Nginx::Upstream`), and `Nginx::Stream::Connection#upstream_server` and `#upstream_server=` raise `ArgumentError` (`uninitialized Nginx::Stream::Connection`). The exception ends the handler like any other exception of the script: a `rescue` in the script catches it, and otherwise ngx_mruby logs it, the request gets 500, and the stream session is closed. The worker goes on to serve the next request and session. An `initialize` that succeeds after one that raised gives the object its upstream, and the methods work again.
- Why it changed:
  - The defect: `initialize` stored the context of the object (the upstream, its peers and its server) before it checked them, and freed the old context and raised before it stored a new one for an upstream with more than one server; the methods read that context without checking that it held an upstream (#816).
  - Why the old behavior could not be kept: an object without an upstream has no server to return, change or keep connections for. `nil` from `#server` was the result of reading an empty context, not a value that the method defined, and the next method on the same object ended the worker, which also ended the other requests that the worker was serving. Raising for every upstream method is the one behavior that the methods can have on such an object. `ArgumentError` with `uninitialized` and the name is what the bundled mruby raises for its own objects whose `initialize` did not run, such as `Time` (`uninitialized time`) and `Range` (`uninitialized range`).
  - What the documentation promised: [Nginx::Upstream#new](https://github.com/matsumotory/ngx_mruby/blob/v2.7.8/docs/class_and_method/README.md#nginxupstreamnewstring---upstream) and [Nginx::Stream::Connection#new](https://github.com/matsumotory/ngx_mruby/blob/v2.7.8/docs/class_and_method/README.md#nginxstreamconnectionnew) in 2.7.8 said that the method raises `RuntimeError` when no upstream has the name, and said nothing about the object afterwards.
- Affected: scripts that keep using an `Nginx::Upstream` or `Nginx::Stream::Connection` object after its `initialize` raised, or an object from `allocate`, and call `#server`, `#server=`, `#keepalive_cache`, `#keepalive_cache=`, `#upstream_server` or `#upstream_server=` on it. An object that `Nginx::Upstream.new` or `Nginx::Stream::Connection.new` returned behaves as before, and the methods of `Nginx::Stream::Connection` that do not use the upstream, such as `#remote_ip` and `#stream_status`, are not affected.
- What to do: create the object with `Nginx::Upstream.new` or `Nginx::Stream::Connection.new`, and do not use it when the call raises; to use another upstream, create another object. Code that called these methods on an object without an upstream got `nil` or ended the worker on 2.7.8.

## New features

None.

## Fixes

- `Nginx::Upstream#server`, `#server=`, `#keepalive_cache`, `#keepalive_cache=` and `Nginx::Stream::Connection#upstream_server` and `#upstream_server=` raise `ArgumentError` on an object whose `initialize` raised, or that came from `allocate`. Before, they returned `nil` or read through a NULL pointer and ended the worker process (#816)
- `Nginx::Upstream.new` and `Nginx::Stream::Connection.new` free the memory of the new object's context when they raise for an upstream with more than one server. Before, each such call left that memory allocated until the worker exited (#816)

## Build and test changes

- New test case: `test/t/cases/upstream_uninitialized.rb`, with the server of `test/conf/conf.d/97-upstream-uninitialized.conf` on port 18093 and the stream server of `test/conf/conf.d/stream/53-upstream-uninitialized.conf` on port 12397 (#816)
- The server of `test/conf/conf.d/96-argument-types.conf`, which `test/t/cases/argument_types.rb` tests, moved from port 18200 to 18092, the port it has on `next`. A new test case takes a port that is free on both `master` and `next`, from 18080 to 18199 for HTTP and from 12345 to 12399 for stream; `AGENTS.md` and `docs/test/README.md` say so (#819)

## Upgrading

- No directive was added, renamed or removed. Rebuild the module with this
  release the way you built 2.7.8, and replace the binary or the dynamic
  module as usual.

Check these before upgrading. Each line is the "What to do" of its entry
above.

- Scripts that keep using an `Nginx::Upstream` or `Nginx::Stream::Connection`
  object after its `initialize` raised: create the object with `.new`, and
  do not use it when the call raises.
