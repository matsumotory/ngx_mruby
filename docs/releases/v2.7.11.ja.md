# ngx_mruby v2.7.11

## 更新前に確認する挙動の変更

### 1. Nginx::Varが、$argsや$limit_rateのようにset_handlerを持つ変数に値を正しく代入する

- 変更前：`Nginx::Var`のアクセサ(`v.name = value`)と`Nginx::Var#set(name, value)`は、set_handlerを持つnginxの変数に代入するとき、値の構造体(`ngx_http_variable_value_t`)を`ngx_palloc`で確保し、そのフィールドを埋める前にset_handlerを呼んでいました。set_handlerを持つ変数とは、変更できる変数のうち、代入をnginxがハンドラで処理するもので、`$args`や`$limit_rate`がその例です。set_handlerは、未初期化の構造体から`len`と`data`を読みます。`$limit_rate`は未初期化のサイズを解釈し、`$args`は未初期化の長さとポインタを`r->args`にコピーしていました。そのため、代入した値は反映されませんでした。また、その後に変数を使うと、未初期化のワーカーのメモリを読みました。値を読み戻すときや、`$args`をクライアントへ送るときがこれにあたります。その結果、ワーカープロセスが終了するか、ワーカーのメモリが外へ送られることがありました。
- 変更後：ngx_mrubyは、set_handlerを呼ぶ前に、値の構造体のフラグ、`data`、`len`を埋めるようになりました。nginxがこのような変数に代入するときと同じ順序です。アクセサ(`ngx_mrb_var_set_vector`)と`Nginx::Var#set`(`ngx_mrb_var_set_func`)の両方を変更したので、set_handlerを持つすべての変数で、代入した値が反映されます。
- 変更の理由：
  - 不具合：set_handlerに渡す値の構造体は、`ngx_palloc`で確保したままで、フィールドが設定されていませんでした。そのため、set_handlerは未初期化の長さとポインタを読みました。
  - 前の挙動を残せなかった理由：代入した値が変数に届きませんでした。また、未初期化のメモリを読むことは、メモリ安全性の問題です。ワーカーはメモリを使い回すので、そのメモリに以前のデータの断片やヒープのポインタが残っていることがあり、それが`$args`を通じてクライアントへ送られることがあります。
  - ドキュメントが示していた挙動：ドキュメントは、アクセサと`set`がnginxの変数に値を設定すると書いています。set_handlerを持つ変数に代入すると、変数が設定されないままになることや、関係の無いメモリを読むことについては、何も書いていません。
- 影響の範囲：mrubyのコードで、`$args`、`$limit_rate`などset_handlerを持つ変数に`Nginx::Var`のアクセサか`#set`で代入し、その後にその変数を使う設定です。
- 必要な対応：対応は不要です。代入した値は反映されます。アップグレードできない以前のリリースでは、これらの変数の値は、`Nginx::Var`ではなくnginxの設定ファイルで指定してください。
- テスト：`test/t/cases/var_setter_init.rb`のポート18104のテストです。

### 2. リクエストとレスポンスのヘッダの削除が、ヘッダのlistの外に書き込まず、名前が完全に一致するヘッダだけを削除し、後で追加したヘッダを残す

- 変更前：`ngx_mrb_del_request_header`は、ヘッダのngx_listを順に調べ、満杯のpartの途中で名前が一致すると、そのpartを分割していました。この関数は、`Nginx::Headers_in#delete`と`Nginx::Headers_out#delete`から呼ばれます。`[]=`も、ヘッダを更新するとき、追加の前の削除にこの関数を呼びます。分割では、元のpartの配列の途中を指す2つ目のpartを作り、`headers->last`をそのpartに設定していました。そのため、次の`ngx_list_push`は、その配列の末尾の1つ先に要素を書き込みました。これは、隣接するワーカーのプールのメモリを壊すヒープバッファオーバーフローで、ワーカープロセスが終了することがありました。また、名前の比較では、削除に指定した名前の長さの分だけを比べていました。そのため、保存されているヘッダの名前の接頭辞にあたる名前で削除すると、そのヘッダを削除しました。また、指定した名前より短い保存済みのキーでは、その末尾を越えて読みました。さらに、2つ目のpartがあるときに最初のpartが空になると、`headers->last`を動かさずに、次のpartを最初のpartの位置に移していました。そのため、その後に追加したヘッダは、listから切り離されたpartに書き込まれたので、読み戻せませんでした。
- 変更後：削除は、一致した要素を取り除くとき、ほかの要素を動かしません。そのため、nginxがこのlistの要素を指して保持しているポインタは、同じヘッダを指したままになります。このポインタの1つは、nginxが専用のフィールドを持つヘッダの`ngx_table_elt_t *`で、`r->headers_in.user_agent`などがあります。もう1つは、同じ名前のヘッダをつなぐ`next`で、CookieやX-Forwarded-Forがその例です。また、`headers->nalloc`を最後のpartの空き容量以下に保ちます。`ngx_list_push`は、partの要素の数が`nalloc`に達すると新しいpartを確保するので、最後のpartの配列の先へ書き込まなくなります。名前の比較では、バイト列の前に長さを比べます。そのため、保存されているヘッダの名前の接頭辞にあたる名前は一致しなくなり、指定した名前より短い保存済みのキーの末尾を越えて読むこともなくなります。空になったpartをlistから外すときと、次のpartを最初のpartの位置に移すときには、`headers->last`と`headers->nalloc`を合わせて更新します。
- 変更の理由：
  - 不具合：分割によって`headers->last`が満杯の配列の途中を指したので、次のpushがその配列の先に書き込みました。名前の比較は、保存されている名前の長さを見ていませんでした。次のpartを最初のpartの位置に移すときに、`headers->last`を動かしていませんでした。
  - 前の挙動を残せなかった理由：配列の範囲外への書き込みはメモリ安全性の問題で、ヒープを壊してワーカーを終了させることがあります。長い名前のヘッダを、その名前の接頭辞で削除するのは誤りです。最初のpartが空になった後に追加したヘッダは、失われていました。
  - ドキュメントが示していた挙動：ドキュメントは、deleteが指定した名前のヘッダを削除すると書いています。名前が指定した名前で始まるだけのヘッダを削除すること、listのpartの範囲を越えて書き込むこと、後から追加したヘッダを失うことは、書いていません。
- 影響の範囲：mrubyのコードで、リクエストかレスポンスのヘッダを削除する設定です。オーバーフローが起きるのは、listのpartを満杯にするだけのヘッダを持つリクエストに、さらにヘッダを追加する場合です。接頭辞の件で影響を受けるのは、別のヘッダの名前の接頭辞にあたる名前でヘッダを削除し、両方のヘッダが削除されることを前提にしていた設定です。
- 必要な対応：オーバーフローと、追加したヘッダが失われる件については、対応は不要です。接頭辞の件については、ヘッダごとに正確な名前で削除してください。
- テスト：`test/t/cases/header_del.rb`のポート18105のテストです。

## ビルドとテストの変更

- `test/t/cases/var_setter_init.rb`(と`test/conf/conf.d/72-var-setter-init.conf`、ポート18104、`test/html/var_setter_init.rb`)は、`Nginx::Var`のセッターと`Nginx::Var#set`で`$args`に代入し、その値を読み戻します。
- `test/t/cases/header_del.rb`(と`test/conf/conf.d/73-header-del.conf`、ポート18105、`test/html/header_del.rb`)は、リクエストのヘッダを削除します。試すのは、ヘッダの名前の接頭辞にあたる名前での削除、2つ目のpartがあるときに満杯の最初のpartを空にする削除、満杯のpartの途中から削除してから、ヘッダを追加する場合の3つです。
