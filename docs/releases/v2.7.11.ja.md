# ngx_mruby v2.7.11

## 更新前に確認する挙動の変更

### 1. Nginx::Var が、set_handler を持つ変数($args や $limit_rate など)に代入する

- 変更前：`Nginx::Var` のアクセサ(`v.name = value`)と `Nginx::Var#set(name, value)` は、
  set_handler を持つ nginx の変数——代入を nginx がハンドラ経由で処理する、変更できる変数で、
  `$args` や `$limit_rate` など——に代入するとき、値の構造体(`ngx_http_variable_value_t`)を
  `ngx_palloc` で確保し、フィールドを埋めないまま set_handler を呼んでいました。set_handler は、
  未初期化の構造体から `len` と `data` を読みます。`$limit_rate` は未初期化のサイズを解釈し、
  `$args` は未初期化の長さとポインタを `r->args` にコピーします。そのため、代入した値が反映されず、
  その後にその変数を使う——読み戻す、`$args` をクライアントへ送る——と、未初期化の worker の
  メモリを読み、worker プロセスが終了したり、worker のメモリが外へ出たりすることがありました。
- 変更後：ngx_mruby は、set_handler を呼ぶ前に、値の構造体(フラグ、`data`、`len`)を埋めるように
  しました。nginx がこの種の変数に代入するときと同じ順序です。アクセサ(`ngx_mrb_var_set_vector`)と
  `Nginx::Var#set`(`ngx_mrb_var_set_func`)の両方を変更したので、set_handler を持つすべての変数で、
  代入した値が反映されます。
- 変更の理由：
  - 不具合：set_handler を、`ngx_palloc` で確保したフィールド未設定の値の構造体で呼んだため、
    未初期化の長さとポインタを読みました。
  - 前の挙動を残せなかった理由：代入が変数に届かず、未初期化の読み取りはメモリ安全の問題です。
    使い回された worker では、そのメモリに以前のデータやヒープのポインタが残っていることがあり、
    `$args` はそれをクライアントへ運びます。
  - ドキュメントが示していた挙動：ドキュメントには、アクセサと `set` は nginx の変数に値を設定すると
    書いてあります。set_handler を持つ変数への代入が、変数を未設定のままにする、別のメモリを読む、
    とは書いてありません。
- 影響の範囲：mruby コードが、`$args`、`$limit_rate` など set_handler を持つ変数に `Nginx::Var`
  (アクセサか `#set`)で代入し、その後にその変数を使う設定です。
- 必要な対応：対応は不要です。代入は反映されます。アップグレードできない以前のリリースでは、
  これらの変数を `Nginx::Var` でなく nginx の設定で設定してください。
- テスト：ポート 18104(`test/t/cases/var_setter_init.rb`)。

### 2. リクエストまたはレスポンスのヘッダの削除が、ヘッダの list の中に収まり、名前を完全一致で照合し、後で追加したヘッダを保持する

- 変更前：`ngx_mrb_del_request_header`(`Nginx::Headers_in#delete` / `Nginx::Headers_out#delete`、
  および追加の前に削除する `[]=` の更新の経路)は、ヘッダの ngx_list を走査し、満杯の part の途中で
  一致したとき、part を分割していました。part の配列の内側を指す 2 つ目の part を作り、`headers->last`
  をそれに設定したので、次の `ngx_list_push` が、その配列の末尾の 1 つ先に書き込みました。隣接する
  worker のプールのメモリへのヒープのバッファオーバーフローで、worker プロセスが終了することが
  ありました。また、要求された名前の長さの分だけを比較したので、あるヘッダの名前の接頭辞にあたる
  名前で削除すると、そのヘッダを削除し、短い方の保存済みのキーの末尾を越えて読みました。さらに、
  2 つ目の part があるときに最初の part が空になると、`headers->last` を動かさずに次の part を
  引き継いだので、その後に追加したヘッダが、切り離された part に書き込まれ、読み戻せませんでした。
- 変更後：削除は、残りの part の要素を手前へ詰めて、一致した要素を削除します。要素は part の `elts`
  から連続したままなので、`ngx_list_push` は part の確保した領域の中に書き込みます。名前は、バイト列の
  前に長さを比較するので、あるヘッダの名前の接頭辞にあたる名前は一致しなくなり、短い方の保存済みの
  キーの末尾を越えて読みません。空になった part を外すときと、最初の part が次の part を引き継ぐときに、
  `headers->last` を合わせます。
- 変更の理由：
  - 不具合：分割が `headers->last` を満杯の配列の内側に向けたので、次の push がその先に書きました。
    比較が保存済みの名前の長さを無視しました。そして、次の part を引き継ぐときに `headers->last` を
    動かしませんでした。
  - 前の挙動を残せなかった理由：領域外書き込みはメモリ安全の問題(worker を終了させうるヒープの
    破壊)です。長いヘッダを、その名前の接頭辞で削除するのは誤りです。最初の part が空になった後に
    追加したヘッダが失われていました。
  - ドキュメントが示していた挙動：ドキュメントには、delete は与えた名前のヘッダを削除すると
    書いてあります。名前が与えた名前で始まるだけのヘッダを削除する、list の part の先に書き込む、
    後で追加したヘッダが失われることがある、とは書いてありません。
- 影響の範囲：mruby コードが、リクエストまたはレスポンスのヘッダを削除する設定(オーバーフローは、
  list の part を満杯にできる数のヘッダを持つリクエストに、さらにヘッダを追加する場合)。接頭辞の件は、
  あるヘッダの接頭辞にあたる名前でヘッダを削除し、両方が削除されることに依存していた設定です。
- 必要な対応：オーバーフローと、失われるヘッダについては、対応は不要です。接頭辞の件は、各ヘッダを
  ちょうどの名前で削除してください。
- テスト：ポート 18105(`test/t/cases/header_del.rb`)。

## ビルドとテストの変更

  `test/html/header_del.rb`)が、リクエストのヘッダを削除します。ヘッダの接頭辞にあたる名前、
  2 つ目の part があるときに最初の part を空にする削除、満杯の part の途中からの削除とその後の
  ヘッダの追加です
