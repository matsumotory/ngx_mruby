# リリースノート

ngx_mrubyの各リリースには、このディレクトリに`vX.Y.Z.md`のファイルがあり、そのリリースで何が変わったかを書いています。ファイルの最初の節の「アップグレードの前に読む挙動の変更」には、同じ`nginx.conf`、Rubyのスクリプト、ビルドが前のリリースと違う動きをする変更を、すべて挙げています。各変更について、変えた理由、影響を受ける人、必要な対応も書いています。アップグレードの前に、今動かしているバージョンより新しいすべてのファイルで、この節を読んでください。ファイルの隣の`vX.Y.Z.ja.md`には、同じ内容を日本語で書いています。日本語版がまだ無いファイルには、そのファイルに追記するか、そのファイルを編集する次のプルリクエストが、日本語版を作ります。詳しくは「エントリーを書く人と時期」にあります。日本語版がまだ無いときは、英語版の`vX.Y.Z.md`を読んでください。英語版が原文で、日本語版はその翻訳です。

v2.7.0までのリリースには、ここにファイルがありません。それらのリリースでは、[GitHubのリリースのページ](https://github.com/matsumotory/ngx_mruby/releases)に、マージしたプルリクエストの一覧があります。

オーナーは2026-10-04に、次のことを決めました。「アップグレードの前に読む挙動の変更」の各エントリーには、修正が挙動を変えなければならなかった理由も書きます。理由は、前の挙動を前提にして設定やスクリプトを作った読み手が納得できる形で書きます。また、リリースノートは、英語と日本語で正確に書きます。セッションは、下のテンプレートの「変更の理由」の行、日本語のファイル、GitHubのリリースの本文、タグの前のチェックで、この決定を実行します。

## ブランチとサポート

v3.0.0でv3が`master`になるまで、`master`には2.xの系列があり、`next`にはv3の開発とそのプレリリースがあります。2.xを使い続けるときにどのブランチかタグからビルドすればよいかは、[Branch strategy](../../../README.md#branch-strategy)にあります。2.xは、v3.0.0の後12か月の間サポートします。サポートするのは、2.xの最新のリリースだけです。詳しくは[サポートするバージョン](../security/README.md#サポート対象のバージョン)にあります。

## 挙動の変更に数えるもの

挙動の変更とは、前のリリースとの違いのうち、設定、Rubyのスクリプト、ビルドから見えるもので、だれかがその挙動を前提にしていたかもしれないものです。次の一覧は例で、すべてではありません。そのような違いは、どれも挙動の変更として数えます。

- レスポンスのステータス、ヘッダ、ボディ
- `mruby_stream`のハンドラが送るデータと、ハンドラが接続を閉じるタイミング
- Rubyのメソッドが返す値と発生させる例外、どのクラスとメソッドがあるか
- どのハンドラが、どのフェーズで、どの順に動くか、その戻り値が何をするか
- `mruby_set`、`mruby_set_code`、`Nginx::Var`が設定するnginxの変数の値。ほかのディレクティブや`log_format`が読む値です
- `nginx -t`が設定を受け付けるかどうかと、ディレクティブの引数が持つ意味
- `error.log`の、レベルが`notice`以上の行のうち、加わった行、無くなった行、別のレベルで出るようになった行。運用者が、これらの行でアラートを出すからです
- ビルドの変更。ビルドの要件を上げること、nginxのstableの系列やプラットフォームのサポートをやめること、ビルドのオプションを消すか意味を変えること、同梱のmrubyか、デフォルトの`build_config.rb`が入れるmrbgemsを変えることです。要件を上げる例は、OpenSSLの最低のバージョンを上げることです。サポートするnginxのバージョンは、下の「サポートするnginxのバージョン」にあります

既存のすべての設定、スクリプト、ビルドが前と同じに動く追加は、挙動の変更ではありません。たとえば、新しいディレクティブ、新しいRubyのクラスやメソッド、ディレクティブが受け付ける新しい値です。このような追加は「新機能」に書きます。ビルドの追加の変更は、「ビルドとテストの変更」に書きます。

オーナーは2026-10-29に「修正対象をしようとして使ってた場合に変更で変わる場合はノート必須」と述べました。「しようとして」は「仕様として」という意味です。セッションは、修正対象のコードを使う設定やスクリプトから違いが見えるなら、挙動の変更と扱います。たとえば、レスポンスのステータスやヘッダが変わる場合や、値を返していたメソッドや受け付けていた引数が例外になる場合です。従来の挙動自体が不具合でも、利用者がそれを前提に実装している可能性があるため、記録が必要です。例外は、クラッシュ、ハング、リークだけを解消し、設定やスクリプトから見えるものがほかに何も変わらない場合に限ります。一部の使い方でクラッシュを直す一方、別の使い方で例外や新しい結果が生じるなら、後者は挙動の変更です。迷ったときは、挙動の変更として記録してください。

「前のリリース」は、前のコミットではなく、最後のリリースのタグ`vX.Y.Z`を指します。プレリリースのタグの`-alpha.N`、`-beta.N`、`-rc.N`は、この意味のリリースではありません。そのため、`v3.0.0.md`は、3.0.0を2.xの最新のリリースと比べます。2つのリリースの間で加わり、その後また変わった挙動は、一度もリリースしていません。2つ目を加えずに、そのエントリーを編集してください。

サポートするnginxのバージョン：ngx_mrubyは、nginxのmainlineとstableの系列をサポートします。系列は[README.md](../../../README.md)にあります。ビルドの方法は、[`docs/install/`](../install/README.md)の説明のとおりです。CIか`nginx_version`で、新しいバージョンに置き換えられたmainlineのバージョンから新しいバージョンへ移っても、サポートするバージョンは減りません。これは「ビルドとテストの変更」に記録します。stableの系列のサポートをやめることと、プラットフォームのサポートをやめることは、挙動の変更です。stableの系列は、1.28のように、マイナーバージョンが偶数の系列です。

テスト、CI、ドキュメントだけの変更と、見える違いの無いリファクタリングには、「アップグレードの前に読む挙動の変更」のエントリーは要りません。コントリビューターやパッケージャーが知る必要のあるテストやCIの変更は、「ビルドとテストの変更」に書きます。たとえば、テストの新しいポートです。そのほかのテストやCIの変更、ドキュメントの変更、リファクタリングには、エントリーはまったく必要ありません。

## エントリーを書く人と時期

- 変更をするプルリクエストが、同じプルリクエストでその変更を記録します。
  - 挙動の変更は、「アップグレードの前に読む挙動の変更」に書きます。上の一覧の最後の項目に書いたビルドの変更も、これに入ります。それらの変更は、「ビルドとテストの変更」に重ねて挙げてもかまいません。
  - ディレクティブ、RubyのAPI、ハンドラへの追加のうち、既存の設定とスクリプトが前と同じに動くものは、「新機能」に書きます。
  - そのほかの修正は、「不具合の修正」に書きます。
  - ビルドの追加の変更と、コントリビューターやパッケージャーが知る必要のあるテストやCIの変更は、「ビルドとテストの変更」に書きます。ビルドの追加の変更の例は、新しくサポートするnginxのバージョンや、新しいビルドのオプションです。テストやCIの変更の例は、テストの新しいポートです。
- リリースの周期の中で、記録することがある最初のプルリクエストが、下のテンプレートからファイルとその日本語版を作ります。その周期の後のプルリクエストは、両方に追記します。こうすると、ファイルはいつも、次にタグを付けるバージョンを説明します。
- 日本語版を必須にする前に作ったために、日本語版がまだ無いリリースのファイルがあります。そのようなファイルには、そのファイルに追記するか、そのファイルを編集する最初のプルリクエストが、日本語版を作ります。そのプルリクエストは、前のプルリクエストのエントリーも含めて、英語のファイルの全体を翻訳します。こうすると、2つのファイルに、同じエントリーがすべてそろいます。
- 同じプルリクエストで、[`docs/directives/`](../../directives/)、[`docs/class_and_method/`](../../class_and_method/)、[`docs/install/`](../install/README.md)を、新しい挙動を説明するように更新します。リリースノートには何が変わったかを書き、これらのドキュメントには今どう動くかを書きます。
- [AGENTS.md](../../../AGENTS.md#review-and-merge)のレビューでは、「アップグレードの前に読む挙動の変更」のエントリーが無い挙動の変更は「must fix」で、マージを止めます。テンプレートの行が欠けたエントリーも同じです。欠けた行には「変更の理由」も含みます。日本語版が無いエントリーと、日本語版が英語のエントリーと違うことを言うエントリーも、同じです。日本語を書かない作者には、レビュアーが日本語の文を渡してもかまいません。「新機能」「不具合の修正」「ビルドとテストの変更」のエントリーが無いことは、「should fix」です。そのようなエントリーの日本語版が無いことと、日本語版が英語のエントリーと違うことを言うことも、「should fix」です。レビューは、そのプルリクエスト自身のエントリーを確かめます。日本語版を必須にする前に作ったリリースのファイルについて、そのプルリクエストが日本語のファイルを作ることがあります。上の項目のファイルです。そのときは、前のエントリーの日本語版が無いことと、英語のエントリーと違うことを言うことを、そのプルリクエスト自身のエントリーと同じように評価します。つまり、「アップグレードの前に読む挙動の変更」では「must fix」で、ほかの節では「should fix」です。「変更の理由」の無い前のエントリーは、下の「タグの前に」に任せ、そのプルリクエストの所見にしません。
- 各タグの前に、1つのプルリクエストが、前のリリースの後にマージしたすべてのプルリクエストとファイルを照らし合わせます。下の「タグの前に」を見てください。

## ファイル名

ファイルの名前は、次にリリースするバージョンにします。別のバージョンでリリースすることになったときは、リリースの前に、ファイルとその日本語版の名前を`git mv`で変えます。

- v3を昇格する前の`master`：次の2.xのパッチリリースの名前です。タグ`v2.<minor>.<patch>`の後のファイルは、`v2.<minor>.<patch+1>.md`です。
- `next`：3.0.0の周期の全体に、1つのファイルの`v3.0.0.md`を使います。周期には、alpha、beta、rcのプレリリースも含みます。このファイルは、3.0.0を2.xの最新のリリースと比べます。`master`をマージして`next`に入った変更は、その変更を出す2.xのリリースのファイルに記録し、`v3.0.0.md`には重ねて記録しません。その2.xのリリースより前に3.0.0のタグを付けるときは、エントリーを`v3.0.0.md`にコピーします。
- v3を昇格した後は、`master`のファイルには次の3.xのリリースの名前を、`v2.x`のファイルには次の2.xのリリースの名前を、それぞれ付けます。

2.xから3.0.0にアップグレードする利用者は、自分のバージョンより新しい2.xのファイルを読み、その後に`v3.0.0.md`を読みます。

`vX.Y.Z.md`の日本語版は、同じディレクトリの`vX.Y.Z.ja.md`です。たとえば、`v2.7.1.md`の隣に`v2.7.1.ja.md`があります。日本語版は、原文である英語のファイルの翻訳です。日本語版には、英語のファイルと同じ節があり、同じエントリーが同じ順にあります。各エントリーは、英語のエントリーと同じことを言います。詳しくは、下の「日本語のファイル」にあります。このREADMEには、リリースのファイルとそのエントリーを作る、追記する、編集する、移す、コピーする、名前を変えるときの決まりを書いています。これらの決まりは、すべて日本語のファイルにも当てはまります。日本語のファイルの変更も、英語と同じプルリクエストでします。

v3の移行ガイドは、`next`の`docs/proposals/v3-plan.md`で計画していて、`v3.0.0.md`の「アップグレードの前に読む挙動の変更」の節を元に作ります。移行ガイドは、その節のすべてのエントリーを扱い、エントリーへリンクし、手順と例を加えます。移行ガイドには、変更の別の一覧はありません。そのため、3.0.0の各挙動の変更は、`v3.0.0.md`の中の1か所にだけ記録します。

## テンプレート

これを`docs/releases/vX.Y.Z.md`にコピーします。すべての節を残し、エントリーの無い節には「None.」と書きます。`docs/releases/vX.Y.Z.ja.md`には、下の「日本語のファイル」の見出しとラベルに置き換えてコピーします。

```markdown
# ngx_mruby vX.Y.Z

## Behavior changes: read before upgrading

### <The change, in one line> (#<pull request>)

- Before: <what a configuration, script or build observed on the previous release>
- Now: <what it observes on this release>
- Why it changed:
  - The defect: <what the old behavior got wrong, with the issue or pull request that reports it>
  - Why the old behavior could not be kept: <what keeping it would have left
    broken; in an entry with "The reason:", what keeping it would have cost>
  - What the documentation promised: <what the docs said about it before this
    release, with a link, or that they described the old behavior or said nothing>
- Affected: <the directives, handlers, methods, configurations or builds that see the difference>
- What to do: <the change to make, or "nothing", with the reason>

## New features

- <The addition, in one line> (#<pull request>)

## Fixes

- <The fix, in one line> (#<pull request>)

## Build and test changes

- <A newly supported nginx version, a new build option, a test or CI change> (#<pull request>)

## Upgrading

<Supported nginx versions, whether rebuilding the module is enough, and the
"What to do" lines above in one list.>
```

次の変更は、「ビルドとテストの変更」だけでなく、「アップグレードの前に読む挙動の変更」に書きます。ビルドの要件を上げること、nginxのstableの系列やプラットフォームのサポートをやめること、ビルドのオプションを消すこと、同梱のmrubyか、デフォルトのmrbgemsを変えることです。

「変更の理由」は、前の挙動を前提にしていて、なぜリリースがその挙動を残さなかったのかと問う運用者に向けて書きます。その3つの行には、前の挙動が誤っていたという主張だけでなく、読み手が確かめられる根拠を書きます。

- 不具合：前の挙動が何を誤っていたかを、それを報告するissueかプルリクエストとともに書きます。不具合を直さないエントリーでは、この行に「背景：」と書き、変更の理由を書きます。不具合を直さないエントリーの例は、ビルドの要件を上げること、nginxの系列やプラットフォームのサポートをやめること、同梱のmrubyやデフォルトのmrbgemsを更新すること、v3が意図して加える変更です。
- 前の挙動を残せなかった理由：不具合を直すのに、なぜ「変更後」に書いた違いが必要だったかを書きます。つまり、前の挙動を残すと、何が壊れたままになったかです。「背景：」と書くエントリーでは、この行に、前の挙動を残すと何を失ったかを書きます。たとえば、古い依存先がもう受け取らない修正や、v3でその変更をする目的のうち、前の挙動では果たせないものです。
- ドキュメントが示していた挙動：このリリースの前に、`docs/`がその挙動について何と書いていたかを、リンクとともに書きます。nginxが決める挙動では、nginxのドキュメントが何と書いていたかを書きます。これは、たいてい修正が戻す挙動です。ドキュメントが前の挙動を説明していたときや、何も書いていなかったときは、そう書きます。

エントリーの最後に、もう1つの行の「このリリースで変わらない挙動：」を置いてもかまいません。この行には、関係する挙動のうち、元のままのものを挙げます。読み手が、その挙動も変更に含まれると思うかもしれないときに使います。この行は任意で、テンプレートの中には含めません。

## 日本語のファイル

`vX.Y.Z.ja.md`は、`vX.Y.Z.md`の英語の文から、エントリーごとに書きます。次の決まりに従います。

- 見出し、行のラベル、「None.」は、下のテーブルのものを使います。こうすると、2つのファイルをエントリーごと、ラベルごとに比べられます。テーブルに無いラベルには、作者が選んだ日本語のラベルを付け、その後に全角のコロンを置きます。たとえば、「影響の範囲」の行の中の「Unchanged:」です。
- 日本語の文字と、ラテン文字、数字、コードスパンの間に、スペースを入れません。
- 日本語の約物を使います。読点は「、」、句点は「。」です。引用する語は「」で囲み、行のラベルの後ろには、全角のコロンの「：」を置きます。
- em dashのU+2014、米印のU+203B、絵文字を使いません。
- 英語の文が丸括弧の中で説明していることは、節か独立の文にします。丸括弧を残すのは、識別子の周りと、正式な名前の後に初めて使う略語の周りだけです。識別子の例は、`(#566)`というプルリクエストの番号です。
- コード、ディレクティブ、クラス、メソッドの名前、`error.log`の行、コマンド、ファイルのパス、issueとプルリクエストの番号、リンクは、英語のままにします。
- 各段落と各リストの項目は、ソースの1行にし、`<br>`も`<wbr>`も入れません。狭い画面で本文をどう折り返すかは、表示するGitHubかngx.mruby.orgのサイトが決めます。Markdownでは決めません。日本語は字の単位で折り返します。日本語の段落の中の改行は、GitHubがファイルから作るHTMLにも入り、Chromiumは2つの文字の間にスペースを表示します。

## タグの前に

リリースを公開する前に、1つのプルリクエストが、ファイルとその日本語版を、マージしたものと照らし合わせます。このプルリクエストは、前のリリースの後にブランチへマージしたすべてのプルリクエストを挙げます。一覧は`git log --first-parent --merges <previous tag>..origin/<branch>`で出します。各プルリクエストについて、エントリーがあるか、設定、スクリプト、ビルドから見えるものを何も変えないかを確かめ、無いエントリーを加えます。「アップグレードの前に読む挙動の変更」のエントリーのうち、テンプレートの行が欠けたものを補います。補う行には「変更の理由」も含みます。リリースに日本語のファイルがまだ無いときは、英語のファイルを翻訳して作ります。日本語のファイルがあるときは、英語のファイルと比べます。同じ節があり、同じエントリーが同じ順にあり、各エントリーが英語のエントリーと同じことを言うかを比べます。無い日本語のエントリーを加え、違うエントリーを直します。このプルリクエストの本文には、各プルリクエストと、そのエントリーの節を挙げます。エントリーが無いプルリクエストには、「no entry」とその理由を書きます。本文には、2つのファイルを比べたことも書きます。こうすると、この決まりより前にマージしたプルリクエスト、作者が決まりに従わなかったプルリクエスト、レビューが見落としたエントリーが見つかります。別のバージョンでリリースするときは、同じプルリクエストが、両方のファイルの名前を変えます。

チェックのプルリクエストには、開くときにラベル`full-matrix`を付けます。コマンドは`gh pr create --draft --label full-matrix`です。リポジトリにこのラベルがなければ、`gh label create full-matrix`で一度だけ作ります。このラベルがあると、`test.yml`の実行は`build`マトリクスの全セルをビルドし、`soak`も実行します。ほかのプルリクエストでは4セルだけを実行します。[docs/test/README.md](../test/README.md)の「実行するジョブの選択」を参照してください。

`next`では、範囲は前のプレリリースのタグから始まります。最初のプレリリースでは、2.xで最新のリリースのタグから始まります。`master`を`next`へマージすると、`master`へマージしたプルリクエストも一緒に入ります。それらは`git log --first-parent --merges <merge>^1..<merge>^2`で一覧できます。そのようなマージでは、チェックは、それらのプルリクエストのそれぞれに、2.xのファイルのエントリーがあることを確かめます。「ファイル名」を見てください。3.0.0のタグの前には、タグがまだ無い2.xのリリースについて、そのエントリーを`v3.0.0.md`にコピーします。

セッションは、オーナーがそのリリースの許可を出した後に、チェックのプルリクエストのマージコミットでリリースを公開します。許可は、リリースノートを用意したセッションがオーナーに求めます。コマンドは`gh release create <tag> --target <commit> --title <title> --notes-file <body>`で、リリースとそのタグを作ります。その後にマージしたプルリクエストは次のリリースで出し、そのリリースのチェックが、それらのエントリーをそのリリースのファイルへ移します。代わりに後のコミットでリリースを公開したときは、チェックのプルリクエストの後にマージしたプルリクエストについて、チェックを繰り返します。セキュリティの修正を出すリリースは、下の「セキュリティの修正」に書いた順に従います。

## GitHubのリリース

セッションがリリースを公開するときは、その本文に、英語を先にして両方の文を載せます。最初に英語のファイルからコピーした「Behavior changes: read before upgrading」の節を載せ、変更が無いときは「None.」と書きます。次に日本語のファイルからコピーした同じ節、最後に2つのファイルへのリンクを載せます。GitHubが生成するプルリクエストの一覧は、本文にコピーしません。プルリクエストは、リリースノートに挙げてあります。`next`のプレリリースでは、両方のファイルから、前のプレリリースの後に加わったエントリーと変わったエントリーをコピーします。それらは`git diff <previous pre-release tag> <new tag> -- docs/releases/v3.0.0.md docs/releases/v3.0.0.ja.md`で表示できます。最初のプレリリースでは、節の全体をコピーします。エージェントはファイルを用意し、オーナーの許可の後にリリースを公開します。アドバイザリはオーナーが公開します。[AGENTS.md](../../../AGENTS.md#branches-and-pull-requests)を見てください。

サイトのトップページは、最新の安定版のリリースを表示します。サイトは、ビルドするときにgitのtagからその版を読みます。リリースを公開した後に、そのセッションが`next`でサイトのworkflowを起動します(`gh workflow run site.yml --ref next`)。こうすると、次に`next`か`master`へのpushがサイトをビルドする前に、トップページが新しいリリースを表示します。

## セキュリティの修正

セキュリティの修正は、アドバイザリの非公開のフォークで用意し、新しいバージョンとしてリリースします。[SECURITY.md](../../../SECURITY.md)を見てください。修正のエントリーは、両方のファイルとも、修正と同じ非公開のプルリクエストで書きます。こうすると、タグを付けたファイルとリリースの本文に、エントリーが入ります。

- エントリーは中立に書きます。影響を受けるコンポーネントの名前を挙げ、今何が見えるかを書きます。問題を悪用する方法や再現する方法と、それが脆弱性であることは、何も書きません。
- 修正が挙動を変えるときは、その「アップグレードの前に読む挙動の変更」のエントリーに、変更前、変更後、変更の理由、影響の範囲、必要な対応を、同じ中立の言葉で書きます。「変更の理由」には、不具合を「変更前」が説明する違いとしてだけ書きます。詳細は、アドバイザリのidが指します。idは、下に書くとおり、アドバイザリを公開したときに加えます。
- アドバイザリの下書きは英語で書き、その後に同じ内容を日本語で書きます。オーナーは2026-10-29に、次のように依頼しました。「日本語でも後半でいいのでしっかりかいておいてほしい、今後は」
- オーナーがアドバイザリを公開したら、1つのプルリクエストが、両方のファイルのエントリーに、アドバイザリのidである`GHSA-xxxx-xxxx-xxxx`を加えます。セッションは、リリースの本文にある両方の文に、idを加えます。そのプルリクエストでは、アドバイザリが扱う修正を、「不具合の修正」のほかの修正と分けて挙げてもかまいません。また、公開したアドバイザリと、`src/`にある公開の修正で分かる範囲で、「変更の理由」に不具合の原因を書いてもかまいません。

セキュリティの修正を出すリリースは、次の順で用意します。こうすると、リリースの前に、修正が公開になっている時間が、できるだけ短くなります。

1. 「タグの前に」のチェックのプルリクエストを、修正より前にマージします。このプルリクエストは、その時点までにマージしたプルリクエストを扱います。修正の非公開のプルリクエストには、その修正のエントリーがあります。
2. オーナーが、アドバイザリの非公開のフォークから修正をマージします(アドバイザリの「Merge pull request(s)」)。その直後に、セッションが、修正のマージコミットでリリースを公開します。これは、チェックのプルリクエストのマージコミットでリリースを公開するという決まりの例外です。2つのマージの間に別のプルリクエストをマージしたときは、修正をマージする前に、そのプルリクエストのエントリーを確かめます。

アドバイザリを公開するまでは、公開のリポジトリのどこにも、脆弱性について書きません。[AGENTS.mdの「Security」](../../../AGENTS.md#security)を見てください。
