# 一つのMCP URLで文書サービスを振り分ける

**用途の設計案です。MCP連携の実行検証はまだありません。** 対象は`next`のngx_mruby 3.xです。HTTP振り分けとストリーム中継は検証されていますが、MCP専用の実例と相互運用テストは未実装です。以下のMCP要件は**2026-07-28**版を対象とします。構築するサービスが満たす要件であり、ngx_mrubyが自動で提供する機能ではありません。

## 誰のための構成か

文書検索、本文取得、重い原本処理を提供するサービスを想定します。利用者のMCP接続先を一つに保ちながら、運営者は処理先を分けたい。ゲートウェイに許可表とサービス固有の規則を置き、設定済みの処理先を選ぶ構成です。複数条件や業務の規則を組み合わせる場合にRubyが役立ちます。単純なヘッダーと処理先の固定対応なら、nginxの`map`だけでも足ります。

想定経路は**AIクライアント → 一つの`/mcp` → nginxとRubyの規則 →検索・本文取得・原本処理のバックエンド → 元の応答**です。原本処理と検索のワーカーを分ければ資源の競合を分離できますが、それだけで遅延や容量を保証するものではありません。実際の負荷で測定します。

LLM向けのMessages／Responsesと、MCP向けのJSON-RPCは別の経路です。一つのゲートウェイに両方のlocationを置いても、相互変換はしません。stdioとHTTPの変換器、MCPサーバー、ツール発見の集約機能、OAuth実装ではありません。

## 公開前に満たす責任

[Streamable HTTP仕様](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)と[版の規則](https://modelcontextprotocol.io/specification/versioning)を契約とします。受け付ける版を明示し、古いクライアントとの互換性は別途設計します。2026-07-28版はプロトコルのセッションとGETストリームを廃止し、SSE切断をキャンセルとして扱います。

`Mcp-Method`、`Mcp-Name`、`MCP-Protocol-Version`は、規定の復号後にJSON-RPC本文と一致する必要があります。宛先のMCPサービスはツール実行前に一致を検査します。ヘッダーだけでは権限を判断できません。discoveryと完全なツール一覧に責任を持つサービスを置き、未知のツールや非対応版を任意のバックエンドに流さず拒否します。JSON／SSE応答と必要なエラーヘッダーも保ちます。

Originを検証し、[MCPの認可契約](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)を満たします。RubyのHashでBearer文字列を照合するだけではOAuthになりません。リソースサーバー側で発行者、対象audience、許可scopeを検証し、別サービス用のトークンを転用しません。本文や秘密の識別子をログに残さず、`tools/call`の一律自動再試行も有効にしません。更新系ツールの再実行は副作用の重複につながります。

## 最初の実行可能な実例で確認する項目

後続の実例では、localhostのmock MCPバックエンドを二つと入口を一つ用意し、外部アカウントや実際の認証情報を不要にします。必要なテストは次のとおりです。

1. discoveryと完全なツール一覧、既知／未知のツール、対応／非対応の版、ヘッダーと本文の不一致。
2. 検索と原本処理の振り分け、リクエスト本文と応答バイトの保存。Rubyの規則を編集すると送信先が変わること。
3. Originの拒否、認可エラーと応答ヘッダー、JSON／SSE、切断時のキャンセル、更新系呼び出しを一度だけ送ること。
4. 古い版をサポートする場合は独立したケース。新版のセッションやキャンセルの規則をそのまま古い版へ適用しないこと。

実例が動くまでは、このページは責任分界の設計に使い、振り分けの実習にはHTTPの実例を使います。LLMテストを根拠にMCP準拠を宣言しないでください。
