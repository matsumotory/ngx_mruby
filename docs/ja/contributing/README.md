# 開発に参加する

ngx_mrubyは、GitHubのプルリクエストで変更を受け付けます。人からの変更も、コーディングエージェントからの変更も同じです。このページには、変更をどのブランチへ送るかと、プルリクエストに何が必要かを書いています。ルールの全体は[AGENTS.md](../../../AGENTS.md)にあります。エージェントは最初にAGENTS.mdを読みます。人にとっても、ルールの参照先はAGENTS.mdです。

## 変更を<wbr>送る<wbr>ブランチ

| 変更 | ベースブランチ |
|---|---|
| 2.xのクラッシュ、ハング、リーク、ビルドの失敗を直す修正 | v3.0.0でv3を`master`へ昇格するまでは`master` |
| 新しい挙動、新しいディレクティブやメソッド、APIの整理、v3のためのすべての作業 | `next` |

2.xの系列では、互換性を最優先にします。設定、スクリプト、ビルドから見える挙動は、不具合の修正に必要な範囲でだけ変えます。v3にも当てはまる修正は、`master`へ送ります。`master`は`next`へマージします。ブランチの説明は[Branch strategy](../../../README.md#branch-strategy)にあります。

セキュリティの脆弱性は、issueにもプルリクエストにも書きません。非公開で報告する方法は[SECURITY.md](../../../SECURITY.md)にあります。脆弱性の修正も、非公開で用意します。

## プルリクエストに<wbr>必要な<wbr>もの

- [プルリクエストのテンプレート](../../../.github/PULL_REQUEST_TEMPLATE.md)のすべての節を書きます。当てはまらない節には「n/a」と書きます。
- コードを変えるときは、実際のレスポンスを検証するテストを`test/`に加えます。できれば、`test/conf/conf.d/`にserverのフラグメントを、`test/html/`にそのスクリプトを、`test/t/cases/`にケースを置きます。書き方は[テスト](../../test/README.md)にあります。スイートは`sh test.sh`で実行します。ドキュメントだけの変更には、テストは要りません。
- 不具合を直すときは、2つのコミットに分けます。1つ目のコミットで回帰テストを加えます。この時点では、そのテストは失敗します。2つ目のコミットで修正を加え、そのテストを通します。プルリクエストには、各コミットでのスイートの結果を引用します。
- 設定、スクリプト、ビルドから見える変更をするときは、`docs/releases/<version>.md`の「Behavior changes: read before upgrading」にエントリーを加えます。`docs/releases/<version>.ja.md`にも、同じエントリーを日本語で加えます。詳しくは[リリースノート](../../releases/README.md)にあります。
- ディレクティブ、Rubyのメソッド、ビルドのオプション、テストのハーネスを変えるときは、`docs/`のドキュメントも更新します。
- `src/`、`mrbgems/`、ビルドを変えるときは、AGENTS.mdの「Design principles」にある性能の比較を付けます。

## レビューと<wbr>マージ

プルリクエストを書いていない人が、AGENTS.mdの「Review and merge」のチェックリストでプルリクエストをレビューし、指摘をコメントに書きます。プルリクエストは、次の条件がそろったときに、マージコミットでマージします。headのコミットでCIが通ること、レビューの「must fix」の項目が残っていないこと、AGENTS.mdに挙げたほかの条件を満たすことです。タグ、リリース、セキュリティのアドバイザリは、オーナーが扱います。

## 質問する<wbr>場所

質問、セキュリティの脆弱性ではない不具合、提案は、GitHubのissueに書いてください。v3の大きな計画は[docs/proposals/](../../proposals/)にあります。作業の状態は[docs/HANDOFF.md](../../HANDOFF.md)にあります。
